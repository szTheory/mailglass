<objective>
Scope the release-please `mailglass` core package so it stops claiming the repository's own
build and tooling directories, then close the empty release proposal PR #222 so release-please
regenerates under the corrected config.

`test/`, `reference/`, `ci/`, `test_js/`) register as core *library* features and fixes. PR #222

<ordering_decision>
**The config fix MUST be merged to `main` before PR #222 is closed.** This ordering is binding.

Rationale: release-please re-evaluates only on pushes to `main`, and it recreates a closed release
PR on its next run. If #222 were closed first, the very next push to `main` — including an unrelated
one from any other work — would regenerate the same stale `2.6.0` proposal under the *old* config,
reopening exactly the mergeable-stale-proposal hazard this task exists to close. Merging the config
fix first means every subsequent release-please run, including the one triggered by the fix's own
merge, evaluates under the corrected `exclude-paths`.

Merging the fix will cause release-please to *update* #222 in place under the new config. That is
expected and harmless; Task 3 still closes it, so the regenerated proposal is built from a clean
slate rather than an amended stale branch.

**Commit-type constraint:** the fix commit MUST use `chore:`. `release-please-config.json` sits at
the repo root and is itself claimed by the core package; a `feat:` or `fix:` title would register
this very change as a core library change in the next proposal.
</ordering_decision>
