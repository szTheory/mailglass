## Phase Details

### Phase 179: Compatibility Policy, Status Map and Brand Pin
**Goal**: Every later phase works from one tested source of truth: which public names stay, what each status and renamed word says on screen, and which brand book (by hash) is canonical. The trademark search result is on record before anything depends on it.
**Depends on**: Nothing (first phase of v2.11)
**Requirements**: BRPOL-01, BRPOL-02, BRPOL-03, BRPOL-04, BRPOL-05
**Success Criteria** (what must be TRUE):
  1. A maintainer can open the compatibility policy file and find every public name that stays (`Mailglass.Operator.*`, `mailglass_operator_routes`, `:operator_access`, `tenant_id`, `:orphan_backlog`, telemetry event names, the `Delivery.status` enum), plus the rule that on-screen and docs words are glossed, never renamed.
  2. The status map's unit test covers all 26 status/event atoms (the 25 badge atoms plus `:subscribed`). Each atom maps to exactly one of Sent, Delivered, Delayed, Failed, Not sent, or "not a delivery status", and an unmapped atom fails the test. The answer to "is Not sent ever a persisted `Delivery.status :suppressed` row, or only a pre-send block?" is recorded with the code path that settles it.
  3. Changing a screen string owned by `MailglassAdmin.Copy` without updating `Copy` fails the copy contract test. A recorded mutation run proves this.
  4. The brand pin test passes against zip sha256 `ed96bb25634ed158f4aeca40d97a892aef368fcc7528ba8cc5a55489b955f87b` and fails when the recorded hash or a copied-in shipped asset is altered. The full book is not in the repository tree.
  5. The trademark, image and register search result for the name and mark is committed with its date, sources searched and outcome, in the place Phase 183 reads as its announcement gate.
**Plans**: 2/4 plans executed

Plans:

- [x] 179-01-PLAN.md — StatusMap + Copy table, components delegation, status-map and copy contract tests with mutation proof, "Not sent" zero-row proof, 25-to-26 amendment (BRPOL-02, BRPOL-03)
- [x] 179-03-PLAN.md — Brand book pin by commit and zip sha256, brandbook/v2 shipped assets, hermetic tamper test, advisory check (BRPOL-04)

**Wave 2** *(blocked on Wave 1 completion)*
- [ ] 179-02-PLAN.md — Brand v2 compatibility policy with parsed, live-verified stays table and api_stability pointer (BRPOL-01)

**Plan budget**: about 3

### Phase 180: Reproducible Admin Bundle and Before-Catalog
**Goal**: The committed admin bundle can be regenerated and diffed by a CI lane that actually runs, `<html>` alone controls the theme, and the current screens are captured on realistic fixtures so the token swap can be judged against a known "before".
**Depends on**: Phase 179 (milestone order; one open PR at a time)
**Requirements**: BRPIPE-01, BRPIPE-02, BRPIPE-03
**Success Criteria** (what must be TRUE):
  1. Running the committed generator reproduces the committed admin bundle byte for byte, and its `--check` mode exits non-zero on any drift.
  2. A required CI lane runs the `--check` gate. A deliberately drifted bundle fails that lane, so "CI diffs the committed admin bundle" is enforced rather than claimed.
  3. Only the `<html>` element carries `data-theme`. Switching light, dark and system re-themes every admin surface, including the region the nested attribute used to shadow, and a browser test checks this.
  4. Before-screenshots of each current admin screen exist on the Northstar, Fjordline and Helios fixtures plus the UX lens's delivery cases. They are stored at unique paths and record the source commit SHA from before any token change.
**Plans**: TBD
**Plan budget**: about 4 (bundle reproducibility is time-boxed; fallback is committing the assembly script as-is behind the same `--check` gate)

### Phase 181: Brand v2 Tokens, Fonts and Logo
**Goal**: In one coordinated change, the admin dashboard takes on brand v2.0 colors, typography and mark in light and dark. Every contrast pair and font asset is verified by tests, and the host's email defaults stay exactly as they were.
**Depends on**: Phase 180 (reproducible bundle and drift gate; before-catalog captured)
**Requirements**: BRTOK-01, BRTOK-02, BRTOK-03, BRTOK-04, BRTOK-05, BRTOK-06
**Success Criteria** (what must be TRUE):
  1. All 36 admin theme slots resolve to brand v2 values through the explicit role map in both light and dark, including the slots with no direct v2 source (solid, on-solid, sunken, input border and the rest). The regenerated bundle passes the Phase 180 drift gate and the updated `token_parity_test`.
  2. A static contrast test checks every declared foreground/background pair per theme against the book's ratios, and lowering any pair below its ratio fails it. `mix.lock` gains no new dependency.
  3. The admin renders Funnel Display at weight 600 and the other faces from the seven bundled woff2 files in `priv/static/fonts`, with the OFL texts beside them. A browser network check shows no font request leaves the host, and a font outside `@allowed_fonts` is rejected.
  4. The new logo and favicon appear in the admin, and the `←` glyph is gone from every screen. The updated `brand_test` and `accessibility_test` pass, and the axe baseline is regenerated exactly once, as the phase's last change.
  5. `config.ex`, `theme.ex`, the email button colors and the VML goldens show no diff, and their existing tests pass without edits.

### Phase 182: Admin Words and Layout, One Job First
**Goal**: An operator handling "a customer says the password reset never arrived" gets a truthful answer in brand v2 words through the real dashboard. The same words, time zones and status marks then roll out across every admin screen, without rendering anything the product cannot honestly know.
**Depends on**: Phase 181 (v2 tokens, fonts and logo in place); uses Phase 179's status map and `MailglassAdmin.Copy`
**Requirements**: BRADM-01, BRADM-02, BRADM-03, BRADM-04, BRADM-05, BRADM-06, BRADM-07
**Success Criteria** (what must be TRUE):
  1. Through the real LiveView, in light, dark and at 375px, an operator searches by email, finds the delivery under Needs attention, and reads a timeline that gives a verdict, says "sent is not delivered" and offers a next step. A browser test against the demo fixtures covers the whole path.
  2. Every time on every admin screen shows its zone, and every status shows a pane mark plus a word from the status map. A contract test fails on a bare time or a mark-only status.
  3. Screen text says "Activity" for Deliveries, "Admin" for Operator, "Account" for Tenant, and "N provider reports match no email" for orphan events. Each mailer shows its plain name with an accessible tooltip. `deliveries_path`, module names and other public names are unchanged, and the existing route and API contract tests pass unedited.
  4. A cause sentence appears only when `reject_reason` or the suppression reason exists; otherwise a fixed honest fallback appears. A contract test proves that "next try at…", "will retry" and cause text with a nil reason never render.
  5. A separate review agent judges each scenario against the book and the Phase 180 before-catalog, and its rejection gate passes. Evidence is stored at unique paths with the served SHA recorded after a server restart.
**Hand-off from Phase 179**: the operator Deliveries projection carries only `status`, `last_event_type` and `delivery_confirmed`, so on that row a bounce followed by an open reads Sent. Before showing a `StatusMap.delivery_class/1` verdict, add `bounced_at` and `terminal` to `Mailglass.Operator.Deliveries.delivery_projection/1` (additive core change), or show the limitation on screen.

**Plan budget**: about 5
**UI hint**: yes

### Phase 183: Docs, Packaging and Launch Prep
**Goal**: Everywhere an adopter meets mailglass outside the dashboard (the hex.pm README, HexDocs, Hex package contents, browser favicon) carries brand v2.0 correctly. Nothing irreversible (an announcement or a ™ claim) goes out before the Phase 179 search result allows it.
**Depends on**: Phase 182 (milestone order); needs Phase 181's logo and font assets and Phase 179's search result
**Requirements**: BRDOC-01, BRDOC-02, BRDOC-03, BRDOC-04, BRDOC-05, BRDOC-06
**Success Criteria** (what must be TRUE):
  1. The README header uses `<picture>` with absolute `raw.githubusercontent.com` URLs pinned to a tag, so it renders on hex.pm. A test rejects relative image paths in the README.
  2. A real `mix docs` build succeeds for each of the three packages. The output carries the "m" logo and code-color-only CSS with no OS `prefers-color-scheme` media query, and the ExDoc body font stays Lato.
  3. `design-system.md` and the `.impeccable` config exist, and the CLAUDE.md/PRODUCT.md updates are drafted and waiting for owner sign-off.
  4. The lowercase-name lint passes. The Hex file allowlist includes the shipped brand assets (fonts, OFL texts, logo) and nothing more, and `mix mailglass.publish.check` passes for every package.
  5. Automated favicon captures at 16, 24 and 32 px exist for Chromium, Firefox and WebKit. A social card/avatar manual-upload checklist with full URLs is written. The announcement and any ™ text are blocked unless the Phase 179 search result clears them, while the code rollout itself is not gated.
