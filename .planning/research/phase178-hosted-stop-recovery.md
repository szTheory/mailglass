## Finding and recommendation

`EEF-CVE-2026-117645` is an XSS issue when attacker-controlled attribute names reach `Phoenix.HTML.attributes_escape/1`; affected Hex versions include `phoenix_html` 4.0.0 through versions before 4.4.0. The Erlang Ecosystem Foundation (EEF) CNA and OSV both name **4.4.0** as the first fixed release in the compatible 4.x line (3.3.5 fixes the separate 3.x line). [CITED: [EEF CNA](https://cna.erlef.org/cves/CVE-2026-117645.html), [OSV](https://osv.dev/vulnerability/EEF-CVE-2026-117645)]

Refresh `phoenix_html` to **4.4.0** in the three lockfiles scanned by the required Hex Audit: root, `mailglass_admin`, and `mailglass_inbound`. Each currently pins 4.3.0; the existing root and admin constraints already admit 4.4.0, and the demo lock already records it. Keep this a targeted dependency update—do not upgrade the whole tree or suppress the advisory. ## Options, risks, and checks

- **Preferred: targeted lock refresh in each scanned project.** Run `mix deps.update phoenix_html` from the root, `mailglass_admin`, and `mailglass_inbound`. Mix 1.18.4 documents targeted `deps.update`; the fixed demo lock records the 4.4.0 package with an empty dependency list (`[]`), so no new dependency is needed. [VERIFIED: local `mix help deps.update` under Mix 1.18.4] “Updates the given dependencies”; [VERIFIED: candidate `reference/demo_app/mix.lock:38`] the 4.4.0 tuple contains `[],` as its dependency list.
- **Optional, broader guard:** raise direct constraints from `~> 4.1` to `~> 4.4` in root/admin along with the lock refresh. This rejects pre-fix 4.x resolutions if a lock is regenerated, but changes package constraints and is not needed to clear the present locked finding. The demo already proves the existing `~> 4.1` constraint can resolve 4.4.0.
- **Do not ignore or allowlist this CVE.** Hex audit exits nonzero for advisory findings; the project’s accepted-advisory contract says only advisories without an upstream fix may be accepted, and fixable findings must hard-block. [CITED: [Hex `mix hex.audit` docs](https://hex.hexdocs.pm/Mix.Tasks.Hex.Audit.html)]; [VERIFIED: `test/mailglass/supply_chain/accepted_advisories_test.exs:8-10`] “The allowlist exists ONLY for advisories with no upstream fix in any release; every fixable advisory must still hard-block”.
- **Compatibility check:** upstream’s fix validates attribute names and raises on malformed names (empty names, whitespace, quotes, `>`, `/`, `=`, control characters, or DEL). Standard HTML attribute names should continue to work; exercise rendering/tests that build dynamic attribute maps, especially if names can come from input. The advisory is exploitable only when untrusted names reach HTML rendering. [CITED: [upstream validation patch](https://github.com/phoenixframework/phoenix_html/commit/a47dc8944a773b7e9273d9691dc6744ec793f1de), [EEF CNA](https://cna.erlef.org/cves/CVE-2026-117645.html)]

**Local verification after the lock edits:** with the installed Elixir 1.18.4 / OTP 27 toolchain, run `mix deps.get --check-locked` separately in all three audited directories, then root `mix mailglass.audit --kind hex`. Also run the existing fast compile gate and affected ExUnit suites to detect invalid dynamic attribute names. The audit wrapper itself uses plain `deps.get`, so the explicit `--check-locked` checks matter. Hex documents that an offline cached registry may miss recently published advisories; verify with the normal online audit, not `HEX_OFFLINE=1`. [VERIFIED: local toolchain command output] `Mix 1.18.4 (compiled with Erlang/OTP 27)`; [VERIFIED: `.github/workflows/ci.yml:782-805`] the hosted job is named `Hex Audit (Elixir 1.18 / OTP 27)` and runs `mix mailglass.audit --kind hex`; [CITED: [Hex audit cache behavior](https://hex.hexdocs.pm/Mix.Tasks.Hex.Audit.html)].

**Hosted boundary:** do not rerun the failed SHA’s job. Phase 178 D-13 states “No rerun of any hosted job is pre-authorized; a rerun needs a new owner approval.” After local fixes and a new candidate SHA, obtain that approval before any hosted dispatch. [VERIFIED: `178-CONTEXT.md:39`].

## Uncertainty

The advisory sources agree on 4.4.0 as the fixed 4.x release. No dependency update, tests, or hosted action was run for this note. The only compatibility uncertainty is whether application or fixture code relies on malformed dynamic attribute names; the recommended rendering tests should settle that locally.
