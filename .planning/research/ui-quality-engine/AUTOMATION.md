# UI quality engine: automation, accessibility, security, and CI

**Date:** 2026-10-26. **Status:** reviewed recommendation; no implementation or CI changes made. Evidence is current source inspection, not a claim that the UI or tests passed today. This note adapts the owner's methodology to Mailglass and supplies the automation portion of the proposed rolling milestones.

## Recommendation

Extend the existing ExUnit, Playwright, axe, token checks, and evidence reporting. Build a manifest-driven Storybook sweep against the real production components. Make fresh results—not a committed historical score—the input to a shrink-only regression gate. Keep connected tests for the LiveView, authorization, persistence, URL, and navigation seams that isolated stories cannot prove. Measure a representative pilot before deciding CI placement or promising a runtime advantage. Add no dependency for a manifest, geometry checks, contrast arithmetic, or findings bookkeeping.

The owner decision in `.planning/METHODOLOGY.md` is binding: **“Put each assertion at the cheapest boundary that proves the user-visible contract”** and **“add or promote a required CI lane only when recurring regression risk justifies its runtime and maintenance cost.”** The source prompt's default that all of L2 is immediately blocking must be implemented with that evidence and the existing CI contract, rather than assumed from a job name.

### Two existing false-confidence risks to close first

1. **Fresh axe results currently are not a fresh regression gate.** `axe-baseline.spec.js` scans 3 surfaces × 3 themes, ensures numeric result shape and required overlays, and writes JSON only with `PERSIST_AXE_BASELINE`. In ordinary CI it does not compare the newly measured violations to an allowed baseline. `axe_baseline_test.exs` compares the two committed JSON blocks. These are useful schema/comparator checks but do not establish that this commit has no new axe violations. The committed `current.run_id` is `axe-2026-06-21T15-53-05-411Z`; each of its 9 cells records one finding. Keep it as history; generate fresh results and compare fingerprints on every intended gating run.
2. **A job's name/comments do not establish protection.** `judgment.spec.js` calls Operator Browser Gate “REQUIRED”; `.github/workflows/ci.yml` currently omits `operator_browser_gate`, `demo_browser_evidence`, and `preview_capture_advisory` from `ci_green.needs`. Thus they are outside the repo's CI Green aggregate. Live branch-protection configuration was not queried in this research; do not infer whether one is independently required by GitHub. Before promoting a story lane, reconcile `ci.yml`, the CI policy scripts/tests and actual required checks as one change. Report advisory evidence as advisory until that is proved.

The score ledger's `current.run_id` is `2026-06-28-phase-123`: 3 surfaces × 6 pillars × 3 themes = **54 historical numeric cells**. Its comparator proves the committed records do not regress, not current visual quality. Preserve history; a new binary advisory rubric must not silently rewrite it or claim its scores are newly measured.

## The matrix: exhaustive about reachable states, selective about redundant axes

Use state equivalence classes, with a documented source caller/read-model and persona/JTBD for every variation. The manifest must identify component, tier, stable story/variation ID, fixture/scenario ID, description, applicable checks, and screenshot selection. Missing expected entries, empty discovery, unknown IDs, skipped required cells, uncaught console/page errors, unavailable fonts/CSS, failed navigation and failed axe scans all fail the run. Report expected, attempted, passed, failed, skipped and not-applicable counts separately. A deliberate N/A needs a reason; it must never become a silently passing cell.

The current matrices differ: Gallery uses **320/390/768/1440** × light/dark/system (`gallery-matrix.spec.js`); primitive structural checks use **320/768/1280**; other specs include 375, 1024, 2048 and actual zoom. Do not delete 390px or an existing regression width merely to standardize. Adopt 320/375/768/1280/1440 as the shared review landmarks, retain defect-triggering widths such as 390, and add actual layout thresholds at threshold−1/threshold/threshold+1 for the owning layout. Check the content container as well as the viewport: the same component is used inside a pane, not only edge-to-edge.

Recommended run profiles, to validate with the pilot:

| Profile | Scope | Purpose |
|---|---|---|
| Fast source/fixture gate | Every declared scenario and story metadata; fixture invariants, packaging/dev-only checks, token and copy rules | Cheap completeness and reachability assurance |
| Story geometry smoke | All declared states, five landmark widths, explicit light + dark, required CSS/fonts and no page errors | Broad cheap layout coverage; measure before treating thousands of navigations as cheap |
| Interaction/a11y | Every distinct semantic/interaction state; all themes/layouts where semantics, visibility, hit area, or contrast changes | Axe plus real focus/keyboard checks; avoid re-running identical axe trees solely because a numeric count changed |
| System and motion | Each theme-owning shell and representative primitive/pattern; both OS preferences under System; reduced motion on every actual motion family | Prove selection/propagation and interruption, rather than triple every static story |
| Screenshots/advisory review | Explicit key state + worst case per section; narrow/wide in light/dark; more widths only for a known visual transition | Preserve useful review signal without a wall of nearly identical goldens |
| Connected journeys | Existing selected Admin and demo flows with real routing/auth/data | Prove events, account scope, mutations and returned outcomes; isolated UI cannot establish these |

This is a proposed factorization, not permission to omit a meaningful theme/state/layout combination. The manifest records which equivalence argument covers each cell. Where that argument is absent, run the full applicable combination. A token/theme-wide change expands selection to every affected story. If reliable dependency selection is unavailable, run the full set; an untrusted changed-files heuristic must not produce green coverage claims.

Pilot on one primitive, one group, one area and one whole screen, including an overlay, long non-ASCII content, empty state and error state. Measure cold/warm host startup, per-cell geometry time, axe time, total wall time, runner minutes, failure diagnosis and flaky count. Synthesis target: **≤5 minutes additional PR wall time and ≤10 additional runner-minutes for the initial story gate**, including setup; these are budgets to test, not measured performance claims. Record the accepted budget and matrix before promotion. If exceeded, first reuse page/host setup safely, remove duplicate assertions and partition independent story tests; retain the accepted coverage. Extended sweeps may be separately scheduled only with explicit scope labels and a retained required minimum—never describe a partial PR run as the full matrix.

Playwright shards test files by default; balanced test-level sharding requires parallel-safe tests and appropriate `fullyParallel` configuration. Generate independent cases or deterministic manifest partitions, collect every partition's expected IDs and merge results, and fail the fan-in on a missing shard. Never enable parallelism on the current shared-reset demo database. [Playwright sharding](https://playwright.dev/docs/test-sharding)

## Correct the generic checks before making them gates

| Generic prescription | Mailglass recommendation and tradeoff |
|---|---|
| Every token foreground/background pair must pass contrast | Check **allowed semantic usages**, including opacity/compositing and state backgrounds; not arbitrary palette pairings. Preserve decorative divider exemptions. `accessibility_test.exs` intentionally pins decorative borders below 3:1; darkening all dividers would violate the brand without improving meaningful controls. Body text uses 4.5:1; qualifying large text 3:1; meaningful non-text states/focus use applicable 3:1 adjacent-color checks. No rounding a below-threshold ratio into a pass. [Contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), [non-text contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html) |
| Ban all arbitrary classes, inline styles and numeric z-index everywhere | Scope the rule to authored Admin presentation and use named exceptions for legitimate host data/content, dynamic positioning and browser-native styles. The current CSS describes an inline `--mg-origin` customization and uses named z-layer utilities. The source guide still documents numeric layer mappings. Migrate mapping and callers together; do not make an undifferentiated grep failure into a redesign. Never scan generated bundles as if every library-emitted value were hand-authored |
| Every computed style must be a token value | Check owned typography, surface, radius, elevation, motion and layer contracts on marked components. Account for unit resolution, inheritance, composed shadows, zero/none/auto, borders, transforms and zoom. First static token-use checks, then narrow computed checks proving the rendered result. Banning every browser default is brittle and makes data tables/native inputs accidental exceptions |
| All interactive boxes must be ≥24px | Distinguish the **WCAG AA minimum with exceptions** from Mailglass's **44px primary/touch-control design floor**. Test the actual clickable target or associated label, excluding hidden/inert content; retain inline-link and UA-control distinctions. A blanket box check is a useful conservative product rule only if labelled as stricter than WCAG. [WCAG target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum) |
| Any horizontal overflow fails | Fail page-level overflow and clipped required content. Permit explicitly identified, keyboard-accessible two-dimensional content inside its own scrolling region where appropriate, with a visible affordance; do not hide overflow to get green. The current Gallery checks per-specimen overflow and explicitly exclude its shell; the new isolated-story and whole-page checks must report those as different contracts. [WCAG reflow](https://www.w3.org/WAI/WCAG21/Understanding/reflow) |
| 200% root font size proves zoom | Preserve the **actual browser zoom extension** already exercised by `phase170-journey.spec.js` and `structural.spec.js`. Root `font-size` changes are a separate stress test and may not scale px-authored text at all. Verify actual 200% text enlargement without lost controls/content; test reflow at 320 CSS px and a representative real 400% zoom route. Also add text-spacing override stress to selected composed states. [Resize text](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html), [text spacing](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html) |
| All axe incomplete results are violations | Retain incomplete/needs-review output as a finding requiring disposition; it means axe cannot decide, not that failure is proved. Unreviewed new findings prevent a “fully reviewed” claim. Use targeted evidence to resolve them, otherwise track the unresolved item with scope/owner; do not relabel all as violations or silently drop them. [Deque result definitions](https://docs.dequelabs.com/devtools-for-web/4/en/needs-review-incomplete/) |
| One generic Tab walk proves focus | Native radio groups, tabs and menus need arrow-key semantics; dialogs need entry, containment, Escape, dismissal and return. A generic Tab walk can catch missing visibility/obscuration but cannot decide all sensible order. Wait for LiveView mounted focus and use retrying assertions; this addresses the known focus race in CI research without sleeping or broad retries. AA focus-not-obscured requires not entirely hidden; prefer fully visible for the product. [WCAG focus](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html) |
| Navigation ARIA snapshots must be identical everywhere | Compare the **stable navigation structure/order and available destinations** within the same role/account context; assert exactly the right active item per route. `aria-current`, current-page labels, permission-dependent destinations and legitimate subnavigation differ. Exact equality would preserve the wrong active-state bug that `judgment.spec.js` currently guards. [Consistent navigation](https://www.w3.org/WAI/WCAG22/Understanding/consistent-navigation.html) |
| Glossary lint bans all technical words | Scope to library-authored visible copy and accessible names, not subjects, module identifiers, provider evidence or user data. Preview authors may need a real Mailable module name; support users may need exact IDs. Maintain explicit context and terminology entries so a blanket regex does not erase truthful evidence |

Automation checks some accessibility defects, not accessibility conformance in full. Retain a bounded manual/assistive-technology assessment for semantics and behavior beyond reliable automation; this is compatible with D-52's human-judgment boundary. [Playwright accessibility guidance](https://playwright.dev/docs/accessibility-testing)

## Fresh ratchets and reproducible evidence

Keep one historical evidence lineage, with per-check fingerprint = rule + stable component/state + semantic target + viewport/theme/motion scope. Compare fresh output to the reviewed allowlist, not merely totals. Flat counts can conceal a fixed old defect replaced by a new one; broad selectors can forgive a new target accidentally. No new violation fingerprint is allowed, existing severity cannot worsen, and repaired entries disappear. Store suppressions separately with a specific reason and revalidation trigger; never turn an owner taste decision into a blanket security or WCAG exemption. A growing baseline requires a deliberate reviewed policy decision, not an automatic “update snapshots” script.

Every finding should name commit/source hash, story/variation and fixture IDs, URL, viewport and container dimensions, explicit theme + OS preference, motion setting, browser/toolchain, check/rubric ID, severity, evidence and lowest owning tier. Save sanitized DOM/ARIA and screenshot/trace on failure. Report console exceptions, incomplete scans, missing shards and flaky-on-retry counts distinctly from passed checks. Playwright's passed/flaky/failed categories are useful; do not turn a retry pass into a claim that the first run was clean. [Retries](https://playwright.dev/docs/test-retries)

For selected screenshot contracts, use the same pinned browser/OS/container, DPR, fonts-ready wait, deterministic clock and synthetic data; disable animation only for stable capture, while motion has separate behavior checks. Mask only irrelevant changing values, never the data or focus ring being tested. Review every baseline change and preserve before/after context. Rendering varies by environment, so local/macOS screenshots are not interchangeable with Linux CI goldens. [Playwright visual comparisons](https://playwright.dev/docs/test-snapshots)

## Story coverage and integrated proof

The manifest is a curated coverage contract, not the source of UI implementation. Generate it through the pinned storybook API and compare it to committed metadata in CI; assert uniqueness and nonempty output. Track required JTBD/state rows with implemented/story-covered/connected-test-covered/not-applicable status. New components, variants and public state branches require a story or a reason. A story inventory generated solely from existing stories cannot reveal missing coverage, so reconcile it with current callers and the persona/JTBD map at each milestone boundary.

When an area moves from Gallery to Storybook, migrate equivalent assertions before retiring old ones. Stories use the exact component rendered by the app, with the actual stylesheet and wrappers; no story-only markup or alternate theme rules. Connected tests still prove URL filters and deep links, account/tenant switching and isolation, action-time authorization, stale replay revalidation, submission outcomes, modal lifecycle and focus return, keyboard navigation, unsubscribe protocol behavior, and rendering provenance. Only delete an old browser assertion once replacement coverage proves the **same boundary**; a static story cannot prove a LiveView event reaches the right handler.

## Security and fixture isolation

Keep Storybook routes and fixture modules dev/test-only, and verify they are absent from production routes and Hex file lists. Don't assume that an `only: :dev` dependency automatically prevents a source directory or asset from being packaged. A DB-free story page may still run inside the demo application whose supervision tree starts Ecto; claim “no DB required” only after the chosen host boots without a DB. Prefer a small isolated host using the existing dependencies if necessary, not production code changes to skip application startup globally.

Use synthetic addresses on reserved example domains, fake opaque IDs and provider payloads generated without copied customer data. Never use actual reset/unsubscribe/auth tokens, production headers or logs in stories/screenshots. Mark malicious HTML/header payloads as security test content; prove escaping/sanitization through existing real rendering boundaries rather than allow a story to execute markup. Fixture visibility/permission flags describe UI states; they confer no authorization. Real host tests must continue to enforce tenant boundaries and authorization. Fixture tests should validate actual public/read-model rules, avoiding invented chronological prerequisites when provider events may arrive out of order.

Keep screenshot/trace artifacts free of secrets, and use existing retention/sanitization mechanisms before adding another store. The dev host should not make real mail/provider calls; observe requests and fail unexpected outbound network access in the story sweep. A demo evidence reset endpoint belongs to its existing run-owned isolation/token contract, never to a generic story runner.

## Adversarial review and stop line

| Recommendation | Strongest objection | Resolution / stop condition |
|---|---|---|
| Reuse existing harness and ratchets | Existing machinery is complicated and some checks are stale | Repair fresh-result ingestion and document ownership first; keep historical evidence instead of treating it as current. A second harness is justified only by a measured incompatible host requirement |
| Manifest-driven broad sweeps | Runtime grows with states × widths × themes and turns fast stories into slow e2e | Equivalence-class selection, cheap/expensive check separation, independent partitioning and a measured pilot; do not promise faster tests before measurement |
| Strong deterministic design checks | Overfitted rules reward conformity and suppress good typography/native controls | Check authored semantic roles and user outcomes with named exceptions; reserve composition/taste for the advisory rubric |
| Shrink-only baseline | Old violations can become permanent excuses | Fingerprint and assign each, remove fixed entries, review at milestone boundaries; never allow aggregate-count swaps to hide new defects |
| Small screenshot set | A rare visual failure may escape geometry checks | Select by JTBD/risk and record the untested scope; add a golden after a real escaped defect, not every permutation |
| Advisory judge | Model judgments are unstable, expensive and duplicative | Session-invoked, bounded passes, binary findings with evidence, pinned prompt/model, owner-labelled calibration and no CI API keys. Do not claim measured precision until labelled examples exist; leave it off when it adds no distinct signal |
| Keep connected tests | Duplicate-looking checks cost CI minutes | Retain boundary proof and remove only proven duplicate presentation assertions. No test deletion solely because a story looks similar |

The first delivery is useful once one end-to-end JTBD can be reviewed from primitive to real page with realistic fixtures, fresh deterministic checks and reproducible findings. Expand to the next section only after that path demonstrates useful signal and acceptable cost. This avoids building a universal UI-testing platform before improving an actual operator task.
