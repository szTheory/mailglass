# Stack Research — v2.2 CI Signal Integrity & Supply-Chain Hygiene

**Domain:** GitHub Actions CI/CD signal integrity + Elixir supply-chain auditing + Ecto test-harness correctness (maintenance milestone, no product stack)
**Researched:** 2026-07-28
**Confidence:** HIGH (GitHub Docs, HexDocs `ecto_sql` v3.14.0, `mix_audit` v2.1.5 README, and this repo's own workflow/source files were all read directly; the one area without an authoritative primary source — GitHub's native "neutral" conclusion — is called out as MEDIUM below)

## Headline finding

**Every tool this milestone needs is already in the repo.** `mix_audit ~> 2.1` (dev/test dep), `mix hex.audit` + `mix deps.audit` CI lanes, an OSV-staleness gate in `mailglass.publish.check.ex`, a 3-directory `dependabot.yml`, a `CI Green` fan-in job, a `Mailglass.CILanes` Elixir-side lane registry, and REST-API-based branch-protection read/write scripts are all shipped. v2.2 is **wiring and honesty work on existing machinery**, not a tool-adoption milestone. Treat any recommendation below that suggests a new dependency as a red flag against the "maintenance only, no CI topology rewrite" scope lock — none is needed, and none is proposed here.

### Supporting Libraries — none proposed

No new Hex package, GitHub Action, or CLI tool is proposed anywhere in this milestone. Every mechanism needed (advisory scanning, transitive-dep detection, branch-protection read/write, status-check aggregation, concurrency serialization, sandbox ownership) is either a language/platform primitive (Ecto's own `Sandbox` module, GitHub Actions' own `concurrency:` block, GitHub's own REST API) or an Elixir/mix construct already vendored in the repo.

### Development Tools (mechanism reference, not new adoption)

| Mechanism | Purpose | Configuration notes |
|------|---------|-------|
| `Ecto.Adapters.SQL.Sandbox.start_owner!/2` + `stop_owner/1` | Per-test connection ownership; `shared: true` widens visibility to every process | `stop_owner/1` is `GenServer.stop/1` under the hood — **synchronous**, blocks until the owner process is fully dead before `on_exit` returns. This rules out "on_exit didn't finish before the next test's setup" as the leak's mechanism for owners created via `start_owner!` itself. |
| `Ecto.Adapters.SQL.Sandbox.mode/2` (raw call, not via `start_owner!`) | Directly sets pool mode to `:auto`, `:manual`, or `{:shared, pid}` | **This is the actual leak surface.** `test/support/mailer_case.ex:158` and `:248` call `Sandbox.mode(repo, {:shared, self()})` **directly**, outside the `start_owner!`/`stop_owner` pair that `on_exit` cleans up. A raw `mode/2` call is not automatically reverted by anything; if the process passed as the shared owner (`self()`, the test process) is still registered as alive when the next `async: false` test calls `start_owner!(repo, shared: true)`, `mode/2` returns `{:error, :already_shared}` and `start_owner!` crashes on the `{:badmatch, :already_shared}` this seed is chasing. **This is HexDocs-confirmed mechanics, not a guess:** the `ecto_sql` v3.14.0 docs state `mode/2` may return `:already_shared` specifically "when another process set the ownership mode to `{:shared, _}` and is still alive." |
| `:async, false` on the whole module (vs per-tag `shared: not async?`) | Determinism | HexDocs is explicit: "Any test using `:shared` mode must be in a test module marked `async: false`." The 9 mode-switching files SEED-007 lists already do this individually — the leak is cross-file, from processes outliving their test (the `{:shared, self()}` calls above), not from those 9 files themselves (already ruled out). |
| `setup_all` + Sandbox checkout | Anti-pattern, do not introduce | Not currently used for sandbox checkout in this repo (confirmed by grep) — keep it that way. HexDocs/community consensus: checking out a sandbox connection in `setup_all` fails because the checked-out connection is scoped to the *setup_all process*, not the individual *test process* that later runs; `Task`/spawned-process access requires `allow/3`, and `setup_all`-scoped connections can't `allow` a process ExUnit hasn't started yet. If Phase 142 work considers hoisting any per-file fixture setup to `setup_all` for speed, this is the reason not to. |
| Multi-repo suites (core `Mailglass.TestRepo`, admin uses the same repo via `mailglass_admin/test/test_helper.exs`, inbound has its **own** `MailglassInbound.TestRepo`) | Each `Ecto.Repo` sandbox is independently moded | The `{:badmatch, :already_shared}` failures are scoped to the **core** suite's single `Mailglass.TestRepo` (confirmed: SEED-007's evidence table and ruled-out list never implicate the admin or inbound repos). No cross-repo interaction is implicated — do not spend phase 142 time auditing `MailglassInbound.TestRepo`, whose suite was independently root-caused and fixed for a *different* flake class (shared-mode/async collision, not a leak) in the v1.15 milestone (`CICD-RELEASE-HARDENING.md` §3). |

## Alternatives Considered

| Recommended | Alternative | When to use the alternative instead |
|-------------|-------------|-------------------------|
| Keep `mix_audit` + `mix hex.audit` + repo's own OSV staleness check | `sobelow` | Sobelow is a Phoenix-*app* security scanner (router pipelines, CSRF, secrets-in-config). mailglass ships libraries, not a deployed app — the prior CI/CD research (`CICD-RELEASE-HARDENING.md` §4.1) already correctly ruled this out. Revisit only if a shipped, deployed app surface appears (it hasn't). |
| Keep `mix_audit` + `mix hex.audit`, both already Elixir-native | A commercial/hosted SCA tool (Snyk, Sonatype, GitHub Advanced Security "Dependency review" beyond what's free) | Only worth it if the project needed org-wide policy enforcement across many repos or SBOM export requirements — neither applies to a 3-package solo-maintained OSS lib. Free-tier GitHub Dependabot alerts (already implicitly on for a public repo) plus the two mix-native tools already cover the detection surface. |
| Hand-rolled `if: always()` + explicit `needs.*.result` check for "must not report SUCCESS while skipping" (TRUTH-02) | A genuine GitHub Checks API "neutral" conclusion via a custom GitHub App / `actions/github-script` write-permission call | GitHub Actions jobs natively report only `success`/`failure`/`cancelled`/`skipped` — there is no first-class YAML syntax to set a job's own conclusion to `neutral`. Posting a true `neutral` Check Run conclusion requires calling the Checks API directly with `checks:write` permission (effectively acting as a GitHub App), which is real net-new complexity for one workflow. **MEDIUM confidence on this being impossible via plain job syntax** — GitHub's own community-discussion evidence (#9875, #82744) confirms no native `neutral`-by-exit-code exists in the current Actions runner; a repo already using the `if: always()` + explicit-failure-check idiom (see `ci_green`, `publish-hex.yml`'s `gate-ci-green`) should reuse that same idiom for TRUTH-02: make the job **fail** (`exit 1`) with a message that reads "cannot verify — PAT missing" when it can't run its check, rather than silently succeeding. This is the pragmatic native-job-status equivalent of "neutral," and it is already this repo's own established pattern. |
| Concurrency group keyed to a **constant string** (or `github.workflow`), not `github.ref` | Per-ref concurrency group (current state) | Per-ref grouping is correct for `ci.yml`/`advisory-matrix.yml` (PRs on different branches should run in parallel) but is the direct cause of TRUTH-08 for `publish-hex.yml`: `publish-core`'s `if:` condition fires unconditionally on `github.event_name == 'release'` regardless of which sibling package's tag triggered the event, and release-please's linked-versions plugin creates **two separate GitHub Releases** (mailglass + mailglass_admin) on **two different tags/refs** for one logical release. Two different refs under a ref-scoped `group:` never serialize against each other — exactly the observed "two publish-hex runs fire and race on publish-core." Use a fixed-string group for this one workflow specifically. |
| Documented triage-cadence runbook for transitive advisories (process, zero new tooling) | A custom `mix deps.audit`-to-GitHub-Issue automation bot | Over-engineering for a 3-package solo-maintained repo. The gap is not detection (mix_audit already detects transitive advisories in CI, just as advisory-only) nor filing infra — it's that nobody reads the advisory-only lane's output on a cadence, and Dependabot's known Hex-ecosystem limitation on transitive PRs (see Pitfalls) means the fallback path (`mix deps.update <transitive_pkg>` or a manual `mix.lock` edit, as was actually done for `hpax`/`cowboy`/`cowlib`) needs to be a written, scheduled human step — not a new bot. |

## What NOT to Use / Add

| Avoid | Why | Use Instead |
|-------|-----|-------------|
| A second Elixir security-audit tool (e.g., adding both `mix_audit` *and* a separate OSV-Scanner binary/Action) | `mix_audit` already reads the OSV-backed `elixir-security-advisories` data; the repo's own `publish.check` already calls the OSV API directly for allowlist staleness. A third tool duplicates coverage without closing any actual gap — the gap is *gating*, not *detection*. | Wire the two existing lanes (`hex_audit`, `deps_audit_advisory`) into `ci_green.needs` per VULN-03. |
| `re-actors/alls-green` (or any external fan-in Action) to replace the hand-rolled `ci_green` job | The repo already has a working, auditable, dependency-free aggregator. Swapping it is scope creep against "no CI topology rewrite" and adds a third-party Action to the trust boundary for zero behavior change. | Keep the existing `ci_green` shell logic; only its `needs:` list changes. |
| A custom GitHub App / Checks API integration to produce a literal "neutral" status | Real engineering lift (App registration, `checks:write` token, webhook handling) to solve a problem the repo already has an idiom for (`exit 1` with a clear message via `if: always()` + explicit result check). Disproportionate to a maintenance milestone. | Reuse the `ci_green`/`gate-ci-green` fail-loud idiom for `branch-protection-drift.yml` and the `ci.yml` "Branch Protection Advisory" job (TRUTH-02). |
| GraphQL `requiredStatusCheckContexts` / `RequiredStatusCheckInput` (the richer GraphQL-only branch-protection shape that can pin a required check to a specific GitHub App) | Nothing in this milestone's scope needs App-scoped required-check disambiguation (mailglass has exactly one CI-producing App: GitHub Actions itself). Adding GraphQL calls alongside the existing REST-only `verify-branch-protection.sh`/`setup_branch_protection.sh` pair is unjustified complexity. | Keep the REST `GET/PUT .../branches/{branch}/protection` pair already in use; it already normalizes both the legacy `contexts` array and newer `checks[].context` shape (see `verify-branch-protection.sh:42`). |
| Bumping `mix_audit`, `erlef/setup-beam`, `actions/checkout`, `actions/cache`, or `actions/github-script` pins as part of this milestone | All are already current (`mix_audit ~> 2.1` resolves 2.1.5; `actions/checkout@...v7.0.0`; `actions/cache@...v5.0.5`; `erlef/setup-beam@...v1.24.0`; `actions/github-script@...v9.0.0`) and bumping them is unrelated to signal integrity or supply-chain hygiene — it's routine Dependabot territory, already covered by the `github-actions` ecosystem entry in `dependabot.yml`. | Let Dependabot handle routine Action version bumps; don't hand-touch pins in this milestone. |
| Retrying/seed-pinning to paper over the sandbox leak (`--seed 0`-style masking) | SEED-007 explicitly warns against "fixing" this by making tests `async: false` or otherwise hiding the interaction — that manufactures green without explaining the mechanism, the same "signal that lies" failure mode this whole milestone exists to kill. | Root-cause the two raw `Sandbox.mode(repo, {:shared, self()})` call sites in `mailer_case.ex` (HARNESS-01) and prove the fix with repeated full-suite runs, not a single deterministic seed. |

## Stack Patterns by Variant

**If promoting a currently-advisory CI lane to required (VULN-03, HARNESS-04):**
- Edit exactly three places in lockstep: `ci.yml` `ci_green.needs`, `test/support/ci_lanes.ex` `@required_lanes`, and `publish-hex.yml`'s `REQUIRED_LANES` JS array — the existing `GATE-03` meta-test (`test/scripts/required_checks_test.exs`) already asserts these three stay set-equal, so a partial edit fails CI loudly rather than silently drifting (this is the exact class of bug that caused the 24-day branch-protection outage).
- Do **not** touch `scripts/setup_branch_protection.sh`'s `REQUIRED_CHECKS` array — it only ever names the two top-level contexts (`CI Green`, `Guard Release Trigger`); leaf-lane promotion happens inside `ci_green`'s `needs:`, one level below what branch protection itself sees. This is precisely the aggregator-gate benefit the prior milestone's research locked in: lane changes never touch branch protection again.

**If fixing a "reports SUCCESS while skipping" lane (TRUTH-02):**
- Apply the same `if: always()` + explicit non-success check idiom already used in `ci_green` (`ci.yml:1129`) and `gate-ci-green` (`publish-hex.yml:190`) — this repo has a working, precedented pattern for "a job that must not lie about whether it actually ran its check." Reuse it verbatim rather than inventing a second mechanism.
- Two known instances need this: the scheduled `reassert-protection` job in `branch-protection-drift.yml` (currently no-ops to success when `BRANCH_PROTECTION_PAT` is unset) and the PR-time "Branch Protection Advisory" job in `ci.yml` (same `pat_present` guard, same silent-success shape). Fix both; they are two separate files/jobs with the identical bug pattern, not one bug in one place.

**If serializing the publish fan-out (TRUTH-08):**
- Change `publish-hex.yml`'s `concurrency.group` from `publish-hex-${{ github.ref }}` to a fixed string (e.g. `publish-hex`) or `${{ github.workflow }}` alone, keeping `cancel-in-progress: false` (a queued-not-cancelled publish run must never be dropped mid-flight — GitHub's own concurrency docs confirm `cancel-in-progress: false` still only allows one *running* + one *pending* run per group, which is exactly the desired "queue, don't drop" semantics here).
- This is a one-line change with a clear causal chain: release-please's linked-versions plugin creates two GitHub Releases (mailglass + mailglass_admin) on two different tags for one logical release; `publish-core`'s `if:` fires on `github.event_name == 'release'` unconditionally (it doesn't check which tag), so both resulting `publish-hex.yml` runs attempt `publish-core`; a ref-scoped concurrency group lets them run in parallel instead of serializing, and the existing "skip if already on Hex" idempotency check (`publish-hex.yml:324-331`) has a TOCTOU window too narrow to close that race — only serialization does.

**If documenting the transitive-dependency triage cadence (VULN-04):**
- Do not build tooling. Write the runbook: (1) the `Deps Audit Advisory` lane's CI output is the detection surface and must be read on a cadence (weekly, or whenever `hex_audit`/`deps_audit_advisory` goes red on `main`/cron) — not only reacted to via Dependabot PRs, because Dependabot will not reliably open one for a transitive finding; (2) the remedy when Dependabot can't help is `mix deps.update <transitive_package_name>` (bumps just that lockfile entry, not the whole tree) or a direct `mix.lock` hash edit, exactly as was done for `hpax`/`cowboy`/`cowlib`; (3) once `hex_audit`/`deps_audit_advisory` are gating (VULN-03), this cadence becomes forcing-function-backed rather than best-effort — a new HIGH blocks merge and the runbook is what a maintainer follows to clear it, rather than a nice-to-have.
