# Phase 100 - UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | Phoenix LiveView HEEx with Tailwind v4 standalone binary and vendored daisyUI |
| Preset | not applicable - this is not a React/shadcn project |
| Component library | Project Phoenix components plus daisyUI utility classes |
| Icon library | Vendored Heroicons inline plugin via `MailglassAdmin.Components.icon/1` |
| Font | Inter for UI, Inter Tight for headings, IBM Plex Mono for code/chips |

Contract:

- Use existing semantic utilities from `mailglass_admin/assets/css/app.css`: `text-label`, `text-body`, `text-heading`, `text-display`, `gap-sm/md/lg`, `rounded-box`, `bg-base-*`, `text-*`, `border-*`, `btn`, `badge`, and `motion-*`.
- Do not add shadcn, external component registries, Node tooling, raw hex colors in HEEx, custom client JS hooks, glassmorphism, bevels, or new routes.
- Treat Phase 97 Preview components as settled. Compose `Preview.Sidebar`, `DeviceFrame`, `Tabs`, `AssignsForm`, and `orientation_strip`; change component internals only where required for mobile reachability, dark-mode inheritance, group hooks, or 44px touch targets.
- Rebuild and commit `mailglass_admin/priv/static/app.css` after class changes; `mix verify.preview` must leave `priv/static/` clean.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, tight inline chips, badge icon spacing |
| sm | 8px | Compact control groups, sidebar list gaps, tab metadata gaps |
| md | 16px | Default card internals, form blocks, preview header groups |
| lg | 24px | Section spacing, main/aside group gaps, desktop card padding |
| xl | 32px | Large page group separation when needed |
| 2xl | 48px | Major page breaks only |
| 3xl | 64px | Page-level breathing room only |

Exceptions:

- `min-h-11` is required for interactive controls, sidebar summaries, scenario links, CTAs, header theme/frame controls, assigns actions, and mobile navigation controls to satisfy the 44px touch target floor.
- Preview iframe dimensions are content simulation values, not layout spacing tokens. Keep existing supported device widths (`375`, `768`, `1024`) unless implementation is only plumbing URL state.
- Bounded read-only preview panes may keep fixed content heights such as `h-[600px]`; do not introduce arbitrary spacing or padding values for page/group layout.
- The desktop sidebar width may stay `w-80`; it is an established navigation rail width, not a spacing scale value.

## Typography

Use exactly these four sizes and two weights on the Preview surface.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 12px | 700 | 1.5 |
| Body | 14px | 400 | 1.5 |
| Heading | 20px | 700 | 1.2 |
| Display | 28px | 700 | 1.2 |

Contract:

- Use `text-heading font-bold` for the selected scenario heading and start/empty/error card headings.
- Use `text-body` for form labels, sidebar summaries, scenario links, legends, helper text, and button labels.
- Use `text-label` with `.mono` or `font-mono` for code, module/function names, raw headers, raw envelope text, and assign type labels.
- Do not add `text-lg`, `text-xl`, `text-2xl`, arbitrary tracking, or weights other than `font-normal`/`font-bold`.
- Preserve exactly one page-level `h1` in the Preview surface. If the sidebar keeps "Mailers" as an `h1`, scenario/start/empty headings must use `h2`/`h3`; otherwise promote the visible page title to the single `h1` and demote the sidebar label.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `bg-base-100` / `--mg-color-background` (`#F8FBFD` light, `#0D1B2A` dark) | Page background, main Preview canvas, default preview pane surrounds |
| Secondary (30%) | `bg-base-200` / `--mg-color-surface-raised` (`#FFFFFF` light, `#152538` dark) | Sidebar rail, start/empty/error cards, assigns form group, tab/read-only panes |
| Accent (10%) | `text-primary`, `border-primary`, `btn-primary`, `focus-visible:ring-primary` / `--mg-color-accent` (`#277B96` light, `#A6EAF2` dark) | Primary CTA, active scenario border, active tab underline, focus rings, selected device button |
| Destructive | `text-error`, `border-error`, `badge-error`, `alert-error` / `--mg-color-error-*` | Render-error state only; no destructive action is introduced |

Accent reserved for: `Preview the first Mailable` CTA, active scenario left border, active tab underline, selected device button, focus rings, check icons in the no-Mailables setup list, and no other structural border/card fill.

Dark-mode contract:

- `?theme=dark|light` is the admin chrome theme. It must re-skin root/page chrome, sidebar, cards, form controls, tab strip, and preview pane surrounds.
- The previewed Message/frame theme is independent from admin chrome. It must use a distinct assign/param name if it is URL-backed and must affect only the preview frame/pane, not the page background, sidebar, shell, form controls, or route shell.
- Root layout and inner Preview wrapper must not fight each other. Explicit `?theme=dark` renders `mailglass-dark`; explicit `?theme=light` renders `mailglass-light`; no explicit param must not unconditionally force light over daisyUI `prefersdark: true`.
- Child Preview components must inherit page-level admin chrome unless they are rendering the independent previewed-message/frame theme.

## Visual Hierarchy And Interactions

Primary focal point:

- On `/dev/mail` with Mailables present, the start card is the focal point and exposes one keyboard-focusable primary CTA: `Preview the first Mailable`.
- On `/dev/mail` with no Mailables, the no-Mailables setup card is the focal point and exposes one real focusable setup/help action.
- On a selected scenario, the focal path is header controls -> assigns form -> tab strip -> preview pane. The sidebar is navigation, not the primary content.

Layout contract:

- Use Preview page rhythm from Phases 98/99: outer padding `px-md py-lg` and `md:px-lg md:py-xl`, inter-group `gap-lg`, in-group `gap-md/gap-sm`, flat surfaces `bg-base-200 border border-base-300 rounded-box`, semantic tokens only.
- At `>=768px`, keep a persistent left Mailables rail using the existing `Preview.Sidebar` hierarchy and a main content column.
- At 390px, Mailables/scenario navigation must be reachable. Render a mobile-first disclosure or inline panel above the start/empty/show content, reusing `Preview.Sidebar` and preserving native `<details>/<summary>` mailable/scenario semantics.
- Do not replace the Sidebar with a flat list or custom JavaScript accordion. Native `<details>/<summary>` remains the mailable to scenario hierarchy.
- Add stable group hooks with kebab-case `data-testid`s at minimum: `preview-shell`, `preview-mobile-mailables`, `preview-start`, `preview-empty-mailables`, `preview-header-controls`, `preview-assigns-form`, `preview-tab-strip`, and `preview-pane`.
- Do not put cards inside cards. The start card, no-Mailables card, assigns form group, and preview pane are sibling groups inside the main flow.

Interaction contracts:

- Header controls include `DeviceFrame` and a distinct previewed-message/frame theme toggle when that state is exposed. Do not use the admin chrome toggle to change the previewed Message frame.
- Admin chrome theme changes must stay URL-driven through `?theme=` and `handle_params/3`/`push_patch/2`; no localStorage theme hook or custom client JS hook.
- `AssignsForm` action buttons use `min-h-11`; if `btn-sm` suppresses the 44px floor in compiled CSS, remove `btn-sm`.
- Text, Raw, and Headers panes are read-only inspection surfaces. HTML uses the sandboxed iframe and must not bleed email CSS into admin chrome.
- Explicit loading UI stays out of scope unless Phase 100 introduces async assigns. Synchronous discovery/rendering should not get decorative skeletons in this phase.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | `Preview the first Mailable` |
| Start state heading | `Render a real Message before you send it` |
| Start state body | `Pick a Mailable from the sidebar to render it through the same pipeline your production sends use.` |
| Empty state heading | `No Mailables discovered` |
| Empty state body | `Preview scans loaded modules that use Mailglass.Mailable. Nothing was found yet.` |
| Empty state setup action | `Read preview setup` |
| Error state | `preview_props/0 raised an error`; body: `Fix the error in [module] and save the file to reload.` |
| Assigns primary action | `Render preview` |
| Assigns secondary action | `Reset assigns` |
| Mobile navigation trigger | `Mailables` |
| Destructive confirmation | No destructive action in Phase 100 |

Copy rules:

- Use domain nouns exactly: Message, Mailable, Mailables, preview_props/0, assigns.
- Do not use `Oops`, `Whoops`, `Uh oh`, `Something went wrong`, generic `No data found`, standalone `Email`, or generic `mailer` when `Mailable` is meant.
- Preview is a developer surface, so render errors name the exact module/function that raised and give the next recovery step.

## Accessibility And Responsive Contract

| Area | Contract |
|------|----------|
| Heading hierarchy | Keep exactly one page `h1`. Start, empty, error, and scenario headings use token type and valid heading order. |
| Focus | Interactive controls use visible semantic focus rings via `focus-visible:ring-2 focus-visible:ring-primary` or outline equivalent. |
| Touch targets | Buttons, sidebar summaries, scenario links, device controls, theme/frame controls, assigns actions, and mobile navigation triggers are at least 44px tall (`min-h-11`). |
| ARIA/state | Device buttons keep `aria-pressed`; tabs keep `role="tablist"`, `role="tab"`, `aria-selected`, `aria-controls`, and `role="tabpanel"`; active scenario remains visually and programmatically discernible. |
| Native disclosure | Sidebar mailable groups remain native `<details>/<summary>` controls in desktop and mobile placements. |
| Viewports | Validate 390, 768, and 1440 widths in light and dark. At 390, Mailables navigation is reachable before the main Preview workflow. |
| Contrast | Text and non-text boundaries meet WCAG AA in both themes using existing `--mg-*` and daisyUI semantic tokens. |
| Theme split | Browser proof must show admin chrome dark mode and previewed-message/frame dark state are independently controllable and do not leak into each other. |
| PII | Preview must not call `Mailglass.Outbound.deliver/2` and must not add telemetry or production send behavior. |

| `data-testid="preview-tab-strip"` | Assert tab ARIA and active state. |

- `/dev/mail?theme=dark` and `/dev/mail?theme=light` on the index route.

- Empty/no-Mailables route through the existing synthetic test route.
- `mailglass_admin/scripts/ui-audit.sh` Preview dark cells using `?theme=dark` with visibly dark chrome.
