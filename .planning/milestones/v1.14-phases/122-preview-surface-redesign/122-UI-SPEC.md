# Phase 122 — UI Design Contract
## Preview surface redesign

> Visual and interaction contract for the Phase 122 Preview surface redesign
> (the v1.14 #4 / **last** surface; 119 → 120 → 121 → **122**).
> Generated by gsd-ui-researcher. Verified by gsd-ui-checker.
>
> Source of truth for the design *system*: `brandbook/brand-book.md`,
> `brandbook/copy/microcopy.md`, and `mailglass_admin/assets/css/app.css`. This spec does NOT
> reinvent that system — it applies it precisely to the scoped Preview-branch changes (PREV-01),
> **mirroring the shipped Phase 120/121 contracts (`120-UI-SPEC.md` / `121-UI-SPEC.md`) verbatim**
> for tokens / typography / color / motion / a11y, and changing only the **two theme toggles, the
> empty-mailables onboarding copy, the error-card copy, a dead-attr removal, and shell-chrome token
> normalization** — PLUS the dual-theme-toggle a11y fixes (adopt the canonical `theme_picker`,
> `aria-pressed` + `aria-live` on the backdrop button).
>
> **This is an ALIGNMENT-AND-POLISH pass of an existing, already-clean surface — NOT a rebuild
> (D-01).** Preview is the CLEANEST of the four surfaces going in: its four-branch render `cond`
> already mirrors the cleaned 120/121 shape, and the orientation strip is **already
> empty-pane-only** (`preview_live.ex:362`, the sole `orientation_strip` call, inside the
> `@mailables == []` branch). The DEFECT-REGISTER records Preview as "no net-new headline defect."
> **Preview is a structurally DIFFERENT beast** — a dev-only email-preview explorer (sidebar of
> auto-discovered Mailables → scenarios; main pane with logo+"PREVIEW" eyebrow + device-frame + two
> theme toggles + tabs + assigns form). It has **no records table, no filters, no tenant scope, no
> replay, no PII, no pagination** — so the Deliveries/Inbound no-data/no-match split, `data_state`
> primitive, replay modal, and PII-reveal machinery **DO NOT port** (they would ship as dead,
> unreachable UI — D-08). Cross-surface coherence is achieved through **shared chrome vocabulary**
> (spacing scale, eyebrow+logo pattern, motion tokens, brand voice, single-h1 hierarchy), **not
> shared structure**. The locked decisions D-01..D-13 in `122-CONTEXT.md` are binding constraints,
> not open questions. **THE LOAD-BEARING INVARIANT (D-05): the two-theme independence carry-through
> (`return_to` + `?frame=dark`) must not break — `theme_picker`'s `set_theme` event MUST route
> through Preview's `preview_theme_path/2`, never the shell's `set_theme_path/2`.** This is the
> single highest-risk item in the phase.

## Color

Inherited verbatim from `121-UI-SPEC.md` / `120-UI-SPEC.md` / `119-UI-SPEC.md`. Admin chrome
light/dark via two daisyUI theme blocks (`mailglass-light` / `mailglass-dark`) keyed on `[data-theme]`;
system follows `prefers-color-scheme`. Use ONLY semantic token class names — never raw hex, never raw
palette classes (`text-gray-500`). **No color token changes in this phase. D-THEME-PARITY guardrail:**
admin-chrome light/dark/system parity is only-move-forward — re-verify, never regress.

> **The previewed-email backdrop theme is a SEPARATE, independent axis** from the admin chrome
> theme (the load-bearing distinction this whole phase protects — D-05). `preview_frame_dark_chrome`
> governs only the **email-rendering iframe backdrop** (`data-preview-frame-theme` on `preview-pane`,
> `tabs.ex:98-104`); the admin `theme_picker` governs the **chrome** (`data-theme` root,
> `preview_live.ex:245`). They are deliberately given **structurally distinct control shapes**
> (segmented 3-way picker vs single binary button) so they are never confused — WCAG 1.4.1 satisfied
> by form-factor, not icon+word alone.

| Role | Light (brand) | Dark (brand) | Semantic class | Usage in the Preview surface (admin chrome) |
|------|--------------|--------------|----------------|---------------------------------------------|
| Dominant (60%) | Paper `#F8FBFD` | Ink `#0D1B2A` | `bg-base-100` | Main preview pane, device-frame chrome background, onboarding pane bg, start-pane bg |
| Secondary (30%) | White / Mist | Ink-raised `#152538` | `bg-base-200` | Sidebar surface, header bar, tab strip, error-card surface, onboarding checklist card |
| Border | Mist-edge `#C7DCE5` | Ink-edge `#315069` | `border-base-300` | Header bottom border, card borders, tab-strip divider, device-frame border, error `<pre>` border |
| Primary text | Ink `#0D1B2A` | Mist `#EAF6FB` | `text-base-content` | Headings, eyebrow, scenario names, onboarding title, error message text |
| Secondary text | Slate `#5C6B7A` | Mist-soft `#B8CAD4` | `text-secondary` | Eyebrow muted state, control captions, checklist body, helper copy, tips, denied copy |
| Accent (10%) | Glass `#277B96` | Ice `#A6EAF2` | `text-primary` / `bg-primary` / `border-primary` | See reserved list below |

### Accent reserved for (the 10% rule — do NOT use outside this list):
1. **Selected Mailable / scenario** in the sidebar: the existing active-entry treatment
   (`border-l`/`bg`/`text-primary` per `sidebar.ex` render paths) — verify, do not restyle.
2. **Active tab** indicator (HTML/Text/Raw/Headers `role=tablist`, `tabs.ex`): `text-primary` /

3. **Active device-width segment** (`device_frame.ex` `aria-pressed` segmented control) — accent +

4. **`theme_picker` selected segment** (the adopted admin-chrome control): accent fill on the

   `:checked` radio state (never color-alone).
5. **Focus ring:** `mg-focus-ring` / `mg-focus-ring-within` / `mg-focus-ring-inset` (`ring-primary`)
   on EVERY interactive control — `theme_picker` segments (`mg-focus-ring-within`, existing), the
   Email-backdrop button (`mg-focus-ring`), tabs, device-width segments, sidebar entries, assigns

6. Onboarding **`mix mailglass.gen.mailable`** generator command rendered in a `mono` `<code>`

### Semantic status colors (status only — never accent):

## Interaction Contracts

The Preview surface resolves to exactly **four reachable states** via the existing four-branch render
`cond` (`preview_live.ex:283-440`). The discriminator is the **existing** render logic, not a new
flag (D-01, D-08). **Do NOT import the no-data/no-match split, `data_state`, replay modal, or
PII-reveal machinery** — Preview has no records / filters / tenant-scope / async / auth for them to
act on; they would ship as dead, unreachable UI (D-01, D-08).

- **render-error** = a Mailable raised during `preview_props/0` or render-time template evaluation;
  struct-matched `TemplateError` + rescue routes here (`preview_live.ex:284-301`, `:120-132`,
  `:720-749`). Invalid assigns-form input folds back through `rerender/1` into this same arm.
- **populated-scenario** = a Mailable + scenario selected and rendered successfully
  (`preview_live.ex:302-360`): header + two theme toggles + device-frame + tabs + assigns form.
- **empty-mailables** = `@mailables == []` (`preview_live.ex:361-402`): the onboarding pane +
  **the sole orientation strip (`:362`, already empty-pane-only — DO NOT MOVE IT — D-11a)**.
- **start / none-selected** = Mailables exist but none selected (`preview_live.ex:403-439`):
  the "pick a Mailable" start pane.

### PREV-01a — Dual-theme toggles: adopt `theme_picker` for chrome, harden the binary backdrop button (D-02, D-03, D-04)

**THE highest-judgment area of the phase.** The two controls govern two independent axes and must
remain structurally distinct, separately labeled, and individually correct.

**Admin-chrome theme — adopt the canonical `theme_picker` (D-02):**
1. **Replace** the bespoke binary sun/moon ghost button (`preview_live.ex:310-328`, which silently
   drops `:system` and diverges from the other three surfaces) with
   `<Components.theme_picker selected={@admin_chrome_theme} event={…} />` — the shipped, a11y-audited,
   **tri-state light/dark/system** native-radio `<fieldset>` + `<legend class="sr-only">Theme</legend>`,
   44×44 segments, `mg-focus-ring-within` (`components.ex:326-360`).
2. Precede it with a small **visible group caption "App theme"** so the relationship of the control
   to what it governs (the chrome) is explicit and distinguished from the backdrop control.
3. **THE LOAD-BEARING INVARIANT (D-05 — single highest-risk item; call out in the plan):** the
   `theme_picker`'s `set_theme` event MUST route through Preview's existing **`preview_theme_path/2`**
   (`preview_live.ex:590-598`, which calls `put_frame_query` to smuggle `frame=dark` through
   `return_to`), **NOT** the operator shell's `set_theme_path/2` (`shell.ex:102-117`), which has NO
   frame handling and would silently reset the email backdrop on every chrome-theme flip. The
   `admin_chrome_theme` persists via a full controller redirect through `/theme/<t>` that remounts the
   LiveView and would drop the in-memory `preview_frame_dark_chrome` — the `frame=dark` carry-through
   (`put_frame_query` → restored by `frame_from_params` on remount, `:626-638`) is what keeps the
   backdrop alive. `flows.spec.js:454-458` locks this end-to-end and must stay green against the swap.

**Email-backdrop theme — keep the binary button, make it a correct toggle (D-03):**
4. `preview_frame_dark_chrome` is genuinely binary (the email backdrop has no "system"). Keep the
   `<button>` with `phx-click="toggle_preview_frame_theme"` and
   `data-testid="preview-frame-theme-toggle"` **verbatim** (the `flows.spec.js:454-458` invariant)
   and the moon/sun icon (`preview_live.ex:329-345`).
5. **Add `aria-pressed={@preview_frame_dark_chrome}`** for the missing state semantic.
6. Pair the icon with an **always-visible "Email backdrop" text label** (never icon/color-alone), keep
   the state-dependent `aria-label` ("Switch the email backdrop to dark" / "…to light"), `min-h-11`,
   `mg-focus-ring`.

**Announce the remote-pane change (D-04):**
7. The backdrop toggle changes a visual region the user is NOT focused on, so `aria-pressed` (the
   button's own state) is insufficient. Add a NEW **`aria-live="polite" role="status" sr-only`**
   region announcing **"Email backdrop: dark" / "Email backdrop: light"** on toggle (the 121 D-11
   precedent). Never the backdrop color alone (WCAG 1.4.1). No new keyframes; reuse existing
   focus-ring/motion tokens.

**Placement (Claude's discretion — least-surprise):** stacked vs inline grouping of the "App theme"
`theme_picker` + "Email backdrop" button (and caption position) within the header — pick the
least-surprise layout that keeps the two controls visually distinct and reads cleanly 320→wide; reuse
existing spacing tokens. Exact `aria-live` region placement within the header subtree is discretion;
mirror 121 D-11.

### PREV-01b — Empty-mailables onboarding: generator as PRIMARY next step (D-09)

**Contract:**
1. Render the onboarding pane (`preview_live.ex:361-402`) with the **brandbook-canonical empty-state
   line verbatim** as headline + lead (voice_test greps it): **"No mailables discovered yet. Define
   one with `mix mailglass.gen.mailable` and it will appear here, ready to preview."** Surface the
   generator command as the PRIMARY next action (the highest-DX-leverage first-run moment — a great
   dev empty state names the exact next step).
2. **Demote** the current module-marker troubleshooting (the `use Mailglass.Mailable`
   compiled-and-loaded check + the explicit `mailables:` router-list escape) to a **secondary
   checklist** — those are recovery paths for "a Mailable exists but isn't found," not the first-run
   primary path.
3. Keep the "Read preview setup" HexDocs link.
4. The **orientation strip (`:362`) renders here and ONLY here** (already empty-pane-only — D-11a). It
   sits as a quiet teach-block; its copy is byte-frozen (`shell.ex:427-436` `:preview` copy) — only
   the render *condition* may change, and it is already correct. **DO NOT MOVE IT.**
5. **Overflow:** verify the long router-snippet `<code>` block wraps/scrolls cleanly at 320px
   (`overflow-auto` / `whitespace-pre-wrap`), never forcing horizontal page overflow.

### PREV-01c — Error card: adapt brandbook VOICE, KEEP the inline exception `<pre>` (D-10)

**Contract — this is a dev-only DX tool; do NOT send the developer to logs:**
1. Generalize the too-narrow headline **"preview_props/0 raised an error"** → **"This Mailable raised
   while rendering"** (render-time template raises land here too, not just `preview_props/0`).
2. Name BOTH the **Mailable** (`inspect(@current_mailable)`) and the **scenario**
   (`@current_scenario`) as load-bearing debugging context.
3. Use a recovery-oriented lead in the brandbook voice, e.g. **"Fix it in {Mailable} and save to
   reload — the full error is below."** (exact wording is discretion within the brandbook voice).
4. **KEEP the inline scrollable exception `<pre>`** (`overflow-auto max-h-80 whitespace-pre-wrap`,
   contained at 320px). The brandbook recipient/operator-facing Error line ("…in your logs.") is
   WRONG for a dev preview tool — the error is right there and inline display is the correct,
   convergent DX (Next 15.2 owner-stacks / Vite overlay). Do NOT redirect to logs.
5. **"Oops" stays banned** (none present). **Match the struct, never the message string** (already
   correct, `:738-740` — do not regress).
6. **Focus / announce on the error transition (D-08a):** when a template raises and the error card
   appears, move focus to it (or announce via `role="status"`/`aria-live="polite"`) so the developer
   isn't left re-scanning — mirror the D-04 live-region pattern (focus-move vs live-region announce,
   or both, is discretion). Apply `motion-reveal` (existing token) to error-card and onboarding-pane
   entry; honor the existing reduced-motion neutralizer; no new keyframes.

### PREV-01d — Dead `dark_chrome` attr removal (D-06)

Remove the dead `dark_chrome` attr from `preview/sidebar.ex` (declared at `:30` and `:72`, threaded
through `sidebar/1` → `mailable_entry/1` at `:56`, but **never read** in any `mailable_entry` clause
`:78-125` or `mailable_label/1`; `preview_live.ex` never passes it). Delete both declarations and the
pass-throughs so a future maintainer can't wire it and collide with the real
`admin_chrome_theme`/`preview_frame_dark_chrome` split. Pure dead-code removal — no visual change.

### PREV-01e — Shell-chrome token normalization, NOT operator structure (D-07)

Preview already shares the operator's spacing scale (`px-md py-lg …`), the logo+"PREVIEW" eyebrow
pattern (`:248-251`), single-`h1` hierarchy, and `motion-reveal`/`motion-tab-swap` on existing tokens.
This is **normalization**: verify the eyebrow/header border + padding tokens match the operator shell
exactly and fix any drift; apply brandbook noun discipline (**Mailable** locked, `brand-book.md:69`;
keep the plural collection label "Mailables"); reconcile running prose toward the brandbook copy-table
strings. **Do NOT** adopt the operator left-rail nav — Preview's sidebar-of-Mailables IS its content
navigation, a different job (cf. Storybook component tree / react-email file tree). **Leave the tabs
strip, device-frame segmented control, and assigns form as-is** — already APG-correct,
controls-above-canvas, matching Mailpit/react-email/Storybook conventions.

### Layout / responsive behavior at breakpoints (inherit, least-surprise)

- **Sidebar + main pane:** the sidebar-of-Mailables is the content navigation; the main pane holds the
  header + device-frame + tabs + assigns form. Preserve the existing grid/flex template — make NO

  rewrite).
- The device-frame segmented widths, the tabs strip, and the assigns form are pre-built and correct —
  verify against the matrix, do not rebuild.
