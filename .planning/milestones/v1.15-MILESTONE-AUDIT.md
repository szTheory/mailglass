## Intent Audit (SHIP-03)

**"CI-the-body" method validation:** Each of the 7 phases (125–131) was pushed via a feature branch with green CI required before merge. The ceremony (Phase 131) was a confirmation, not a discovery:

- The two Wave-0 landmines (D-05 inbound `docs_contract_test` redoing the expected core pin derivation, and D-11 the `~>`-aware post-publish-smoke inbound-compat grep) were pipeline-migration debt surfaced by planning. They were not regressions in the shipped product code — they existed in the test/CI machinery from before v1.15 but only manifested under the new `~>` pin semantics.
- The gate-ci-green self-heal path ran as designed (ci.yml on the squash-merged SHA `827cede1b2b1` was blocked by bot-merge anti-recursion, and gate-ci-green found the push-triggered ci.yml run on the same SHA with all required lanes green).
- Racing publish-hex fan-outs (3 runs, one per release tag): the `mailglass-v1.11.0` and `mailglass_inbound-v1.6.0` tag runs failed publish-core with "must include the --replace flag" (idempotency guard didn't catch that the version was already published from a prior dispatch). The `mailglass_admin-v1.11.0` run's publish-core succeeded (idempotency check passed), then published inbound + admin in sequence.

**Key keystone payoff:** inbound's 1.6.0 minor was scored by Release Please from the banked `feat(125-01)` pin-loosening commit — no deliberate `fix(inbound): re-pin ==` dance was needed. The floor intentionally stayed `>= 1.10.2` (NOT bumped to `>= 1.11.0`) to preserve LD-2 decoupling; "verified against core 1.11" went in the CHANGELOG, not the floor.
