<objective>
Close review findings WR-06 and WR-05 on both collections. They share a mechanism: a URL value the filter normalization rejects.

- WR-06 (D-13): with an invalid value in the URL, any later change event (typing in Search, another select, or the phx-auto-recover payload after a reconnect) re-posts that value. The commit fails validation and sets the error source to `:draft`. Because the URL note is keyed on the error source being `:url`, it disappears, and the results, which still exclude the URL's invalid filter, are left without the label D-13 requires ("explicitly labeled as excluding that filter"; UI-SPEC row 112 "Never an unlabeled fallback population").
- WR-05 (D-12): an invalid enum value is kept in the draft, but the select has no matching option. The browser therefore shows the prompt ("Any status" / "Any outcome") beside "... was not applied". D-12 says the select must never contradict its error (UI-SPEC row 111).

Purpose: FILTER-04 "without silent fallback results". D-12 and D-13 are locked; this plan implements both as written and does not amend or narrow either.
Output: a `filter_url_invalid` assign in both LiveViews that drives the URL note independently of the draft; the draft note left exactly as D-12 specifies; a selected "Not applied: <value>" option in both enum selects; LiveView tests that fail before each fix; one browser test per collection covering reconnect and Search; and two clarifications in the UI-SPEC.

Decisions (owner-approved guidance, reversible):
- The fix for WR-06 is solely that the URL note no longer disappears on a re-post or reconnect. The draft note is not suppressed or gated: whenever the draft is invalid, the D-12 draft note shows; whenever the committed URL carries an invalid value, the D-13 URL note shows; when both apply, both render (review WR-06: "render the URL note whenever that map is non-empty, alongside the draft note"). No bounded reading of D-12 is recorded, because none is needed.
- Track URL-invalid fields separately, as review WR-06 suggests (`filter_url_invalid`, the URL error map snapshot from `handle_params`). Do not infer them from `filter_errors`, which mixes URL and draft origins after a change event.
- WR-05 is fixed in the product, not deferred. Deferring would mean rewriting UI-SPEC row 111 and weakening D-12's locked "so its select never contradicts its error". The option label shape "Not applied: <value>" is the one review WR-05 proposed. It mirrors the window select's existing custom option and reuses the word the error already uses.
</objective>
