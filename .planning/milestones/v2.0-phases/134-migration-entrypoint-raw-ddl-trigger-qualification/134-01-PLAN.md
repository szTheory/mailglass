<objective>
Wire the migration entrypoint to inject the runtime schema prefix, and make the
Postgres dispatcher actually issue CREATE SCHEMA / DROP SCHEMA around the structural
DDL. This is the layer that lets a non-`public` schema physically exist before the
v01–v05 tables are created into it, and be torn down cleanly on rollback.

Purpose: Close MIGR-01 (entrypoint prefix injection) and MIGR-02 (CREATE/DROP SCHEMA
lifecycle with the `create_schema: false` escape hatch and `RESTRICT` drop). Together
they are the precondition for Plan 134-02's raw-DDL qualification and the load-bearing
regression proof.

Output: `Mailglass.Migration.up/down` inject `prefix: Config.schema()`;
`Mailglass.Migrations.Postgres.maybe_create_schema/1` + `maybe_drop_schema/1`;
migration tests proving up/down round-trips against a non-public prefix.
</objective>

  <action>
    Add `maybe_create_schema/1` as the FIRST action of `up/1` — after `opts =
    with_defaults(opts, @current_version)` and BEFORE `migrated_version(opts)` /
    `change(...)`. Per dossier §3.5:

      defp maybe_create_schema(%{prefix: prefix, create_schema: true}) do
        validate_identifier!(prefix, :prefix)
        execute(~s(CREATE SCHEMA IF NOT EXISTS #{inspect(prefix)}))
      end
      defp maybe_create_schema(_), do: :ok

    `with_defaults/2` already sets `create_schema: prefix != @default_prefix` via
    `Map.put_new`, so a `public` prefix never issues CREATE SCHEMA and an explicit
    caller `create_schema: false` (locked-down prod role lacking CREATE — dossier §4.4)
    is honored because `Map.put_new` will not overwrite it. `inspect(prefix)`
    double-quotes the already-identifier-validated name (matches the `quoted_prefix`
    convention). Re-validate via `validate_identifier!/2` immediately before
    interpolation as the belt-and-suspenders chokepoint (WR-01 lineage — the single
    unquoted-identifier gate per decision 132-01), even though the value is operator
    config not request input.

    Add `maybe_drop_schema/1` and call it in `down/1` AFTER the tables are fully torn
    down. The correct hook is inside `change/3` on the `:down` branch when the range
    minimum reaches the initial version (i.e. the schema's tables are all dropped and
    `record_version` will stamp version 0). Implement it so the DROP SCHEMA fires ONLY
    when (a) `create_schema: true` AND (b) the down migration reached version 0
    (`Enum.min(range) - 1 == 0`). Per dossier §3.5:

      defp maybe_drop_schema(%{prefix: prefix, create_schema: true}) do
        execute(~s(DROP SCHEMA IF EXISTS #{inspect(prefix)} RESTRICT))
      end
      defp maybe_drop_schema(_), do: :ok

    Use `RESTRICT` (never `CASCADE`) so a non-empty schema (adopter parked other objects
    there) fails loudly rather than silently nuking data. Re-validate the identifier
    before interpolation here too.

    Placement guidance for the down hook: in `change/3`, the `:down` case already calls
    `record_version(opts, Enum.min(range) - 1)`. Add the `maybe_drop_schema/1` call in
    that same `:down` branch, guarded on `Enum.min(range) - 1 == 0`, so it runs after
    v01's tables are dropped and only on a full teardown to version 0. Keep it a no-op
    for partial down-migrations that don't reach 0. Ensure `down/1` invoked with the
    default (public) prefix never issues DROP SCHEMA (create_schema is false for public).

    Do NOT change `with_defaults/2`'s existing `create_schema` computation, the
    `quoted_prefix`/`escaped_prefix` derivations, or `migrated_version/1`.
