## Summary

The defect is a single conflated boolean. `should_run` answers "should the release-please *action*
run?" (correctly `false` in the permanent post-close-out steady state) but is also used to gate
"can the proposal-evidence control observe the repository?" (which is always yes — GitHub's PR list
API works regardless of tag state). Research strongly favors **candidate shape (a) — un-gate
`proposal-discovery` from `should_run`, keep `capture-proposal` gated on it** (see Recommendation
below), plus a **new discovery verdict** for the case where `should_run=false` and an open proposal
exists (count==1), because that world state is unreachable via the sync-gated capture step and today
silently degrades to the wrong writer branch. This new verdict — proposed name `pending` /
`proposal_awaiting_release_action` — must be added to the writer's whitelist (`:831-834`) and to
**both** copies of the pass predicate (`:857`, `:885`), which is the one widening this phase performs
and must document as "admitting a truthful observation," per D-05.

Two existing ExUnit test files (`release_trigger_recovery_test.exs`, 1543 lines, and
`workflow_hardening_contract_test.exs`) already extract-and-execute the *actual* bash bodies of each
named workflow step against fixture `gh`/`git` fakes — this is the load-bearing test harness the plan
must extend, not something to invent. Today's tests exercise the full discovery→capture→writer→gate
chain **only** under `should_run=true` fixtures (`with_idle_schedule_fixture(:none, ...)`, etc.); the
`with_fake_gh(:all_present, ...)` fixture that produces `should_run=false` is exercised **only**
against the preflight step in isolation (`empty commit messages check all release states before
permitting recovery`, line 187) — it never runs discovery/capture/writer under that fixture. That is
precisely the untested seam this phase's regression lives in, and precisely where the new tests must
land.

**Primary recommendation:** Un-gate `proposal-discovery` from `should_run` (keep it gated only on
`github.event.inputs.candidate_digest == ''`), leave `capture-proposal` gated on `should_run` exactly
as today (respecting D-03's sync-ordering hazard), add a `count==1 && should_run=false` branch inside
discovery that reports a new truthful `pending`/`proposal_awaiting_release_action` verdict (never
`pass`, never silently falling through to empty strings), and widen the writer's `case` whitelist plus
both instances of the pass predicate to admit that one new `pending`-reason pair. Extend
`release_trigger_recovery_test.exs` with a `with_fake_gh(:all_present, ...)` variant that runs
discovery+writer+gate together for count 0/1/many, pinning all five reachable world states.

### Pattern 1: Un-gate discovery, keep capture gated (Recommendation for D-01)

**What:** Change `proposal-discovery`'s `if:` condition (`:518`) from
`steps.release-preflight.outputs.should_run == 'true' && github.event.inputs.candidate_digest == ''`
to just `github.event.inputs.candidate_digest == ''`. Leave `capture-proposal`'s `if:` condition
(`:603`) unchanged (still requires `should_run == 'true'`).

**When to use:** When the "can we produce evidence" question is answerable independently of the
"should the mutating action run" question — which is exactly this control's situation. `gh pr list`
is a read-only call; it costs nothing to run unconditionally on every trigger with no candidate digest.

**Why over shape (b):** Shape (b) (a second preflight output) would require the preflight step itself
to answer a *second* question it currently has no reason to ask, duplicating the "what does the
control's own truthful verdict look like" logic into a step whose entire job today is "should the
action run." It also does not resolve D-03: whichever shape is chosen, the writer still needs a new
verdict for the count==1/`should_run=false` case, because capture cannot safely run there. Shape (a)
is the smaller diff: one `if:` clause changed, one new `case` branch inside a step that already
computes `count` and already branches on it, one new whitelist entry. Shape (b) would touch the
preflight step (which the plan D-19-equivalent constraint in Phase 166 explicitly said not to
touch/extend with new logic) *and* still need the same case-branch/whitelist changes downstream.

**Example (discovery step's existing `case`, `:582-597`, to be extended — quoted verbatim from the
file read this session):**
```bash
# Source: .github/workflows/release-please.yml:582-597 (read this session)
          count=$(jq -er 'length' <<<"$prs")
          case "$count" in
            0)
              should_capture=false
              result_status=pending
              result_reason=no_open_proposal
              ;;
            1)
              # Capture retains the existing exact identity and candidate
              # validation semantics for an active proposal.
              ;;
            *)
              # Keep capture authoritative for the existing multiple-proposal
              # blocked classification rather than converting ambiguity into
              # a successful pending observation.
              ;;
          esac
```
The count==1 branch is currently a no-op comment — `result_status`/`result_reason` stay at their
initialized empty strings (`:525-526`), which is fine when capture is about to run and will emit its
own verdict. It stops being fine the moment discovery runs unconditionally and `should_run=false`:
capture is skipped, so nothing ever overwrites those empty strings, and the writer's override
predicate (`:826`) requires `DISCOVERY_STATUS`/`DISCOVERY_REASON` to be **non-empty** — so it still
falls through to the `cannot-check` defaults even after discovery is un-gated. **This is the exact
mechanism CONTEXT.md's Research Question 2 (D-03) predicted and it is the reason a code change
inside the count==1 branch, not just the `if:` un-gating, is required.**

### Anti-Patterns to Avoid

- **Un-gating both discovery and capture:** Would capture a pre-sync digest (D-03's explicit hazard)
  — the sibling-pin sync step (`:391`) that settles README/pin content on the release branch runs
  only when `should_run == 'true'`, so a `should_run=false` capture would validate against
  potentially-stale branch content. Not attempted in this plan.
- **Adding `continue-on-error` to the gate steps:** Pre-refused by name in CONTEXT.md.
- **Widening the predicate to admit `cannot-check`:** Pre-refused by name in CONTEXT.md.
- **Inventing a brand-new top-level status value outside `pass|blocked|cannot-check|pending`:** Would
  require touching D-04's four-condition override branch AND the `case` whitelist AND both gate copies
  for no benefit — `pending` with a new `reason` string is sufficient and keeps the enum closed.

## Common Pitfalls

### Pitfall 1: Un-gating discovery alone does not fix the count==1 case (the crux, D-03/RQ2)
**What goes wrong:** Discovery runs, finds `count==1`, does nothing (its case branch is a no-op
comment today), leaves `result_status`/`result_reason` empty. Capture is skipped (still gated on
`should_run`). The writer's override predicate requires *non-empty* `DISCOVERY_STATUS`/`REASON`
(`:826`), so it still falls through to `cannot-check` defaults. **Net result: un-gating discovery by
itself does not close this phase for the `should_run=false` + open-proposal world state (today's live
state, PR #280) — only for the count==0 and count>1 states.**
**Why it happens:** The count==1 branch was written assuming capture always runs next to supply the
real verdict; that assumption breaks once discovery can run standalone.
**How to avoid:** Add an explicit branch: when `count==1` AND the step can detect it should not hand
off to capture (i.e., `should_run` was false — discovery does not currently receive that value as an
env var; it must be added), emit a positive verdict, not empty strings. Proposed:
`result_status=pending`, `result_reason=proposal_awaiting_release_action`, `should_capture=false`.
**Warning signs:** Writer output still shows `cannot-check`/`github_evidence_unavailable` after
un-gating discovery in isolation — this is the signature.

### Pitfall 2: Both `:857` and `:885` must change together (D-05)
**What goes wrong:** Editing only the writer's internal check (or only the standalone `Fail non-pass…`
step) leaves one predicate stricter than the other — the writer's step could exit 0 on the new
`pending` reason while the dedicated fail-step (which reads the *artifact-persisted* status/reason via
its own env, `:882-883`) still fails the job, or vice versa.
**Why it happens:** The predicate is duplicated by design (one inline in the writer for its own exit
code, one in a separate step reading the uploaded values) — CONTEXT.md D-05 already flags this.
**How to avoid:** Grep both `[ "$status" = pass ] ||` occurrences before and after the edit; diff must
show the identical clause added to both.
**Warning signs:** `grep -n '"$status" = pass\|RESULT_STATUS" = pass' .github/workflows/release-please.yml`
returns a different clause at the two sites.

### Pitfall 3: The `case` whitelist at `:831-834` is a silent second gate
**What goes wrong:** Even if discovery correctly emits `pending`/`proposal_awaiting_release_action`
and the writer's override branch correctly copies it through, the `case "$status" in
pass|blocked|cannot-check|pending) ;; *) status=cannot-check; ...` at `:831-834` only inspects
`$status` (`pending` already passes this), **not** `$reason` — so this specific whitelist does not
need editing for a same-status/new-reason addition. Verify this explicitly rather than assuming a
whitelist edit is needed; over-editing this switch would be exactly the "narrowing a generator in
reverse" motion the standing prohibition is watching for on the other side (accidentally rejecting a
previously-valid reason while adding a new one).
**Why it happens:** Confusing "the status whitelist" with "the pass predicate" — they are two
different pieces of code operating on different variables (`$status` alone vs. `$status` AND
`$reason` together).
**How to avoid:** Read `:831-834` and `:857`/`:885` side by side before editing; only the latter two
need the new `reason` string added, in an `||` branch alongside the existing `no_open_proposal` clause.

### Pitfall 4 (carried from 166-04's own finding): Line numbers in this file drift between plans
**What goes wrong:** Citing `:518`/`:826` etc. as stable coordinates when the file has already been
edited twice this milestone (Phase 166 Plan 04, then whatever lands in this phase).
**Why it happens:** Every edit shifts subsequent line numbers.
**How to avoid:** As 166-04's own SUMMARY recorded: "the plan's line numbers should not be trusted
for this file without re-grepping." Locate every edit point in the executing plan by `grep -n` on a
literal string (step name, `if:` condition text, or a unique comment), never by line number alone.
Line numbers in this RESEARCH.md are current as of this session's read and are already stale the
moment the first task edits the file.
