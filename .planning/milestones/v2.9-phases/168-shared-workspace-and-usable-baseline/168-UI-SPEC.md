# Phase 168 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Design System

| Property | Value |
|----------|-------|
| Tool | Manual — existing Mailglass design system; no shadcn |
| Preset | Not applicable |
| Component library | Phoenix.Component / HEEx; Tailwind v4 + vendored daisyUI utilities |
| Icon library | Vendored Heroicons Tailwind plugin, rendered inline |
| Font | Inter for UI/body; Inter Tight for headings; IBM Plex Mono for identifiers/code |

Continue the existing LiveView/HEEx and prebuilt asset model. Use semantic theme tokens and shared components; do not add a framework, component registry, client-JS build, or competing stylesheet. Keep the existing sealed-flap Mailglass identity and flat surfaces. No glassmorphism, gradients, bevels, decorative noise, or new visual identity.

**Phase scope:** refine shared shell, navigation, Account context/switching, type/spacing, theme choice, common controls, feedback, and representative operator screens. Use the Operator Overview and Deliveries as the working-task examples; verify Inbound only for shared-shell consistency. Keep complete outbound recovery, inbound recovery, developer preview, recipient journeys, and final gallery/documentation consolidation with their roadmap owners.

**Baseline prerequisite (D-10):** after reconciling the preserved workspace with the merged cleanup source, identify the actual checkout/revision and assets the preview serves, then capture the rendered before state before any UI edits. Record the source/revision, host and route, fixture/persona, theme and OS setting, CSS viewport and zoom, interaction state, and observed issue for each specimen. Use the deterministic AtlasDesk demo and seeded Northstar Logistics (`tenant_id=northstar`); cover `/ops/mail?tenant_id=northstar`, `/ops/mail?tenant_id=northstar&view=deliveries`, and `/ops/mail/inbound?tenant_id=northstar` where the inbound package is configured. Route through the demo login as documented. Historical captures and source inspection are not current rendered proof. This contract does not claim the baseline has been captured.

**Composition:** retain the topbar, desktop sidebar, narrow-screen navigation row, and bounded main content frame. On desktop, keep the Mailglass mark at the leading edge, selected Account context and switcher in the shared topbar, and appearance control at the trailing edge. At narrow widths the topbar may wrap, but the selected Account name and stable scope remain visible without opening filters; keep Account control and appearance control separately labeled. Keep section navigation visible and the current surface unmistakable. Show only destinations configured and available for the mount. Page title precedes task content; preserve each screen's content-led layout rather than forcing every job into identical cards.

**Primary visual anchors:** with no selected Account, the Account chooser leads. Once scoped, Health leads with the current operational health summary; Deliveries leads with the Delivery list and its selected record. The page title and persistent Account context establish orientation; filters and supporting metrics are secondary. In Quick view, the record identity and observed outcome lead, followed by evidence and eligible actions. Avoid promoting the logo, appearance picker, every card, or every row action to equal visual weight.

**Responsive contract:** use the existing `md` breakpoint (768 CSS px) for sidebar versus compact navigation. Below it, use the horizontal navigation row and allow the topbar to wrap without clipping Account or appearance controls. At 320 CSS px and 200% browser zoom, essential content and controls remain reachable without page-level horizontal scrolling. Keep the existing `max-w-7xl` main content bound on wide screens. Long labels and identifiers wrap or expose the complete value in an accessible, keyboard/touch-available detail; never make hover/title the only way to read them.

## Spacing Scale

Declared values preserve the established 4px grid.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, inline alignment |
| sm | 8px | Compact element spacing |
| md | 16px | Default control/content spacing |
| lg | 24px | Section padding and grouping |
| xl | 32px | Layout gaps |
| 2xl | 48px | Major section breaks |
| 3xl | 64px | Page-level separation where content allows |

Control dimensions are distinct from spacing tokens: existing small/medium/large controls are 36/44/52px high. Interactive controls, including icon-only controls, must provide at least a 44×44px hit target. A 36px visual tab is allowed only inside a non-overlapping 44px target. Do not introduce off-grid spacing values.

### Radius, elevation, and stacking

Preserve the source tokens in `mailglass_admin/assets/css/app.css`; these dimensions are not extra spacing tokens.

| Role | Contract |
|------|----------|
| Radius | `--radius-selector` / `--radius-field`: 4px; `--radius-box`: 8px. Reuse these on shared controls and panels. |
| Borders | Existing 1px semantic border. Essential control boundaries and focus must remain distinguishable in both themes. |
| Elevation | `--shadow-flat: none` for ordinary surfaces; `--shadow-raised: 0 1px 2px 0 rgb(13 27 42 / 0.06)` only for existing raised groups; `--shadow-overlay: 0 8px 24px -8px rgb(13 27 42 / 0.18)` for floating panels. |
| Layers | Named `--z-base: 0`, `--z-sticky: 10`, `--z-dropdown: 20`, `--z-overlay-scrim: 30`, `--z-overlay-panel: 40`, `--z-toast: 50`; no local escalating z-index values. Keep floating content clear of clipping ancestors and modal focus boundaries. |

Consolidate changed Quick view positioning into the shared stylesheet and update the corresponding presentation assertions. Keep rebuilt static assets with source changes. Do not preserve duplicate rules merely to avoid a parity check.

## Typography

Use the installed 400 and 700 weights only. The 14/16/20/28px size choices deliberately replace the current 12/14/20/28px formal scale for this shared workspace: running body copy meets the brand's 16px floor, and essential labels stop using 12px text. Use Inter Tight only for headings; use IBM Plex Mono at 14px for exact identifiers and code.

Implement these as fixed rem equivalents of the specified sizes at the default root size; preserve browser/user text sizing. Keep the installed system and monospace fallbacks usable while fonts load or fail. These are design targets; their fit must pass the source-identified rendered acceptance before phase completion.

| Body | 16px | 400 | 1.5 |
| Label | 14px | 400 | 1.4 |
| Heading | 20px | 700 | 1.2 |
| Display | 28px | 700 | 1.2 |

## Copywriting Contract

Use Mailglass's plain, exact voice and domain nouns. Say **Account** in shared operator UI; show the host-supplied human-readable name with the stable `tenant_id` available directly underneath. Preserve the distinctions between dispatch and delivery, requested and completed work, and replay and resend.

| Element | Copy |
|---------|------|
| Primary CTA | `Choose Account` |
| Empty state heading | `Choose an Account` |
| Empty state body | `Select an Account to see scoped operator data.` |
| No Accounts with activity | `No Accounts with mail activity` — `Send a Message from your app, or check how your app sets tenant_id.` Render `tenant_id` as code. This is distinct from having available Accounts with no selection. |
| Account switch failure | `Account was not changed. Try choosing it again.` Use only when the prior selection is retained; otherwise show the actual access/load failure without presenting prior data as the requested Account. |
| Restricted access | `Access to this Account is restricted.` — `Choose another Account, or contact your Mailglass host administrator.` Offer another Account only if one is actually available. Preserve the host's denial and reauthentication behavior. |
| Stale view | `This view may be out of date.` — `Refresh the view to check for updates.` |
| Error state | `This view could not be updated. Refresh to try again. If it continues, contact your Mailglass host administrator.` |
| Destructive confirmation | None added by Phase 168. Preserve existing exact-target confirmation, authorization timing, recent-auth, and outcome copy for any recovery action shown. |

Theme control visible labels: `System`, `Light`, `Dark`; fieldset label: `Appearance`. Keep the selected preference visibly distinct as well as exposed through radio checked semantics. If a switch is busy or rejected, retain the prior selected Account and scope until the new selection succeeds; announce the result in the shared live status region.

Use `Account` as the field label and `Choose Account` only when selection is needed; a selected workspace keeps its existing task actions primary. Existing populated-screen no-data, filtered-empty, validation, and action-outcome copy stays specific to its cause and source behavior. Do not substitute the generic update-error row for actionable existing messages or use empty-state copy for denied, stale, or unavailable data.

## Interaction and Acceptance Contract

- **Account and navigation:** keep selected Account context visible on desktop and narrow screens, independent of filters. Preserve `tenant_id` in shareable URLs and compatible filters on same-surface switching; clear record selections belonging to the previous Account. Cross-surface navigation preserves Account scope while dropping surface-specific filters/selections. Preserve existing zero/one/many behavior, including single-Account auto-selection when the route omits `tenant_id`, and the explicitly unselected route. Host labels fall back to stable IDs; preserve a selected permitted ID even if absent from the activity-derived option list. Do not broaden authorization or make developer preview production-account scoped.
- **Theme:** persist exactly one Light, Dark, or System preference across Admin/preview chrome and reload. While System is selected, OS appearance changes update effective chrome without replacing the System selection. Keep email preview/device appearance independent. Theme changes are immediate and do not animate the whole page's colors.
- **Controls and feedback:** provide applicable default, hover, visible focus, pressed, selected, disabled, busy, and validation states through shared components. Hover treatment is for fine pointers; selected, focus, and status states remain apparent without hover and beyond color. Keep control hit targets at least 44px. Use visible labels on controls; icon-only actions receive an accessible name and a visible focus ring.
- **Overlays:** inspect the rendered Quick view and confirmation interactions before changing their presentation. Give each overlay a meaningful title, contain focus when modal, support Escape and the existing dismissal behavior, and return focus to its trigger. Preserve exact-target, action-time authorization, recent-auth, and confirmation semantics. Do not add destructive actions in this phase.
- **Motion:** reuse the existing named motion tokens. Limit routine control state transitions to 90–150ms and first-mount detail/overlay reveal to at most 220ms; use opacity and small settling movement only. Do not animate keyboard-repeatable actions, theme-wide color changes, routine LiveView patches, or repeated list updates. Reduced motion removes movement and reduces transitions/animation to effectively instant while retaining understandable state changes. Loading and success/error status remain understandable without motion.
- **Rendered proof:** use a batched review, one corrective batch, and one confirmation review per coherent slice. Cover the baseline specimens above at 320, 390, 768, and 1440 CSS px; Light, Dark, and System with OS change/reload; keyboard and touch; 200% zoom; reduced motion; selected and unselected Account; no configured optional Inbound destination; long names/IDs; empty, busy, validation, and error states as applicable. Use a representative matrix covering each dimension, rather than multiplying every fixture by every variant. Add a further review only for a concrete unresolved blocker. Existing focused checks remain the verification path; no historical screenshot or unchanged score substitutes for current rendered inspection.
