## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-01:** Sync and Oban-backed async delivery must enter one canonical dispatch seam with the same fully prepared `Mailglass.Message`/Swoosh input shape. The only permitted differences are timing and values generated by the provider after Mailglass hands off the request.
- **D-02:** The Phase 150 envelope codec is the durability boundary, not a second message-authoring path. Async loads its immutable envelope; sync normalizes through the same preparation/dispatch contract without persisting a payload solely to send synchronously.
- **D-03:** Wire-equivalence tests compare the actual adapter input for every supported one-recipient field, ordered header, attachment, Mailglass metadata/tag, and JSON-safe provider option. Unsupported values remain typed pre-dispatch failures rather than being silently dropped by either path.
- **D-04:** Existing public adapter callback compatibility is preserved. Internal structural outcome metadata may wrap or translate existing adapter results, but custom adapters are not forced through an unrelated breaking callback redesign in this phase.
- **D-05:** The dispatch boundary returns a closed structural classification with three operational classes: `retryable`, `terminal`, and `uncertain`. Worker behavior keys only on this structure—never exception text or provider-message substring matching.
- **D-06:** Retryable means Mailglass has evidence that another attempt is appropriate, including transport failure before confirmed acceptance and structurally identified transient/server outcomes. Only this class is returned to Oban for automatic retry.
- **D-07:** Terminal includes malformed/configuration/suppression errors, missing/corrupt/expired/unsupported/scrubbed payload states, confirmed permanent provider rejection, and other pre-dispatch failures. Terminal outcomes persist an actionable delivery/event state and cancel/discard without retry.
- **D-08:** Uncertain means provider acceptance may have occurred and automatic resend could duplicate customer mail. It persists a repair/reconciliation-required outcome with safe correlation context and does not automatically retry.
- **D-09:** Classification must retain stable reason classes and bounded, non-sensitive context. Raw message content, credentials, provider payloads, attachment bytes, and arbitrary exception text remain outside public projection/events/logging.
- **D-10:** Research may refine provider/status mappings, but ambiguity is resolved conservatively: never claim confirmed rejection or safe retry when the available structured evidence cannot establish it.
- **D-11:** Confirmed dispatch success uses one database transaction to update the non-sensitive Delivery projection, append the success ledger event, and scrub recoverable envelope content. A partial “sent but payload still readable” persistence transition is not accepted.
- **D-12:** Scrubbing keeps a private tombstone row with lifecycle/version/digest identifiers and `scrubbed_at`, while removing all recoverable subject/body/header/token/attachment/provider-option bytes. Delivery and ledger history remain intact.
- **D-13:** Missing, corrupt, unsupported-version, expired, and already-scrubbed payloads are distinct operator-actionable terminal reasons. Modern queued work never falls back to reconstructing a message from incomplete `Delivery.metadata`.
- **D-14:** Projection/envelope route mismatch and integrity failures remain fail-closed. Payload lifecycle handling must not weaken Phase 150 tenant scoping, digest verification, version discrimination, or ID-only job arguments.
- **D-15:** A worker retry races safely with lifecycle transitions: row locking or equivalent compare-and-set semantics prevent double dispatch caused by concurrent payload state changes, and repeated terminal handling remains idempotent.
- **D-16:** Successful payloads scrub immediately. Terminal, discarded, abandoned, uncertain, and legacy queued payloads receive explicit lifecycle states and a configurable bounded retention window; no private content is retained indefinitely by default.
- **D-17:** Exact default durations and configuration names are delegated to research/planning, which must justify them against current project configuration conventions and provider reconciliation needs. Defaults must be finite, documented, testable, and safe for a one-maintainer library.
- **D-18:** Pruning is tenant-safe, schema-prefix-safe, bounded in batches, idempotent, and observable through non-sensitive counts/reason classes. It preserves the public Delivery/event audit trail and a private non-content tombstone sufficient to explain why recovery is no longer possible.
- **D-19:** Legacy queued rows retain only the narrow forward-compatible reader already promised by Phase 150. There is no backfill that invents a complete envelope from old public metadata. Legacy recovery/cleanup has an explicit window and then settles to an actionable terminal state.
- **D-20:** Recovery never means blind resend of an uncertain outcome. Operator action must distinguish retry-safe recovery from reconciliation of possible provider acceptance.
- **D-21:** Public guidance explicitly states the at-least-once boundary: Mailglass can make its database/queue transitions atomic, but cannot make provider acceptance and local acknowledgement one transaction.
- **D-22:** Guidance explains provider idempotency keys and correlation identifiers as duplicate-risk reduction/reconciliation tools, not exactly-once guarantees. Provider-specific claims require executable or authoritative evidence.
- **D-23:** Docs and contract tests enumerate retryable, terminal, and uncertain behavior; payload retention/scrubbing/pruning; missing/corrupt/expired/scrubbed handling; and the absence of private content from public metadata.

## Summary

Use one internal `dispatch_prepared/2` pipeline after both paths have produced the same fully prepared `Mailglass.Message`. The sync path should persist its queued projection, stamp the already-prepared message with the persisted delivery ID, and call that seam. The durable worker should load and verify the immutable envelope, acquire its lifecycle lease/state guard, then call exactly the same seam. This removes the present divergence where sync calls the adapter directly while async separately loads payload and has broader failure handling. [VERIFIED: codebase grep]

Represent adapter results internally as a closed success-or-outcome value, not as a new public adapter callback. Swoosh’s callback only promises `{:ok, term}` or `{:error, term}`; it cannot establish a portable provider-acceptance certainty contract. Mailglass must therefore make the generic/custom-adapter fallback conservative (`:uncertain`), recognize only structured, documented local facts as retryable or terminal, and never parse error text. [CITED: https://swoosh.hexdocs.pm/Swoosh.Adapter.html]

Treat `mailglass_outbound_payloads` as a private state machine. Add an explicit state/reason representation because the existing nullable `scrubbed_at` and `expires_at` timestamps cannot distinguish recoverable, scrubbed, expired, corrupt, or legacy-settled rows. Success performs projection update + ledger event + content removal in one Multi; later prune transitions content-bearing non-success rows to an expired tombstone in bounded batches. The existing row, delivery, and event ledger remain the audit trail. [VERIFIED: codebase grep]

**Primary recommendation:** Add internal `DispatchOutcome` and `PayloadLifecycle` modules; make the Oban worker return `{:error, safe_reason}` only for `:retryable`, and atomically tombstone all non-recoverable payload outcomes under the configured Mailglass prefix.

### Pattern 1: Canonical prepared dispatch seam

**What:** Route both sync and durable async through a helper that accepts an already-prepared message and resolved adapter; the helper returns either accepted data or a closed `DispatchOutcome`.

**When to use:** After all rendering/preflight/routing work has completed. Never let worker-specific code invoke an adapter directly.

**Example:**

```elixir
# Internal shape; adapter callback remains Mailglass.Adapter.deliver/2.
with {:ok, adapter_result} <- call_adapter(prepared, adapter) do
  {:accepted, normalize_acceptance(adapter_result)}
else
  {:error, reason} -> DispatchOutcome.classify(reason)
end
```

The Swoosh adapter behavior allows generic success/error terms, so classification must be local and conservative rather than inferred from arbitrary response text. [CITED: https://swoosh.hexdocs.pm/Swoosh.Adapter.html]

### Pattern 2: Closed outcome to worker-result mapping

**What:** Give `DispatchOutcome` a closed type such as `{:accepted, acceptance}` or `{:outcome, %{class: :retryable | :terminal | :uncertain, reason_class: atom(), context: map()}}`.

**When to use:** For every adapter return, payload error, route mismatch, and persistence-safe dispatch result before `Worker.perform/1` chooses an Oban response.

**Example:**

```elixir
case Outbound.dispatch_by_id(delivery_id) do
  {:ok, %Delivery{status: :sent}} -> :ok
  {:outcome, %{class: :retryable, reason_class: reason}} -> {:error, reason}
  {:outcome, %{class: class, reason_class: reason}} when class in [:terminal, :uncertain] ->
    {:cancel, reason}
end
```

Oban marks `{:error, reason}` retryable until exhausted and `{:cancel, reason}` cancelled without another retry. [CITED: https://oban.hexdocs.pm/Oban.Worker.html]

### Pattern 3: Lock then call provider, but never hold a database transaction across I/O

**What:** In a short transaction, lock/read the tenant-scoped payload and atomically claim an allowed recoverable state; release it before provider I/O. On outcome, use a separate short transaction with a compare-and-set/lock-version guard to settle state. If a concurrent transition wins, do not issue another provider call.

**When to use:** Durable worker dispatch and prune/recovery races.

**Why:** Keeping provider I/O inside an Ecto transaction risks pool starvation, while no guard permits two workers to dispatch the same recoverable payload. The present code already documents the former constraint and has optimistic-lock support in `Projector`. [VERIFIED: codebase grep]

### Pattern 4: Atomic success tombstone

**What:** On confirmed adapter success, one `Ecto.Multi` updates Delivery, appends `:dispatched`, and replaces recoverable envelope bytes with a non-content tombstone carrying state/version/digest and `scrubbed_at`.

**When to use:** Only durable payload-backed dispatch. Sync and the explicitly non-durable Task.Supervisor path share the provider-input seam but have no Payload: their success transaction updates Delivery and Event only and must not query, create, or scrub a payload.

**Example:**

```elixir
Ecto.Multi.new()
|> Ecto.Multi.update(:delivery, sent_changeset, Repo.multi_opts())
|> Events.append_multi(:event_dispatched, safe_event_attrs)
|> Ecto.Multi.update(:payload, Payload.scrub_changeset(payload, now), Repo.multi_opts())
|> Repo.multi()
```

Every Multi step must use `Repo.multi_opts()`; transaction-level options do not apply the Mailglass schema prefix to individual statements. [VERIFIED: codebase grep]

### Pattern 5: Lifecycle policy and prune entrypoints

**What:** Put retention parsing/defaults and `prune/1` in a non-Oban lifecycle module; expose an optional Oban maintenance worker and a Mix task that both call it.

**When to use:** Daily scheduled cleanup with Oban, and manual/system-cron cleanup when Oban is unavailable.

**Example:** The existing webhook pruner uses this exact split, including a callable `prune/0`, optional worker wrapper, prefix-facade deletes, telemetry, and a Mix task. [VERIFIED: codebase grep]

### Anti-Patterns to Avoid

- **Error/message matching:** Do not branch on `Exception.message/1`, `body_preview`, `inspect/1`, or provider body substrings; arbitrary adapter/provider text is neither stable nor safe. [VERIFIED: codebase grep]
- **Treating every `:adapter_failure` as retryable:** Existing `SendError.retryable?/1` is intentionally too coarse for this phase; use the new structural outcome instead. [VERIFIED: codebase grep]
- **Synthetic success IDs as confirmed provider correlation:** Swoosh bridge currently creates an ID for success maps lacking `:id`; retain compatibility but mark correlation availability explicitly and do not promise reconciliation identity. [VERIFIED: codebase grep]
- **Fallback from a modern missing Payload to Delivery.metadata:** Only recognizable pre-v2.4 rows use the legacy reader; new rows must become terminal. [VERIFIED: codebase grep]
- **Deleting the envelope row:** This erases the required explanatory tombstone. [VERIFIED: phase context]
- **Unbounded `:infinity` for private outbound content:** Unlike webhook audit records, D-16 requires a finite default for queued private content. [VERIFIED: phase context]

## Recommended Outcome and Payload Policy

### Closed reason-class policy

| Evidence at dispatch boundary | Class | Stable reason class | Worker action |
|---|---|---|---|
| Adapter success result | accepted | `:accepted` | Persist success + scrub, then `:ok`. |
| Swoosh `{:error, {:api_error, status, _}}` with 400–499 | terminal | `:provider_client_rejected` | Persist failed/rejected state; `{:cancel, safe_reason}`. |
| Swoosh `{:error, {:api_error, status, _}}` with 500–599 | retryable | `:provider_server_error` | Persist non-terminal attempt fact if desired; `{:error, safe_reason}`. |
| Known local failure before adapter invocation (preflight, config, route, serialization) | terminal | existing bounded reason class | Persist terminal state when Delivery exists; no retry. |
| Payload missing/corrupt/unsupported/expired/scrubbed/route mismatch | terminal | a distinct `:payload_*` reason per state | Persist terminal state; no legacy reconstruction for modern rows. |
| Explicit adapter extension marks `before_acceptance` transport failure | retryable | `:transport_before_acceptance` | Retry. |
| Timeout, exit, connection failure, malformed/unknown adapter error, or custom adapter error without proof | uncertain | `:provider_acceptance_unknown` / bounded subtype | Persist repair-required state; cancel, never resend automatically. |

The Swoosh behavior only defines generic success/error terms. The shown HTTP tuple is Mailglass’s current bridge convention, not a portable Swoosh guarantee; keep this mapping isolated to `Mailglass.Adapters.Swoosh` and unit-test it. [CITED: https://swoosh.hexdocs.pm/Swoosh.Adapter.html] [VERIFIED: codebase grep]

For D-04 compatibility, allow existing custom adapters to keep returning the present contract. They receive conservative handling unless they opt into an additive, documented internal result marker or a typed `SendError.context` field that declares one of the closed reasons. Do not accept arbitrary atoms, arbitrary maps, or raw exception content as a classification. [VERIFIED: codebase grep]

### Payload states and retention

Use this closed private lifecycle set: `:recoverable`, `:dispatching`, `:scrubbed`, `:expired`, `:terminal`, `:discarded`, `:abandoned`, `:uncertain`, and `:legacy`. Persist a bounded `reason_class` for every non-recoverable state. V07 is required because V06 timestamps cannot distinguish these operational causes safely. [VERIFIED: codebase grep]

| Lifecycle state | Required bounded reason contract | Recoverable content | Default retention/action |
|---|---|---:|---|
| `:recoverable` | `nil` (no failure yet) | yes | retry horizon; only state eligible for a new claim |
| `:dispatching` | `:dispatch_claimed` | yes | a later observer settles it to `:uncertain`, never auto-resends |
| `:scrubbed` | `:accepted` | no | retain explanatory tombstone |
| `:expired` | retain the prior bounded reason, or `:retention_expired` when none exists | no | retain explanatory tombstone |
| `:terminal` | closed permanent reason such as `:provider_client_rejected`, `:pre_dispatch_failure`, or exact `:payload_*` reason | yes until prune | 14 days, then `:expired` |
| `:discarded` | `:job_discarded` | yes until prune | 14 days, then `:expired` |
| `:abandoned` | `:job_abandoned` | yes until prune | 14 days, then `:expired`; stale post-I/O claims use `:uncertain` instead |
| `:uncertain` | `:provider_acceptance_unknown` or a closed bounded uncertainty subtype | yes until reconciliation/prune | 30 days, reconciliation only, then `:expired` |
| `:legacy` | `:legacy_queued` | only if the old row actually has it | 14 days; never invent an envelope from Delivery metadata |

Retryable settlement returns `:dispatching` to `:recoverable` while Oban attempts remain; the final attempt records `:discarded/:job_discarded` before exhaustion. `:abandoned` is an explicit idempotent lifecycle transition applied only when queue/recovery evidence proves no viable job exists—it is never inferred from provider ambiguity. Observing a stranded post-handoff `:dispatching` claim is `:uncertain`, not abandoned or retry-safe.

Recommend this NimbleOptions subtree:

```elixir
config :mailglass, :outbound_payload_retention,
  terminal_days: 14,
  uncertain_days: 30,
  legacy_days: 14,
  prune_batch_size: 500
```

- `terminal_days: 14` is a finite default slightly longer than the currently documented maximum default Oban retry horizon of about 13 days, leaving a one-maintainer recovery window without retaining bodies indefinitely. [CITED: https://oban.hexdocs.pm/Oban.Worker.html]
- `uncertain_days: 30` is longer because reconciliation may require provider/support investigation; it is still finite as D-16 requires. This is a project-policy recommendation, not a provider SLA. [ASSUMED]
- `legacy_days: 14` gives recognizable pre-v2.4 queued work one bounded chance to run/recover before terminal settling; it must never construct a new envelope from metadata. [VERIFIED: phase context]
- `prune_batch_size: 500` bounds locks/WAL/maintenance time while avoiding one-row query churn. Make it a positive integer and test an override; this is a safe operational default, not a performance guarantee. [ASSUMED]

Set `expires_at` on creation for legacy/terminal/uncertain retention and only let recovery load a `:recoverable` payload with `expires_at > now`. Successful sends scrub immediately rather than waiting for the clock. A prune should select one prefix/tenant-safe batch of expired content-bearing rows, atomically turn each to `:expired`, remove envelope content, retain version/digest/IDs/reason/timestamp, and repeat only when invoked again. Do not use bulk `delete_all` for the payload table because each row needs a retained tombstone and idempotent state transition. [VERIFIED: phase context] [VERIFIED: codebase grep]

## Common Pitfalls

### Pitfall 1: Retrying an acceptance-unknown timeout

**What goes wrong:** A provider may receive and accept mail while the client loses the response; retry sends a duplicate.

**Why it happens:** The existing `SendError.retryable?/1` treats all adapter failures alike, and Oban retries all `{:error, _}` outcomes. [VERIFIED: codebase grep] [CITED: https://oban.hexdocs.pm/Oban.Worker.html]

**How to avoid:** Default unknown transport/adapter failures to `:uncertain`; allow `:retryable` only from structural evidence. Persist a non-PII correlation ID if the adapter has one.

**Warning signs:** A worker branches on `retryable?(error)`, a provider error string, or `inspect(error)`.

### Pitfall 2: Scrubbing after, not within, success persistence

**What goes wrong:** A crash between “sent” projection and a later scrub leaves private content readable.

**Why it happens:** Current `persist_dispatched_multi/3` updates only Delivery and Event. [VERIFIED: codebase grep]

**How to avoid:** Include payload tombstone update in the same Multi and broadcast only after it commits.

**Warning signs:** A standalone `Payload.scrub` follows `Repo.multi` success.

### Pitfall 3: Holding a row lock while calling the provider

**What goes wrong:** Long provider latency holds DB connections/locks and blocks prune/recovery.

**Why it happens:** “Make it atomic” is incorrectly applied to external I/O.

**How to avoid:** Short claim transaction, provider call outside transaction, short compare-and-set settlement transaction.

**Warning signs:** `call_adapter` is nested in `Repo.multi` or a transaction closure.

### Pitfall 4: A non-explicit lifecycle encoded as nullable JSON/timestamps

**What goes wrong:** `nil` envelope or timestamps conflate missing, scrubbed, expired, and corrupt conditions.

**Why it happens:** V06 was storage infrastructure, not the Phase 151 policy/state machine. [VERIFIED: codebase grep]

**How to avoid:** Explicit closed state + reason fields and exact fetch result mapping.

**Warning signs:** `nil` checks decide whether to retry.

### Pitfall 5: Prefix or tenant leakage in prune

**What goes wrong:** A raw query or Multi step targets `public`/ambient search_path or crosses tenant rows.

**Why it happens:** Ecto transaction options do not propagate `:prefix` to individual Multi operations. [VERIFIED: codebase grep]

**How to avoid:** Use `Repo.multi_opts()` on each update and `Tenancy.scope/2`/tenant predicates for fetch, claim, and prune tests; retain hostile-search-path coverage.

### Pitfall 6: Treating Oban uniqueness as exactly-once dispatch

**What goes wrong:** Unique enqueue prevents some duplicate jobs but cannot atomically join provider acceptance with the local database acknowledgement.

**Why it happens:** Queue uniqueness is an insertion/execution control, while provider I/O is external.

**How to avoid:** Document at-least-once semantics and use provider idempotency/correlation only as risk reduction/reconciliation aids.

**Warning signs:** Docs claim “exactly once,” or tests infer provider non-duplication solely from Oban `unique`.

### Oban terminal versus retryable mapping

```elixir
# Source: https://oban.hexdocs.pm/Oban.Worker.html
def perform(%Oban.Job{args: %{"delivery_id" => id}}) do
  case Mailglass.Outbound.dispatch_by_id(id) do
    {:ok, %Delivery{status: :sent}} -> :ok
    {:outcome, %{class: :retryable, reason_class: reason}} -> {:error, reason}
    {:outcome, %{class: class, reason_class: reason}} when class in [:terminal, :uncertain] ->
      {:cancel, reason}
  end
end
```

Oban documents `:ok` as completed, `{:error, _}` as retryable until max attempts, and `{:cancel, _}` as non-retryable cancellation. [CITED: https://oban.hexdocs.pm/Oban.Worker.html]
