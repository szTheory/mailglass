# Milestone v0.6: Production Maturity

**Status:** ✅ SHIPPED 2026-05-05
**Phases:** 32-34
**Total Plans:** 9

## Overview

v0.6 closed the last major pre-`v1.0` operational credibility gaps in
mailglass. The milestone hardened replay and reconcile operator flows,
added a truthful incident-support and observability surface, and turned
the support-contract verification story into an explicit, enforceable CI
contract.

## Phases

### Phase 32: Replay & Reconcile Hardening

**Goal**: Operators can replay and reconcile webhook-driven delivery state safely, with explicit guardrails around authorization, ambiguity, and audit outcomes.
**Depends on**: Phase 31
**Plans**: 3 plans

Plans:

- [x] 32-01: Action-time replay authorization and exact-target guardrails
- [x] 32-02: Shared repair-state wording for replay availability, outcome, and effect
- [x] 32-03: Reconcile fallback contract, docs, and regression coverage

**Details:**
- Replay now follows one server-side sequence: resolve the tenant-safe target, authorize the adopter-owned destructive action, then execute replay.
- Operator-visible replay wording is centralized so `ready`, `choice required`, `unavailable`, `requested`, `completed`, `failed`, `new work`, and `no change` are consistent across the UI.
- Reconcile now runs through one honest contract with or without Oban, including a truthful `mix mailglass.reconcile` fallback and aligned maintenance docs.

### Phase 33: Observability & Incident Support

**Goal**: Operators can diagnose production delivery issues through documented telemetry, backlog signals, and incident-response workflows.
**Depends on**: Phase 32
**Plans**: 3 plans

Plans:

- [x] 33-01: Canonical incident guide, telemetry contract correction, and docs-alignment tests
- [x] 33-02: Tenant-scoped support-summary read model backed by durable webhook and ledger facts
- [x] 33-03: Operator support cards, privacy-minimized overview cues, and LiveView regression coverage

**Details:**
- Added a canonical symptom-first incident guide and corrected telemetry docs to match the shipped signal surface.
- Added a tenant-scoped support summary read model driven by durable webhook rows and append-only event facts.
- Added delivery-centric support cards, masked overview cues, and exemplar drilldowns so operators can inspect support state without widening the product into a separate dashboard.

### Phase 34: Verification & Regression Closure

**Goal**: Maintainers can trust automated verification to catch the most material support and regression gaps before `v1.0`.
**Depends on**: Phase 33
**Plans**: 3 plans

Plans:

- [x] 34-01: Root support-contract authority and bootstrap honesty
- [x] 34-02: Admin support-contract authority and bootstrap honesty
- [x] 34-03: Honest orchestrator, explicit CI contract, and advisory/docs alignment

**Details:**
- Added explicit `verify.support_contract.core`, `verify.provider_compatibility`, and `verify.support_contract.admin` authorities.
- Made both root and admin citext probes fail honestly on retry exhaustion with deterministic regression coverage.
- Reworked CI so the required contract is the three explicit buckets: `Compile No Optional Deps`, `Support Contract Core`, and `Support Contract Admin`.

## Milestone Summary

**Decimal Phases:**

- None.

**Key Decisions:**

- Keep replay and future manual repair actions on the existing adopter-owned `:destructive_action` auth seam.
- Keep support cues delivery-centric and read-only inside the existing operator detail experience.
- Make support-contract verification explicit and separate required checks from advisory breadth.

**Issues Resolved:**

- Replay authorization, ambiguity, and operator wording were hardened into one consistent operator contract.
- Production-support docs and telemetry references now describe the actual shipped support surface.
- Root/admin support-contract verification no longer depends on vague or implied CI truth.

**Issues Deferred:**

- GitHub branch-protection verification remains manual because that state is external to the repo.
- A small number of non-blocking boundary warnings remain in support-summary and admin probe verification paths.

**Technical Debt Incurred:**

- The remaining boundary warnings are accepted debt rather than repo-blocking regressions.
