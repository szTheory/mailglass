<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| workflow config → CI runner | An edited cache key / setup-beam input changes what toolchain runs and what artifacts are restored. A wrong exact-patch pin or a stale restore-key crosses here as a correctness risk. |
| `.tool-versions` → setup-beam + cache | One file drives both toolchain setup and cache-bust; a bad value fails-loud (setup-beam errors under strict), which is the desired safety property. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-129-01 | Tampering | `.tool-versions` exact-patch pin | high | mitigate | Resolve patches from a green CI run / setup-beam manifest, not by guessing; setup-beam version-type:strict fails loud on an unresolvable pin (no silent wrong-toolchain run). phase/129 CI must go green. |
| T-129-02 | Information Disclosure (stale artifact) | broad `-mix-` restore-key | high | mitigate | Replace with a toolchain-hash-scoped restore-key so a `_build`/PLT built under a different toolchain can never be restored (§P1-A). |
| T-129-03 | Denial of Service (broken lane) | matrix-collapse renaming a required job | medium | mitigate | Scope fence: if a matrix edit would change a job `name:`, keep the matrix; display-name literals are branch-protection contract identifiers. |
| T-129-SC | Tampering | npm/pip/cargo installs | low | accept | No package-manager installs in this plan (infra-only YAML + one `.tool-versions` file). No new deps. |
</threat_model>
