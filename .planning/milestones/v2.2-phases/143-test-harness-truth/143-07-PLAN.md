<objective>
Close the two leak classes that are actually red on both gating legs today.

RESEARCH.md's four-leg measurement is unambiguous: `:already_shared` is **absent** from both Elixir 1.18
legs, whose 29 and 12 failures are dominated by `42P01 undefined_table`. Those split into two defects by
relation-name shape — an unqualified `mailglass_deliveries` means the migration baseline is genuinely gone
(**Class A**), and a `mailglass.mailglass_suppressions` miss on the *public* leg means
`Mailglass.Config.schema()` leaked to `"mailglass"` (**Class B**). Class B is also the upstream trigger for
Class C: it is what makes `CitextProbe.run` raise inside the unguarded acquire/release window.

HARNESS-02 cannot be met by fixing Class C alone. This plan is the D-31 amendment made real.

Purpose: three global-state leak classes, one disease — process-global or pool-global state escaping the
module that set it. Classes A and B get the same registered-first discipline Class C got.
Output: a restore-first seam on the sanctioned door, the two culprit modules fixed, and a post-fix local
full-suite run on both axes with zero `:config_schema_drift` and zero `:baseline_missing` violations.
</objective>

  <action>
Make the migration baseline restoration unconditional and verified.

Today the restoration in `migration_test.exs`'s `on_exit` is conditional on `baseline_tables_present?()` —
it restores only if it believes the baseline is missing. The CI evidence says restoration does not always
complete: `Mailglass.MigrationTest` itself has two failures and twenty-two downstream tests then fail on
missing tables, on a cold database created fresh by `mix ecto.create` per run. The seed's ruling-out of this
file was measured locally against an already-restored database and is not binding for CI conditions.

Change the restoration so it:

- Runs unconditionally rather than behind a presence guard. A guard that decides "the baseline looks fine,
  skip the restore" is exactly the "cannot verify, reports green" shape this milestone exists to kill.
- Is registered before any statement in the module's setup that can raise, following the same discipline
  `checkout!/1` and the schema seam use. Reuse `unsandboxed_module/1`'s registered-first placement rather
  than adding a second ordering rule.
- Ends by **verifying** the restore, reusing `SandboxOwnership.baseline_tables_present?/1` rather than
  re-implementing the check. When the post-restore verification is false or `:cannot_verify`, raise a
  composed message naming the relations that are still absent and the command that rebuilds them. Never
  return quietly.

Apply the same treatment to `upgrade_v2_schema_migration_test.exs`'s teardown if the mechanism account names
it, and to whichever module the account named as the Class A culprit if it is neither of these two.

If `baseline_tables_present?/1` needs to grow — for instance to report *which* relations are absent rather
than a bare boolean — change it on `SandboxOwnership` and update plan `143-01`'s formatter call site and its
tests accordingly, keeping the `:cannot_verify` result path intact.

Also address the second recorded failure shape: `migration_test.exs:164`→`:186` asserts no immutability
trigger functions remain and observed one. Read that assertion and its teardown; if the teardown drops the
trigger function conditionally, make that unconditional and verified on the same terms. Do not weaken the
assertion.
  </action>
