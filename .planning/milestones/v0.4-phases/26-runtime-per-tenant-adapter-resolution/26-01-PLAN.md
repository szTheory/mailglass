<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Adopter tenancy callback -> library routing contract | App-owned policy code chooses a route identity that Mailglass will persist and later dispatch through |
| Runtime config -> adapter registry accessors | Application env becomes the trusted set of named transport definitions |
| Database schema -> queued dispatch semantics | Persisted delivery fields become the source of truth for later async retries |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-26-01 | Tampering | tenancy callback output | mitigate | Limit valid callback outcomes to `{:ok, adapter_ref}` and `:default`; treat malformed outputs as typed failures rather than implicit fallback per D-26-07. |
| T-26-02 | Elevation of Privilege | hidden runtime registry state | mitigate | Keep routing state in explicit config accessors only; do not add a process-backed registry or cache per D-26-16. |
| T-26-03 | Repudiation | delivery route intent | mitigate | Persist route identity on `mailglass_deliveries.adapter_ref` instead of ambiguous metadata so queued intent is durable and auditable per D-26-12 and D-26-15a. |
| T-26-04 | Regression | single-tenant defaults | mitigate | Keep the callback optional, keep `config :mailglass, adapter` as the only required default, and pin the zero-config path in tenancy/config tests per D-26-05 and D-26-07a. |
</threat_model>
