<objective>
Create the tenant-safe replay identity seam for Phase 24 by making delivery detail screens resolve to exact raw webhook candidates instead of guessing from delivery ids alone.

Purpose: the current operator UI is delivery-first, but Phase 24 locks replay identity to a single `mailglass_webhook_events` row. Before any replay command or modal can be safe, the codebase needs one canonical resolver and durable future-write linkage from ingest to replay targets.

Output:
- a tenant-scoped replay-target read model
- ingest metadata/linkage that preserves replay identity for future rows
- resolver tests that cover zero/one/many target states, especially SendGrid ambiguity
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Delivery detail context -> replay candidate lookup | User-selected delivery ids cross into tenant-scoped raw webhook lookup |
| Webhook ingest -> ledger metadata | Future-write linkage becomes the durable identity source for later replay decisions |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-24-01 | Elevation of Privilege | replay target resolver | mitigate | Require `tenant_id`, scope every read, and return unavailable/ambiguous states instead of guessing. |
| T-24-02 | Tampering | ingest linkage metadata | mitigate | Write linkage only inside the existing ingest multi path; do not patch ledger rows after insert. |
| T-24-03 | Information Disclosure | historical lookup fallback | mitigate | Do not expose unscoped webhook identifiers or payload excerpts when historical rows cannot be resolved safely. |
| T-24-04 | Integrity | SendGrid batch identity | mitigate | Treat many-candidate cases as explicit selection flows rather than auto-picking one child event. |
</threat_model>
