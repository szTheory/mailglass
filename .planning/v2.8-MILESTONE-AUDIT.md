## The one thing actually blocking closure

> **Revised 2026-09-18 after direct investigation.** The first version of this section repeated the
> diagnosis carried in `166-UAT.md`, `166-POSTMERGE-EVIDENCE.md` and the session memory: *"PR #280
> proposes already-tagged 2.6.0, so preflight short-circuits."* **That diagnosis is wrong on both
> halves.** It was never verified against a run log. The corrected finding is below.

`release-please` is red on **every** run on `main` — push and schedule alike, 23 consecutive failures
as of 2026-09-18T16:27Z. It is not a rate limit (`gh api rate_limit` reads 5000/5000).

### What PR #280 actually is

`#280` proposes **2.6.1 / 2.6.1 / 2.3.0**, not 2.6.0. Its branch manifest reads
`{".": "2.6.1", "mailglass_admin": "2.6.1", "mailglass_inbound": "2.3.0"}`, and **no 2.6.1 tag
exists**. It is a legitimate, correctly-generated proposal for the `fix(release):` commit `7e9617b2`
(#279). It is not stale and it is not bogus.

### The actual mechanism

The preflight step reads the manifest of the **checked-out `main`** — `2.6.0/2.6.0/2.3.0` — and asks
GitHub whether those tags exist. They do, because 2.6.0 shipped and was closed out. So it logs
*"All expected release tags already exist"* and sets `should_run=false` (`release-please.yml:132-136`).

Both evidence-producing steps are gated on that flag:

- `:518` — `Discover an open Release Please proposal before capture`, `if: should_run == 'true'`
- `:603` — `Capture Release Please proposal identity without activation`, same gate

With both skipped, the result writer at `:823-829` finds `DISCOVERY_STATUS` empty, so its override
branch never fires and it falls through to its initialized defaults — `cannot-check` /
`github_evidence_unavailable` — which `:885` then fails the job on.

**This is deterministic and permanent.** `main`'s manifest equals the published tags in the steady
state after *every* completed release close-out, so `should_run` is `false` on every run, so the
proposal control can never produce evidence again. Verified identical on both the push run
(35361151297) and the schedule run (35368608097) at `dcbda58f` — each ran exactly:
`Detect already-tagged release PR → Write proposal-only release control result`, with the
release-please action, discovery and capture all skipped.

### Two consequences that change this audit's verdict

1. **Closing PR #280 would not fix it.** `pending` / `no_open_proposal` is reachable only from the
   discovery step, which does not run. Closing #280 leaves `should_run=false`, leaves discovery
   skipped, and leaves the control at `cannot-check`. It would also discard a valid 2.6.1 proposal.
   The audit's original recommendation to "dispose of #280" is **withdrawn** — it was the wrong
   action for the wrong reason.

2. **Exit criterion 4 is unachievable, not merely unobserved.** CTRL-02 and CTRL-03 are not waiting
   on a release-ceremony decision or on elapsed time. They are blocked by a defect in the control
   they were meant to fix.

### Timeline corroboration

The reds begin exactly at `7e9617b2` (2026-09-17T19:39Z, the first push after 2.6.0 close-out that
carried a shippable commit). The runs immediately before it — `b4dd27f0` 19:06Z and the 2.6.0 tag SHA
`6a0447a9` — were green with `RESULT_STATUS: pending` / `RESULT_REASON: no_open_proposal`, proving the
discovery step *did* report a verdict under the pre-v2.8 workflow. The regression window is the v2.8
change to this file.

### Recommended disposition

This is a code change to a fail-closed release control, so it belongs in a planned phase, not in an
audit and not in an ad-hoc edit. The shape of the fix is narrow and must not weaken the gate: let the
preflight short-circuit still emit a `pending` / a named non-alarm reason for the proposal control, or
un-gate discovery from `should_run` so it can report `no_open_proposal` / `proposal_captured` on its
own. **Do not** make the failing step `continue-on-error` — that is the milestone's own pre-refused
temptation #1 in a new costume.
