# Phase 182: Admin Words and Layout, One Job First - Context

**Gathered:** 2026-11-15 (assumptions mode, four-agent fan-out: codebase analyzer, truthful-status UX/prior-art researcher, verification/review-gate researcher, core-projection/release-impact researcher; conflicts between reports resolved against the code)
**Status:** Ready for planning

<domain>
## Phase Boundary

An operator handling "a customer says the password reset never arrived" gets a truthful answer in brand v2 words through the real dashboard (search by email, find the delivery, read a verdict, "sent is not delivered", a next step), in light, dark and 375px. The same words, time zones and status marks then roll out across every admin screen, without rendering anything the product cannot honestly know. Requirements BRADM-01..07. Plan budget about 5 (milestone cap: 12 plans used by 179-181, 3 left for Phase 183).

**Stop line (milestone):** no new data capture or backend features. No "next try at...", "will retry", or cause text with a nil reason, ever. `Mailglass.Operator.*`, `mailglass_operator_routes`, `:operator_access`, `tenant_id`, `:orphan_backlog`, telemetry names, the `Delivery.status` enum and `deliveries_path` stay (gloss, don't rename).

The single allowed backend touch is the additive operator-projection fields in D-05, which is a read of columns that already exist, not new capture.
</domain>

<decisions>
## Implementation Decisions

### Verdict model and microcopy (BRADM-01, BRADM-06)
- **D-01:** **Five verdicts, one per `StatusMap.delivery_class/1` class** (Sent, Delivered, Delayed, Failed, Not sent). No "probably lost" state (needs an invented age threshold) and no event-level verdicts (events stay in the timeline as evidence). The verdict is computed once, as pure data in `MailglassAdmin.Copy` (word, sentence template, rule line, next step), fed by `delivery_class/1` for the class and by timeline events for the cause. It is rendered by one component used by the Quick view (one-line form) and Full detail (full form). Never computed in HEEx per screen, or list, Quick view and detail drift apart.
- **D-02:** **"Sent is not delivered" lives in every Sent-class verdict, unconditionally.** Verdict shape: mark + word (heading), one sentence, a rule line, then "Next step". Draft strings (planner may tighten for the 375px width, not change the claims):

  | Class | Sentence and rule line | Next step (existing features only) |
  |---|---|---|
  | Sent | "Sent with {provider}. Mailglass has recorded no delivery report for this email." Rule: "Sent is not delivered: your app handed the email to the provider, and the receiving server has not reported accepting it." No provider name: "Sent to the provider." | "Check this address on the suppression list below. Then look up the email in {provider}'s logs, and ask the customer to check spam. Delivery reports reach mailglass only if the provider's webhook is set up." |
  | Delivered | "Delivered at {time}: the receiving server accepted this email." Rule: "Delivered is not the same as read. It may not be in the inbox." | "Ask the customer to check spam and promotions, and to search for the sender address." |
  | Delayed | "Delayed: the receiving server asked to try again later. No final result is recorded yet." No retry time, no "will retry". | "Nothing to do yet. Check this page again later, or see the retry schedule in {provider}'s logs." |
  | Failed | With reason: "Failed: the email did not get through. The provider reported: {reason word}." Without: "Failed: the email did not get through. No reason was recorded for this email." | "Check the address for a typo. See whether it is on the suppression list. Correct it in your app, then send again." |
  | Not sent | "Not sent: nothing was sent. This address is on your suppression list." Add "Reason: {x}." only if the reason exists, else "No reason was recorded for this email." | "Remove this address from the suppression list if it should receive email, then trigger the email from your app again." Links to the existing suppression card. |

  - **Fixed honest fallback sentence: "No reason was recorded for this email."** It is true whether the provider said nothing or mailglass did not capture it, and it cannot be confused with a cause sentence.
  - When opened/clicked events exist, add "Open and click reports are not delivery reports." Engagement never implies delivered and never erases it (179 D-05).
  - Tone: calm maintainer, past tense, "reported", "recorded", "asked". Banned: "successfully", "Oops", "unfortunately", "will", "should arrive". Never render `last_error` (exception text).
  - **Queued** rows read as the Sent class only with the qualifier word "Queued" and the line "Not handed to the provider yet." They never read "Delivered" or imply handoff succeeded (179 D-03). "Dispatched" becomes "Sent with {Provider}".
  - "Not sent" is for suppression only; a send-time `:failed` reads Failed (179 D-06).
- **D-03:** **The brand book's own example sentences conflict with the stop line and lose.** `brandbook/v2/brand.json` says Delayed means "The provider will retry" (lines 256, 720), Failed "will not be retried" (263, 725), and gives "Next try at 2:12 PM UTC" (649). `Copy` takes only the book's status *words* (Sent, Delivered, Delayed, Failed, Not sent), never those sentences. The BRADM-07 reviewer is told the stop line wins over the book on these strings. Feeding the correction back to the book repo is a deferred idea, not this phase's work.
- **D-04:** **Cause text is structural, not just filtered.** `Copy.cause_sentence/1` is generated by comprehension over the `reject_reason` enum (7 values) plus the suppression-reason enum with **no `nil` clause**, so rendering a cause for nil raises in tests. `Copy.cause_or_fallback/1` returns the D-02 fallback for nil. Also fix the tooltips that promise a cause that may not exist: `components.ex` `outcome_help` (~1433-1442: "Open the delivery to inspect the bounce reason", "inspect the recorded reason", "inspect the error") must be conditional on the reason existing, else say what is recorded. The suppression card's nil `Reason` currently prints "Unavailable" (`suppression_card.ex:69-72,133-139`); it takes the fixed fallback instead. Clean the gallery fixtures that say "retry window" (`gallery_live.ex:683,728`).

### Projection hand-off (Phase 179 hand-off, BRADM-01)
- **D-05:** **Do the additive core change; do not settle for showing the limitation.** On the three-field operator row a bounce followed by an open reads "Delivered" today (`delivery_display_status` returns `:opened`, `operator_live.ex:2742-2746` buckets it as Delivered), so the headline card for this job is wrong. Add to `Mailglass.Operator.Deliveries.delivery_projection/1` (`lib/mailglass/operator/deliveries.ex:119-134`, called by `list_recent_deliveries_page/2` and `get_delivery/2`): **`bounced_at`, `terminal`, `delivered_at`, `complained_at`, `suppressed_at`**. Keep `delivery_confirmed`. Reason for five (not the roadmap's two): the projector latches `terminal` on delivered, bounced, complained, rejected, failed and suppressed (`projector.ex:48,126-132`), and `StatusMap.durable_failure?/2` (`status_map.ex:151-155`) reads `complained_at`/`suppressed_at` to tell a failure from a complaint; with only two fields a complaint with no delivery would read Failed, a new false verdict. Do **not** add `failed_at`/`rejected_at` (no such columns, would be new capture), `last_error` or `reject_reason` (INSIGHT-01..03).
  - Extend the `outcome_groups` query (`deliveries.ex:70-83`) `group_by`/`select` with boolean forms (`not is_nil(bounced_at)`, `terminal`, complained, suppressed) so the summary counts agree with the row marks.
  - **Placement and release:** Plan 1, its own isolated commit (`feat(core):` unless the repo's scope list says otherwise; planner verifies against the PR-title check), with the core test in a **new** core file (`config/test_exceptions.exs` is file:line keyed; it runs in the required `core_deterministic_suite`). It is a shippable kind, but release PR #325 (2.8.0 linked) is already open from earlier `feat(admin):` commits, so it adds one changelog line and no new ledger interaction. Do not hand-edit `.planning/release-target.json`.
  - **Tests:** (1) DB-backed: seed `bounced_at`, `terminal: true`, `last_event_type: :opened`; both read functions return the real values and `outcome_groups` has a bounced+opened group not merged with ordinary opened rows. (2) Replace the pinned "operator row limitation" test (`mailglass_admin/test/mailglass_admin/status_map_test.exs` ~326-335) so a real projection row for bounce then open gives `delivery_class/1 == :failed`. (3) Mutation-proven contract test over bounce→open, bounce→click, rejected→open, delivered→bounce; dropping `bounced_at`, then `terminal`, from the select must each fail it, evidence recorded in the plan summary. (4) Additive-only guard that old keys remain (do not pin the exact key set).
  - **Docs:** add to `docs/api_stability.md` and `mailglass_admin/docs/api_stability.md` "operator read-model maps may gain keys in a minor release; match on the keys you use, not the whole map". Delete the "limitation" comment in `status_map.ex:43-48`.
- **D-06:** **Admin degrades honestly when keys are absent.** The published admin pins `{:mailglass, "~> 2.0"}` (`mailglass_admin/mix.exs:150-155`) and path deps hide the mismatch locally, so admin 2.8 can resolve against core 2.7. Gate the verdict on `Map.has_key?(row, :bounced_at)`; if absent, render no verdict and say "Status cannot be fully determined with this mailglass version." (never the old confident "Sent"). A test renders a three-field row. Tightening the published pin to `~> 2.8` is a separate `chore`/`build` commit, flagged as a deferred idea; do not bundle it.
- **D-07:** **"Needs attention" stays a summary count plus row marks, not a filter (owner-vetoable default).** Today it is a count-only `stat_card` (`operator_live.ex:997-1026`, bucketing at 2738-2773). A clickable bucket filter needs a new server-side query parameter in core (pagination lives in `list_recent_deliveries_page/2`), which is new public API and outside a words-and-layout phase. Re-bucket the summary by `delivery_class/1`: Needs attention = Failed + Delayed + Not sent; Delivered = Delivered; Awaiting = Sent (including Queued). `:complained`/`:unsubscribed` leave Needs attention (not delivery statuses, 179 D-03). Success criterion 1's "finds the delivery under Needs attention" is satisfied by: search narrows to the recipient's rows, the row carries a Failed/Delayed/Not sent mark+word, and the summary count includes it. Sent is never in Needs attention (no honest age rule). A server-side filter is a later core change (deferred).

### Time and status marks everywhere (BRADM-02)
- **D-08:** **Server renders "H:MM AM/PM UTC"-style absolute time with its zone; the browser upgrade keeps the zone.** The localizer is live (`controllers/assets.ex:105-135`, pinned by e2e `operator.spec.js:713-720`, `flows.spec.js`) and currently formats with `toLocaleString(undefined, {year, month, day, hour, minute})` and **no `timeZoneName`**, so after JS runs every `<time>` shows a bare local time ("Nov 15, 2026, 2:21 AM"). A server-render-only scan would pass while the real screen fails. Fix: add `timeZoneName: "short"` and a fixed `"en-US"` locale to `FMT`, and stop overwriting `aria-label` with text that omits the visible text (WCAG 2.5.3 Label in Name; the copy button's `aria-label` "Copy timestamp as UTC: ..." has the same defect). Keep `datetime` as ISO Z, keep the exact UTC value in the tooltip/copy value, no relative times on timelines or lists. At 375px the zone sits under the time (`block` below `sm:`), per the book. `Components.timestamp/1`'s docstring (`components.ex:1512-1513`) is corrected to match.
- **D-09:** **Every time is a `Components.timestamp`.** Offenders to fix: `operator/timeline.ex:170,222` (raw `provider_occurred_at` metadata string: parse to a datetime and render through `timestamp`, or if unparseable show it labelled as the provider's raw value, never as a bare time), `operator/support_cards.ex:385,388` (`DateTime.to_iso8601(at) <> " UTC"` gives "...Z UTC"), `results_status.ex:38` (`%H:%M UTC`, already has zone, route through the helper if cheap), `preview_live.ex:1184` (sample email Date header, allow-listed by name). Remove the `title` attribute from `copy_value`/timestamp; accessible text only.
- **D-10:** **Status = pane mark + word, only through `status_badge`.** The mark is `aria-hidden="true"` (no `aria-label`, no `title`), the word is the accessible name and equals the `Copy` class label. Marks in the five book silhouettes (check, triangle, cross, slash-circle, outbound arrow) must differ in greyscale and keep 3:1 against the pane in light and dark; word colour uses the book `textLight`/`textDark` pairs (4.5:1). Pane marks replace the heroicon on **delivery-class badges only**; event/non-delivery atoms (opened, replay, inbound outcomes) keep word badges with their current icons (analyzer assumption, Likely). **Provenance:** the marks are not standalone files in the pinned zip; they exist only as inline `<svg class="stm">` fragments in `mailglass-brand-book.html`. Record the path data once in a small pinned file (`brandbook/v2/status-marks.json`, with the source book-HTML sha256 and the zip sha), extracted by a script step, and a required-lane test asserts the component's path data equals it; the byte-check against the zip itself is advisory, like Phase 179 D-19. Planner chooses the exact file layout.
