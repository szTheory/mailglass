# Phase 999.2 Research: Shift-Left Email Screenshot + Responsive Preview Workflow

## Summary

Phase 999.2 is plan-ready. The repo already has the core ingredients for this workflow:

- one canonical render truth source (`MailglassAdmin.PreviewLive` -> `Mailglass.Renderer.render/1`),
- an existing responsive matrix (`375`, `768`, `1024`) plus chrome theme toggle,
- scenario discovery through `preview_props/0`,
- CI/browser orchestration patterns, deterministic fixture patterns, and artifact-writing conventions.

The best planning default is a **no-new-Node** capture workflow:

1. add deterministic URL-driven preview state (`scenario`, `width`, `theme`) to `PreviewLive`,
2. add a `mix` task in `mailglass_admin` that captures screenshots via headless Chromium CLI,
3. emit a deterministic manifest/checkpoint JSON beside image artifacts,
4. wire a CI **advisory** artifact lane (not required branch protection).

This aligns with the phase context (D-01..D-08), keeps claims honest (preview-pipeline confidence, not client parity), and avoids widening runtime/public API surface.

- Project-level intent: avoid introducing new Node toolchain requirements.
- Claims must stay bounded and honest: preview screenshot confidence is not provider client parity.
- Keep workflow at admin/tooling surface, not new `mailglass` runtime API.

## Implementation Options

### Option A: No-Node Chromium CLI capture task (recommended)

**Shape**

- Extend `PreviewLive` to accept deterministic URL params for width/theme.
- Add `mix mailglass_admin.preview.capture`:
  - discovers scenarios via existing discovery pipeline,
  - builds matrix (scenario x width x theme),
  - calls headless Chromium (`--headless --screenshot --window-size --virtual-time-budget`) for each URL,
  - writes PNGs + deterministic manifest JSON (`scenario`, `width`, `theme`, file path, sha256, timestamp metadata, browser version).

**Pros**

- Fits no-new-Node direction.
- Reuses shipped preview truth source and existing matrix.
- Works for local and CI with one command.
- Keeps output as trust artifact/checkpoint (D-06).

**Cons**

- Requires browser binary availability management (local + CI).
- CLI screenshot ergonomics are less rich than Playwright visual tooling.

### Option B: Playwright visual snapshots on preview route

**Shape**

- Add preview-focused Playwright spec with `toHaveScreenshot` for each matrix case.
- Use built-in flake controls (`animations: "disabled"`, `caret: "hide"`, masking).

**Pros**

- Mature visual diff tooling.
- Existing repo already has Playwright lane and config.

**Cons**

- Expands Node dependence for this phase goal.
- Snapshot maintenance across environments is operationally heavier.
- Conflicts with "no Node toolchain" preference unless explicitly accepted.

### Option C: Manifest-only render evidence (no browser screenshots)

**Shape**

- Generate render matrix + metadata only (scenario/width/theme/html hash), no PNGs.

**Pros**

- Lowest complexity, fully deterministic, no browser setup.

**Cons**

- Does not meet "realistic rendered example emails" intent well.
- Misses responsive visual regressions.

## Recommended Approach

Use **Option A** with a staged rollout that keeps scope tight and reversible.

### Stage 1: Deterministic capture state in PreviewLive

- Add URL-param parsing in `handle_params/3` for:
  - `width` (`375|768|1024`),
  - `theme` (`light|dark`).
- Ensure invalid params fall back safely to defaults.
- Keep this internal and non-contractual (no new public API promise).

### Stage 2: Capture task + artifact contract

- Add `mix mailglass_admin.preview.capture` with strict options:
  - `--base-url`,
  - `--output-dir`,
  - `--mailables` (optional explicit list),
  - `--theme` (`light|dark|both`),
  - `--widths` (default `375,768,1024`),
  - `--dry-run`.
- Produce deterministic filenames and a sorted `manifest.json`.
- Include explicit claim text in task output/docs: "preview-pipeline confidence only."

### Stage 3: CI advisory artifact lane

- Add CI job that:
  - boots a deterministic preview host,
  - runs capture task,
  - uploads artifact bundle (`images + manifest`).
- Keep advisory (non-branch-protection) at first, consistent with current browser-lane posture.

### Stage 4 (optional, defer until needed): Diff gate strategy

- If confidence needs increase, add a baseline manifest or visual diff mode as a separate slice.
- Do not combine first implementation with mandatory screenshot diff gating.

## Risks and Mitigations

- **Risk: Flaky captures from timing/animation drift.**  
  Mitigation: fixed viewport, virtual-time budget, deterministic seed data, disable dynamic UI motion where needed.

- **Risk: Non-determinism from preview internals (Message-ID/Date on non-HTML tabs).**  
  Mitigation: default capture scope to HTML tab only; avoid raw/header visuals in baseline matrix.

- **Risk: Cross-OS rendering differences (fonts/subpixel).**  
  Mitigation: one canonical CI environment for trust artifacts; treat local output as convenience.

- **Risk: Scope creep into client-parity promises.**  
  Mitigation: docs and manifest metadata explicitly state bounded claim (Chromium preview only).

- **Risk: CI noise and artifact bloat.**  
  Mitigation: matrix caps, naming contract, artifact retention policy, advisory gate first.

- **Risk: Hidden Node creep via tooling choices.**  
  Mitigation: prefer Chromium CLI path; keep Playwright option explicitly non-default.

## Validation Architecture

### Layer 1: URL/state contract tests

- Extend `mailglass_admin/test/mailglass_admin/preview_live_test.exs`:
  - valid width/theme params apply correctly,
  - invalid params fall back to defaults,
  - scenario rendering still uses existing flow.

### Layer 2: Mix task contract tests

- Add `mailglass_admin/test/mix/tasks/mailglass_admin.preview.capture_test.exs`:
  - CLI option validation and error messages,
  - dry-run matrix generation,
  - deterministic filename ordering.

### Layer 3: Determinism check

- Execute task twice in same environment and compare produced `manifest.json` entries/hashes.
- Fail if matrix cardinality or identity set drifts unexpectedly.

### Layer 4: CI artifact check

- CI lane must always produce:
  - non-empty screenshot directory,
  - manifest with schema/version and capture metadata,
  - upload artifact success.

### Layer 5: Claim-boundary checks

- Docs/test wording checks should prevent "client parity" language from creeping into this workflow.
- Keep this as preview confidence evidence only.
