# Phase 999.2: Shift-Left Email Screenshot + Responsive Preview Workflow (BACKLOG) - Context

**Gathered:** 2026-05-27 (assumptions mode)
**Status:** Ready for planning

<domain>
## Phase Boundary

Make it easy, at any time, to inspect realistic rendered example emails across responsive widths and theme presentation through a low-friction workflow (task, preview pipeline, and/or CI artifact path) that builds on existing preview infrastructure.

This phase improves confidence workflow ergonomics. It does not add a new mail rendering engine, broaden provider/client rendering guarantees, or absorb unrelated post-publish smoke dependency debt.

</domain>

<decisions>
## Implementation Decisions

### Workflow entry surface
- **D-01:** Introduce the screenshot/responsive workflow at the admin/tooling surface (mix task and CI orchestration), not as a new `mailglass` core runtime API.
- **D-02:** Keep workflow integration aligned with existing cross-package task orchestration patterns in root aliases and admin package tasks.

### Render truth source
- **D-03:** Capture screenshots from the existing `MailglassAdmin.PreviewLive` path so artifacts reflect the same render pipeline adopters use in `/dev/mail`.

### Responsive and scenario matrix
- **D-04:** First implementation pass uses existing width controls (`375`, `768`, `1024`) and existing preview chrome theme toggle.
- **D-05:** Email content variants are driven by existing mailable `preview_props/0` scenarios; no new rendering capability is added in this phase.

### Deterministic artifact contract
- **D-06:** Treat outputs as deterministic trust artifacts (manifest/checkpoint evidence), not ad hoc local screenshots.
- **D-07:** Bound claims explicitly: Chromium preview captures prove regression confidence for the preview pipeline, not cross-client parity (for example Outlook/Gmail production client behavior).
- **D-08:** CI capture path should run in one canonical, pinned environment with flake controls (stable browser/runtime versions, deterministic capture settings, and reduced timing variance).

### Claude's Discretion
- Exact command/task naming and whether orchestration lives at root or inside `mailglass_admin`, as long as adopter entry is low-friction.
- Exact artifact packaging (file names, directory shape, manifest format) as long as outputs are deterministic and CI-consumable.
- Exact diff/assert strategy (baseline snapshots vs manifest-only checkpoint contract) as long as scope remains bounded to preview-pipeline confidence.

</decisions>

- `MailglassAdmin.PreviewLive` event/model flow already supports scenario selection, rerendering, dark toggle, and responsive width switching.
- `MailglassAdmin.Preview.*` components already encode responsive controls and HTML iframe rendering.
- `MailglassAdmin.Preview.Discovery` + `Mailglass.Mailable.preview_props/0` already provide a structured scenario matrix source.
- Existing CI browser lane and operator browser server setup provide a usable automation harness for deterministic screenshot capture.

### Established Patterns
- Trust claims in this repo are expected to be backed by deterministic artifacts and executable checks, not prose-only assertions.
- Public seam boundaries are explicit and protected; workflow additions should layer on stable routes/tasks instead of introducing new core APIs.
- Scope discipline is strict: related debt is tracked and referenced, but not absorbed into unrelated phase delivery.

### Integration Points
- Preview capture should anchor on `/dev/mail` routes provided by `MailglassAdmin.Router`.
- Screenshot workflow should connect to existing CI/browser infrastructure instead of introducing a parallel automation stack.
- Artifact outputs should plug into current trust-proof evidence posture used by reference-host scope and contract tests.

</code_context>
