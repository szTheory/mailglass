    The operator guide is the production operations manual for `mailglass_inbound`. It covers:

    **Section: mix mailglass.inbound.doctor**
    - Purpose: DNS-free pre-deploy config validation; exit-coded for CI
    - Flags: --strict (warn→fail), --format json (machine-readable), --verbose (show route list)
    - Exit codes: 0 (all pass), 1 (failure or warn+strict), 2 (cannot diagnose — no router)
    - What it checks: routes compile, no conflicts, mailboxes exist + implement process/1,
      provider signing keys configured (presence only, never verifies a signature), MIME backend
    - Example CI usage: `mix mailglass.inbound.doctor --strict --format json`

    **Section: mix mailglass.inbound.replay**
    - Purpose: CLI surface over the replay engine; appends ExecutionRun with source: :replay
    - --tenant <id> is REQUIRED (cross-tenant replay guard — a foreign-tenant record-id
      resolves to nothing, not a cross-tenant replay)
    - --record-id <uuid>: replay a specific record
    - --since <iso8601>: replay all records since a timestamp (within --tenant scope)
    - --yes / -y: skip confirmation prompt
    - --dry-run: report scope without replaying
    - Confirmation tier: simple [y/N] defaulting to No (non-destructive — replay appends rows)

    **Section: mix mailglass.inbound.prune**
    - Purpose: enforce retention policy; deletes in batches of 1000 under advisory lock
    - --yes / -y: skip confirmation
    - --dry-run: report scope without deleting
    - Typed "yes" confirmation required (DELETES rows — stronger gate than replay's [y/N])
    - Scheduled pruning: MailglassInbound.Prune.Worker is NOT auto-registered; adopter wires
      `{MailglassInbound.Prune.Worker, cron: "0 3 * * *"}` in their Oban config; Oban-less
      adopters run this from system cron

    **Section: Retention Policy Configuration**
    - The four retention windows with their defaults and :infinity option
    - FK-lineage invariant: records_days >= evidence_days >= max(execution_runs_days, replay_runs_days)
    - Config example in runtime.exs

    **Section: Rate-Limit Configuration**
    - Three buckets: tenant (1000/min default), recipient (500/min), sender_domain (200/min)
    - Bucket evaluation order: tenant → recipient → sender_domain (fail-fast)
    - HTTP 429 + Retry-After on trip; no `:transactional` bypass
    - Config example

    **Section: Suppression Flag Interpretation**
    - Suppressed senders are flagged, not auto-bounced
    - InboundRecord.suppression_flagged: true is visible in the admin LiveView
    - Rationale: preserves diagnostic signal for forwarders, complaint replies, and
      false-positive recovery — the mailbox callback decides whether to :reject or process
    - The :suppression_flagged key is in InboundMessage.metadata
