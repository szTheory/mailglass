  <behavior>
    The routing-debug guide answers the question: "I sent an email but my mailbox didn't process
    it — why?" It covers three investigation paths and common failure modes.

    **Section: Starting Point — the Routing-Trace Card**
    - In mailglass_admin, open the failing InboundRecord's detail view
    - The routing-trace card shows every route that was attempted and which clause failed
    - Example: "Route 1 (SupportMailbox): recipient ✓ — subject_header FAILED (expected 'Support',
      got 'Re: Billing Question')"
    - Reading pass/fail: green checkmarks pass, red X marks fail — the FIRST failing clause
      ends the attempt for that route

    **Section: Common Failure Mode 1 — Header AND-Semantics**
    - ALL conditions in a route must match. A route with both a `recipient:` and a `subject_header:`
      condition requires BOTH to match (not either/or)
    - Example (the confusion): "I have `route "support@*", with: [subject_header: "Support"],
      MyApp.SupportMailbox` — why doesn't 'Re: Billing Question to support@example.com' match?"
    - Fix: split into two routes (one for `subject_header:`, one without) if either condition alone
      should trigger the mailbox

    **Section: Common Failure Mode 2 — Regex vs Exact Match**
    - `"support@example.com"` is an exact string match (case-sensitive)
    - `~r/support@/` is a regex pattern (case-sensitive by default; use `~r/support@/i` for case-insensitive)
    - Wildcard glob `"support@*"` uses the router's glob semantics (not regex) — `*` matches the whole domain
    - Example confusion: `"support@example.com"` doesn't match `"Support@Example.com"` (different case)

    **Section: Common Failure Mode 3 — Envelope vs To: Header**
    - The route pattern matches against the SMTP envelope recipient (the `RCPT TO:` address),
      NOT the `To:` header in the message body
    - Forwarding rules can change the envelope while preserving the `To:` header, making them appear
      identical in the email client but different to the router
    - InboundLive detail view shows both the envelope recipient and the To: header for comparison

    **Section: CLI Inspection**
    - `mix mailglass.inbound.doctor --verbose` lists all compiled routes (no DB needed)
    - IEx introspection: `MyApp.MailglassInboundRouter.__mailglass_inbound_routes__/0` returns the
      compile-time route list

    **Section: Worked Example — Full Debug Session**
    This must be a fully-narrated trace (not a list of tips). Example scenario:
    - Symptom: `support@mg.example.com` emails arrive in InboundLive with outcome `:no_match`
    - Router has: `route "support@example.com", MyApp.SupportMailbox`
    - Step 1: open InboundRecord in InboundLive → routing-trace card shows "Route 1 (SupportMailbox): recipient FAILED"
    - Step 2: hover over the recipient diff → expected `"support@example.com"`, got `"support@mg.example.com"`
    - Root cause: Mailgun routes deliver to the subdomain MX address (`mg.example.com`), not the main domain
    - Fix: change route pattern to `"support@mg.example.com"` or use wildcard `"support@*"`
    - After fix: re-replay the record from InboundLive replay modal → outcome `:accept`

    Footer: links to inbound-install.md, inbound-operator.md, and inbound-mailgun.md
  </behavior>
