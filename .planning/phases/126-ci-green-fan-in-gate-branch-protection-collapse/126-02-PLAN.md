<objective>
Close the release-SHA hole and the two GATE-04 latent-staleness bugs. On the publish path, a `skipped`
required lane must NOT count as green (a `docs(state):` release commit path-skips CI, and a required lane
that skips would be blessed green today). And the two "stale default" traps — `gate-self-test.yml`
polling a gate name that no longer exists, and `guard-release-trigger` needing to always report now that
it is a required context — get fixed and locked.

Purpose: GATE-02 makes the publish gate re-assert that each required lane actually EXECUTED with success
(the PR-path `CI Green` tolerates `skipped` by design; the release SHA must not). GATE-04 removes the
stale `"Tests ("` self-test default (so the self-test proves the REAL gate) and adds an executable
invariant so `Guard Release Trigger` — newly a required branch-protection context — can never silently
stop reporting and stick a PR "Expected".

Output: A `REQUIRED_LANES` set + required-lane-must-be-success check in `publish-hex.yml gate-ci-green`;
`gate-self-test.yml` defaulting to `CI Green` with gate-agnostic copy; and a new
`guard_release_trigger_test.exs` invariant.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| release/tag SHA → publish gate | A required lane that path-skips on the release commit would be blessed green and publish a broken release; the gate must re-assert each required lane executed with success. |
| required `REQUIRED_LANES` set (publish-hex.yml) ↔ `ci-green.needs` (ci.yml) | Two independently-editable copies of the required-lane set; drift lets a lane skip on a release SHA and still publish. |
| `Guard Release Trigger` required context → every PR | As a required context it must post a status on every PR; a path filter would leave some PRs stuck "Expected". |
