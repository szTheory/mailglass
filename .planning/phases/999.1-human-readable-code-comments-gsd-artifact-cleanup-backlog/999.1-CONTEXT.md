# Phase 999.1: Human-Readable Code Comments + GSD Artifact Cleanup (BACKLOG) - Context

**Gathered:** 2026-05-27 (assumptions mode)
**Status:** Ready for planning

<domain>
## Phase Boundary

Reduce distracting internal planning references in code comments (for example `D-20`, `Phase N`, `Plan N`, and similar GSD artifact text) so source code reads clearly for maintainers, while preserving the architectural and safety intent those comments currently carry.

This phase is comment readability and maintainability work. It does not add new runtime features or broaden milestone scope.

</domain>

<decisions>
## Implementation Decisions

### Cleanup scope
- **D-01:** Primary cleanup scope is production source comments in `lib/`, `mailglass_admin/lib/`, and `mailglass_inbound/lib/`, where planning-ID density is highest.
- **D-02:** Test/comment cleanup is secondary and selective: only comments that act like maintainer guidance are rewritten in this phase.

### Comment rewrite policy
- **D-03:** Replace planning artifact references (`D-*`, `Phase *`, `Plan *`, `[ASSUMED ...]`) with plain-language rationale anchored to behavior, module names, or stable docs paths.
- **D-04:** Preserve explanatory value; do not strip comments that describe load-bearing invariants.

### Invariant preservation
- **D-05:** Keep explicit comments for security and correctness invariants (for example verify-before-tenant order, adapter call outside transactions, PII-safe telemetry/logging discipline, append-only event semantics), but rewrite them without planning shorthand.

### Drift prevention
- **D-06:** Add or extend a lightweight enforcement guard so new planning-ID artifact comments do not re-enter source after cleanup.

### Scope boundaries and todo handling
- **D-07:** Existing post-publish smoke reliability debt remains out of scope for this phase and is not folded into 999.1 implementation work.

### Claude's Discretion
- Choose the exact banned-pattern set and enforcement point for comment-artifact drift prevention.
- Choose rollout order (single pass vs package-by-package) as long as behavior-impact risk remains near zero.
- Choose which low-value comments to delete entirely versus rewrite when they provide no durable architectural value.

</decisions>
