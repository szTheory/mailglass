# 999.1 Focused Code Review

## Findings

1. **High - Unscoped dependency churn in `8c622ea` introduces upgrade risk outside phase intent**
   - Commit `fix(999.1-01): unblock verification gates for execution run` includes a broad `mix.lock` refresh alongside a comment tweak.
   - The lockfile change upgrades many packages (including major jumps such as `decimal` `2.3.0 -> 3.1.0`, `ecto` `3.13.5 -> 3.14.0`, and `sigra` `0.2.5 -> 1.20.0`) without corresponding `mix.exs` intent changes in this phase.
   - For a comment-cleanup phase, this materially expands regression surface (runtime behavior, compatibility, and release reproducibility) and should be isolated or explicitly justified with dedicated verification evidence.

2. **Medium - `NoPlanningArtifactComments` can be bypassed by inline comments**
   - In `credo_checks/no_planning_artifact_comments.ex`, `collect_comment_surfaces/1` only captures lines where the first non-whitespace character is `#`.
   - Inline comments after code (for example, `def run, do: :ok # Phase 50`) are not scanned, allowing planning tokens through.
   - Verified locally via probe:
     - `mix run -e '{:ok, _} = Application.ensure_all_started(:credo); ... "def run, do: :ok # Phase 50" ...'`
     - Result: `0` issues returned.

3. **Low - Multiple comment/docstring rewrites became less readable or semantically degraded**
   - Several rewrites replaced planning tokens with empty fragments, producing confusing prose rather than behavior-first explanations.
   - Representative examples now present in source:
     - `lib/mailglass/config.ex`: `Required from + onwards.`
     - `lib/mailglass/config.ex`: `'s ingest_multi/3 runtime-guards...`
     - `lib/mailglass/errors/signature_error.ex`: `retained until  consolidates`
     - `lib/mailglass/events/reconciler.ex`: repeated empty parenthetical references and truncated ownership text.
   - This is not a runtime defect by itself, but it is a regression against the phase's human-readable-comment objective and maintainability goals.

## Open Questions

- Was the large `mix.lock` refresh in `8c622ea` intentional scope for phase `999.1`, or should it be split into a dedicated dependency update change with its own verification trail?
- Should `NoPlanningArtifactComments` treat inline comments as in-scope by policy (recommended), or only full-line comments/docstrings?
- Is there an accepted cleanup pass planned for malformed prose introduced during token stripping, or should this phase remain open until comments are readable end-to-end?

## Test Gaps

- No test currently asserts that inline comments are flagged by `NoPlanningArtifactComments` (only full-line `#` comments and docstrings are covered).
- No automated check currently guards against malformed cleanup artifacts (for example dangling `"'s"`, `"+"`, empty `()`/blank reference placeholders) in source comments/docstrings.
- The dependency churn in `mix.lock` lacks dedicated compatibility evidence in this phase scope (for example focused smoke suite for Ecto/Oban/Swoosh-sensitive paths).
