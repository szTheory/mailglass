This order front-loads ingress/security and telemetry invariants before broad cleanup passes.

### Wording style to preserve

- Use direct causal language: "X is done before Y to prevent Z."
- Keep comments behavior-anchored: module/function/invariant names, not planning chronology.
- Mention degraded path explicitly when relevant (`no-op`, `fail closed`, `defer to runtime guard`).
- For operator-facing notes, keep them short and action-oriented ("run command X", "selection resets", "payload is redacted").
- Prefer stable anchors (`docs/api_stability.md`, specific behavior callbacks) over temporary project artifacts.

### Anti-patterns to avoid

- Planning provenance in comments: `D-*`, `Phase *`, `Plan *`, `[ASSUMED ...]`, "landed in Plan N".
- Historical implementation narration that does not explain current behavior.
- "Magic" comments without consequence ("important", "critical") unless they state the failure mode.
- Deleting invariant comments during cleanup because they look verbose.
- Replacing precise invariants with vague summaries ("security checks happen here").
- Embedding mutable workflow jargon in public docstrings.

## 4) Transformation Heuristics for Plan Tasks

- **Rewrite, do not strip** when a comment explains order, security boundaries, idempotency, replay semantics, tenant scoping, or PII policy.
- **Strip entirely** when a comment is only provenance and adds no present-tense behavior rationale.
- **Split long comments** into:
  - invariant statement,
  - why it exists,
  - fallback/operator outcome.
- **Prefer one-sentence headers** for dense sections; move detail to short bullets in moduledocs when needed.
- **Preserve error-contract language** (typed error structs, "match struct not string") even when removing planning tags.
