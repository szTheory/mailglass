## Rewrite Policy Recommendations

### Rewrite

- Replace planning references with stable behavioral rationale:
  - `D-20` -> "adapter call stays outside DB transaction to avoid pool starvation"
  - `Phase 4` / `Plan 06` -> concrete module/function name and purpose
  - `[ASSUMED — ...]` -> explicit current rule or remove if obsolete
- Prefer these anchors:
  - module/function names (`Mailglass.Webhook.Ingest.ingest_multi/3`)
  - invariant descriptions ("verify before tenant resolution")
  - stable docs paths when needed (`docs/api_stability.md`, `guides/...`)

### Keep

- Comments that carry security, correctness, or operational invariants.
- References to external standards and real protocol constraints (RFCs, provider semantics).
- Error-contract and API-stability wording that users rely on.

### Remove

- Pure planning provenance breadcrumbs that do not explain behavior ("landed in Plan XX", "from Phase YY").
- "Forward ship" notes that reference already-shipped phase chronology instead of current mechanism.
- Historical implementation breadcrumbs where current code is self-evident.

### Special Cases / False Positives

- Preserve intentional string fixtures used by checks/tests (for example stale-token literals in `lib/mix/tasks/mailglass.docs.check.ex`) even if they include `Phase` text.
- Do not blanket-remove tokens inside data tables that are themselves enforcement inputs.

## Drift-Prevention Options

### Option A: New Credo check (recommended)

- Add `credo_checks/no_planning_artifact_comments.ex`.
- Register in `.credo.exs` `extra_checks` with path scope:
  - `lib/`
  - `mailglass_admin/lib/`
  - `mailglass_inbound/lib/`
- Check behavior:
  - detect banned planning tokens in comments/docstrings
  - allow configurable allowlist for intentional literals
  - fail with actionable message pointing to rewrite policy

**Why this is best:** it fits existing invariant-at-lint-time culture, runs in current `mix credo --strict` gates, and prevents reintroduction continuously instead of only during docs-specific checks.

### Option B: Extend `mix mailglass.docs.check`

- Add source-file scanning mode to existing task.
- Pro: minimal new surface.
- Con: currently wired to docs lanes; weaker coverage than Credo unless aliases/CI are expanded.

### Option C: Contract test (`rg`-based)

- Add explicit ExUnit contract test asserting no banned planning patterns in scoped source files.
- Pro: easy to reason about.
- Con: overlaps lint responsibility and can be noisier to maintain.

### Recommended enforcement placement

- Primary: **Option A** in `credo_checks/` + `.credo.exs`.
- Secondary (optional hardening): keep `mix mailglass.docs.check` docs-only for Tier 1 docs as-is.

## Risks and Mitigations

- **Risk:** deleting load-bearing context while stripping IDs.
  - **Mitigation:** enforce invariant checklist per file review; "rewrite before delete" for safety comments.
- **Risk:** large PR churn causes merge conflicts.
  - **Mitigation:** execute in waves by package/hotspot density; keep each wave reviewable.
- **Risk:** guard false positives on intentional literals.
  - **Mitigation:** explicit allowlist/exclusions; start warning-only locally, then enforce.
- **Risk:** behavior drift hidden in comment-only PR.
  - **Mitigation:** no logic edits policy + compile/test verification after every wave.
- **Risk:** inconsistent tone across sibling packages.
  - **Mitigation:** single rewrite rubric and examples applied package-wide.
