# Phase 171 — UI Design Contract

> Visual and interaction contract for the Developer Preview. Generated by gsd-ui-researcher; checker and post-verification UI-consideration probe complete the workflow.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | Manual — existing Mailglass Admin design system; no shadcn |
| Preset | Not applicable |
| Component library | Phoenix.Component / HEEx; Tailwind v4 + vendored daisyUI utilities |
| Icon library | Vendored Heroicons Tailwind plugin, rendered inline |
| Font | Inter for UI/body; Inter Tight for headings; IBM Plex Mono for identifiers/code |

Continue the existing LiveView/HEEx and prebuilt asset model. Use semantic theme tokens and the existing Preview modules and shared components. Do not add a frontend framework, component registry, client-JS build, dependency, or competing stylesheet. Keep the Mailglass sealed-flap identity, borders-first flat surfaces, and current reduced-motion behavior. No gradients, glassmorphism, bevels, or decorative noise.

The page remains a developer workbench: the selected Mailable and named scenario orient the author; the current rendered output is the primary visual anchor and work area, with editable scenario inputs supporting it; framing controls stay secondary. Keep the selected scenario legible when the existing compact picker is closed on narrow screens. Reuse its mobile disclosure rather than adding a second sidebar.

**Truth and host boundaries:** call the result renderer output from `Mailglass.Renderer` (the content-rendering stage also used by outbound preflight). Do not imply that output equals provider-bound bytes or final recipient rendering. HTML and plaintext are renderer outputs; Raw is a best-effort MIME-shaped preview envelope, not serialized wire output. Identify generated Message-ID and Date as preview values. State that Preview does not call `Outbound.deliver/2` and has no send action. The browser frame and its backdrop do not certify Gmail, Outlook, Apple Mail, dark-mode support, or other email-client behavior.

The adopter owns the development-only route guard: `mailglass_admin_routes/2` does not enforce development mode or add preview authorization. Recommend synthetic, non-sensitive preview assigns. Captures can contain sensitive data; remote image URLs in rendered HTML may cause browser requests. Disabled iframe scripts are not HTML sanitization or a network/privacy boundary. Do not promise isolation or change supported same-origin/resource behavior without demonstrated need.

## Spacing Scale

Preserve the established 4px grid and named spacing tokens.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps and inline alignment |
| sm | 8px | Compact control/content spacing |
| md | 16px | Default control and content spacing |
| lg | 24px | Section padding and grouping |
| xl | 32px | Layout gaps |
| 2xl | 48px | Major section breaks |
| 3xl | 64px | Page-level separation where content allows |

Exceptions: interactive controls, tabs, and icon-only targets have a minimum 44×44px hit area; this is a control dimension, not an off-grid spacing token. Existing control heights remain 36/44/52px, and phase interactions use at least 44px. Avoid page-level horizontal scrolling at 320 CSS px and 200% browser zoom.

Keep the existing `md` (768 CSS px) responsive breakpoint. At narrow widths, let picker labels, tab controls, and framing controls wrap within the content width. Show the active Mailable and scenario in the compact picker before it opens. Long plaintext wraps; Raw and Headers keep their own bounded scroll region; essential content is never clipped or available only on hover. At wide widths, retain the existing bounded Admin content frame.

## Typography

Use installed 400 and 700 weights only; Inter Tight is for headings and IBM Plex Mono is for exact values/code. Keep user/browser text sizing available.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label / code | 14px | 400 | 1.4 |
| Body | 16px | 400 | 1.5 |
| Heading | 20px | 700 | 1.2 |
| Display | 28px | 700 | 1.2 |

Use the existing fallback stacks if the named fonts are unavailable. Do not introduce 500/600 weights or reduce essential type for narrow layouts or zoom.

## Color

Keep the existing semantic theme tokens and light/dark mapping. These are approximate screen-surface proportions, not literal per-component percentages.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | Light `#F8FBFD` (`Paper`); dark `#0D1B2A` (`Ink`) | Page ground and primary work surface |
| Secondary (30%) | Light `#FFFFFF` (`surface-raised`); dark `#152538` (`surface-raised`) | Sidebar, grouped panels, editor/output surfaces |
| Accent (10%) | Light `#277B96` (`Glass`); dark `#A6EAF2` (`Ice`) | Active tab cue, primary action when present, and visible focus emphasis |
| Destructive | Light `#B42318`; dark `#E29089` | No destructive action is added in this phase; use semantic error roles for validation/render failures. |

Accent reserved for: active output-tab cue, a primary action only when a real action is needed (failure-state retry), and visible keyboard-focus emphasis. Keep borders and default surfaces neutral. Use semantic error/info/success roles with text labels; never rely on color alone. Keep Admin System/Light/Dark appearance independent from the preview backdrop and CSS-pixel frame width.

## Copywriting Contract

Use Mailglass's plain, specific voice and the domain nouns Mailable, scenario, assigns, Message, and preview. Do not describe browser output as a guaranteed recipient/provider result.

| Element | Copy |
|---------|------|
| Primary CTA | No persistent Render button: supported scalar edits update the preview live. In a render-failure state, show `Retry preview` only if it invokes a real retry. |
| Empty state heading | No Mailables: `No Mailables discovered yet.` Mailables without scenarios: `No preview scenarios configured.` Keep these as distinct states. |
| Empty state body | No Mailables: `Define a Mailable with` followed by the `mix mailglass.gen.mailable` command as code, then explain it will appear here. No scenarios: `Add named scenarios to preview_props/0 in this Mailable.` |
| Error state | Associate validation copy with the field: `Enter a valid value for {field}.` For render failure, explain that the preview could not be rendered and point to correcting the scenario input/logged diagnostic. Preserve entered drafts. If old output remains, label it `Last successful preview` and say it does not reflect the current inputs. |
| Destructive confirmation | None. Preview has no send or destructive action. |

Do not label Elixir `inspect` output as JSON. Only expose editors for scalar values with safe, lossless established parsing. Nested maps/structs and timezone-sensitive DateTimes remain read-only unless their round-trip semantics are established; show how to edit the Mailable scenario. Invalid values remain visible as drafts and are never silently replaced with defaults. Use built-in LiveView debounce on free-text fields. Announce state changes once, associate errors with fields, and do not nest duplicate live announcements inside an alert.

Correct the `guides/preview.md` example to the supported named-scenario-to-assigns-map shape. Keep discovery constrained to discovered Mailables/scenarios; do not convert URL or event strings into atoms.

## Interaction Contract

- **Discovery and selection:** preserve the existing Mailable, optional `preview_props/0`, and named-scenario/assigns contract; add no public preview API or separate registry. Preserve automatic and explicit discovery, custom mount paths, and mount-aware selection. Distinguish no discovered Mailables from discovered Mailables with no preview scenarios. Show a useful next step in each state.
- **Live edits and recovery:** supported scalar edits rerender live. Do not show a redundant always-visible Render action or introduce a manual draft/commit flow. Preserve attempted input on validation/render failure and keep the editor/correction path visible. A stale successful output may remain only with the explicit stale label above. Retry is only shown for a failure that can actually be retried.
- **Output tabs:** implement the conventional horizontal WAI-ARIA APG tabs pattern: one Tab stop; Left/Right arrows wrap; Home/End move to first/last; arrows move focus without activating; Space/Enter or click activates. Keep `aria-selected`, `aria-controls`, labelled panel IDs, and visibility consistent, with every relationship resolving. Show a visible focus indicator. Make an output panel keyboard-focusable when it has no focusable descendant so users can reach and scroll long output.
- **Output semantics:** HTML and Text are renderer outputs. Raw is an illustrative best-effort MIME-shaped preview envelope, not wire serialization. Headers identify generated preview Message-ID and Date. Never invoke outbound preflight, `Outbound.deliver/2`, or a provider adapter from Preview; do not add a send action, transport serializer, or dependency.
- **Framing:** width choices are `375`, `768`, and `1024` CSS pixels, never physical device names. Keep Admin chrome theme, preview backdrop, and width as separate controls/state. Backdrop affects the browser preview surface only and does not claim email dark-mode support. State that the iframe represents browser rendering and is not email-client proof.
- **Responsive and content behavior:** tabs and controls wrap without page-level horizontal scrolling. Preserve complete long and non-ASCII values. Text output wraps; Raw/Headers scroll within their own regions. No essential value is clipped or discoverable by hover alone.
- **Motion and accessibility:** retain the current semantic tokens, visible focus, reduced-motion behavior, and 44px minimum targets. Routine updates must not animate repeatedly; no motion may be needed to understand success/error/loading state.
- **Security boundary:** preserve disabled iframe scripts and current supported resource behavior. Do not describe the iframe as sanitization or isolation. The route macro is not authorization; adopters must guard the mount as dev-only. Use synthetic/non-sensitive preview data and treat captures as potentially sensitive; rendered remote images may trigger browser requests.
- **Acceptance evidence:** align machine-observable criteria with existing Admin LiveView/ExUnit tests and existing browser/capture suites. Support Contract Admin is required behind CI Green; Operator Browser Gate and Preview Capture Advisory remain advisory/outside the CI Green aggregate. Do not promote a lane or add a test framework. Automated acceptance closes machine-observable behavior without owner UAT; retain bounded rendered review only for visual questions.

| loading | output tabs | ✅ covered | During a pending render, output tabs remain operable and retained prior results are marked not current until a successful render replaces them. |
| error | output tabs | ✅ covered | A render failure presents the error and correction route without removing the editor or silently changing the selected output tab; prior output remains explicitly stale. |

| long-text | textual output | ✅ covered | Full long and non-ASCII plaintext, Raw-envelope, and header values remain available for reading and copying without silent truncation. |
| loading | preview controls | dismissed | Width and backdrop controls are synchronous view settings with no independent data-loading state; in-flight message rendering is covered by the editor and output surfaces. |
| error | preview controls | dismissed | Width and backdrop controls do not submit or fetch data; render failures are reported by the output surface, not by these view-only settings. |
