  <action>
    Two edits, both extending the existing classify-then-gate convention rather than inventing a new
    evidence-reporting shape.

    (a) Wrap each of the two `gh api` calls in a bash retry loop. Classification: retry only when the
    HTTP status is 403 or 429 AND the response body matches a case-insensitive secondary-rate phrase.
    Do not classify on headers alone, and do not retry on any other status. The call that already
    passes an include-headers flag gives you the response headers; add the same flag to the other call
    if headers are needed there.

    Sleep computation, in this precedence order: use the `retry-after` header when present and
    non-blank; otherwise use `x-ratelimit-reset` minus the current epoch plus one, but ONLY when
    `x-ratelimit-remaining` is zero; otherwise use 60 seconds. Floor every computed wait at 60
    seconds, and double the wait on each consecutive secondary failure. Bound the loop to 3 attempts
    with waits of 60, 120 and 240 seconds (roughly 7 minutes worst case), then stop retrying and fall
    through to the SAME existing classification the call already produces on failure — status
    `cannot-check`, reason `github_evidence_unavailable`. Do not invent a new status value.

    Build no pre-flight probe (D-24): there is no endpoint or header that reports secondary-limit
    status, the primary buckets read full during a secondary 403, and a probe is itself an extra call
    against the budget it claims to protect.

    (b) Add `continue-on-error: true` to the `googleapis/release-please-action` step — currently the
    only step in the proposal path without it — and add exactly ONE guarded re-run of that step after
    a backoff wait computed by the same policy. The `continue-on-error` exists solely to route the
    failure into classification; it must never allow the job to proceed as if the action had
    succeeded, and it must never enable blind repeated requests while limited (GitHub documents
    banning risk). If the guarded re-run also fails, the run classifies and the gate denies it a pass.

    Do NOT model the loop on octokit defaults or the github-script retries input (D-23): both put 403
    in their do-not-retry set and finish well inside the documented 60-second floor.

    Leave the final gate expression byte-for-byte unchanged (D-21) and add no `permissions:` entry.
    Label the 3-attempt count in the PR description as project policy, not a documented GitHub value.
  </action>
