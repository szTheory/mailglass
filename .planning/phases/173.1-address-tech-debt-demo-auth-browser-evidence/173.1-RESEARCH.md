## Summary

**Item 1 (demo auth).** `MailglassDemoWeb.AdminAuth` grants `:operator_access`, `:replay_webhook`, `:replay_inbound` and `:reveal_raw`, then denies everything else. The library never calls `:replay_webhook` and does call `:destructive_action` for outbound replay. The fix is a three-line change: swap the dead `:replay_webhook` clause for `:destructive_action`. The guard is a contract test. Put it in **`mailglass_admin/test`**, not `reference/demo_app/test`. Reason: no required CI lane runs `mix test` in `reference/demo_app` (only the local `verify.phase67`/`verify.phase69` aliases do). A demo-side test would not run in CI, which is the same blind-spot class that let this defect ship. The admin package's `verify.support_contract.admin` runs the full `mix test --warnings-as-errors`, and `token_parity_test.exs` already reads `reference/demo_app/*` files from there, so there is precedent.

**Item 2 (docs).** `api_stability.md` names only `:operator_access` and `:destructive_action`. Add `:replay_inbound` and `:reveal_raw` with their context shapes, and update `operator-trust.md` to match. No docs-contract test pins the action list, so none breaks. Add a drift guard to the new contract test: the actions found in source must each appear in `api_stability.md`.

**Item 3 (browser evidence red).** The orchestrator's hypothesis (email component overflowing at 320px) is **refuted**. The tree is byte-identical between the passing PR head `86f76754` and the failing main push `9588d4f0` (`git diff --stat` is empty), and the Chromium (148.0.7778.96 / playwright v1223) and apt font versions are identical in both logs. The real cause is a race in the spec. The preview iframe's `id` is `"preview-iframe-" <> render_nonce`. `handle_params` assigns a fresh `System.unique_integer` nonce on the static (dead) render and again on the connected LiveView mount. So the iframe is **replaced** when the websocket connects, resetting the inline `style.width` the spec just wrote. I reproduced this in the exact CI image (same Dockerfile, Chromium 1223): without a connected-wait, 2 of 4 runs replaced the iframe or measured the fresh 375px iframe (`scrollWidth` 373, which matches the CI "Received: 373" exactly). With a `.phx-connected` wait, 8 of 8 runs passed. The fix is in the spec, with no product change and no loosened assertion. The assertion at `:245` is correct.

**Primary recommendation:** (1) `fix(demo)`: replace the `:replay_webhook` clause with `:destructive_action`. (2) Add one admin-package contract test that scans library `Auth.authorize(` call sites, fails if it finds fewer than the 4 known atoms, and asserts both that the demo adapter returns `{:ok, _}` for each and that `api_stability.md` documents each. (3) `docs(admin)`: document the two actions. (4) `test(demo)`: wait for LiveView connected before every iframe mutation in `demo.spec.js`. Prove green with the PR's own Demo Browser Evidence run plus the post-merge push run on main.

## Architecture Patterns

### Auth call-site inventory (all of `mailglass_admin/lib`) [VERIFIED: grep + Read this session]

Public wrapper `MailglassAdmin.Auth.authorize/3` (`auth.ex:54-55`: `@spec authorize(module(), action(), map())`, `def authorize(module, action, context) when is_atom(module) do`). Callback is `@callback authorize(action(), context :: map()) :: result()` (`auth.ex:51`). Type is `@type action :: :operator_access | :destructive_action | atom()` (`auth.ex:33`).

| Atom | Call site | Context keys passed |
|------|-----------|---------------------|
| `:operator_access` | `operator/mount.ex:29` `Auth.authorize(opts[:auth], :operator_access, auth_context)` | `params, session, socket, actor` |
| `:destructive_action` | `operator/destructive_action.ex:18` `Auth.authorize(adapter, :destructive_action, %{` | `actor, delivery, replay_target` |
| `:replay_inbound` | `inbound/destructive_action.ex:23` `Auth.authorize(adapter, :replay_inbound, %{` | `actor, inbound_record` |
| `:reveal_raw` | `inbound_live.ex:1653` `MailglassAdmin.Auth.authorize(adapter, :reveal_raw, %{` | `actor` |

Exactly four atoms. All four calls are one-line `Auth.authorize(` headers, and the atom is the second argument. `operator_live.ex:572` and `inbound_live.ex:1015` call the *wrapper modules* `DestructiveAction.authorize(`, which are different functions and must not match the scan regex. The existing test double `mailglass_admin/test/support/endpoint_case.ex:368-447` handles all four. The host_app adapter (`reference/host_app/.../admin_auth.ex:5-16`) grants only `:operator_access` and denies the rest by design. It is a minimal host, so do not extend it. [VERIFIED: Read admin_auth.ex files]

### Current demo adapter [VERIFIED: reference/demo_app/lib/mailglass_demo_web/admin_auth.ex:1-23, read this session]

```elixir
defmodule MailglassDemoWeb.AdminAuth do
  @behaviour MailglassAdmin.Auth
  @impl true
  def authorize(:operator_access, %{actor: %{subject_id: subject_id}}) when is_binary(subject_id) do
    {:ok, %{subject_id: subject_id, role: :support_lead}}
  end
  def authorize(:replay_webhook, %{actor: %{subject_id: subject_id}}) when is_binary(subject_id) do ... end
  def authorize(:replay_inbound, ...), def authorize(:reveal_raw, ...)   # same shape
  def authorize(_action, _context),
    do: {:error, :unauthorized, %{message: "demo operator login required"}}
end
```

All clauses return `{:ok, %{subject_id:, role: :support_lead}}`. There is no tenant or role scoping on any clause. **`:destructive_action` should match: same guard, same return**, with no per-tenant logic. The demo's `:operator_access` is already a global grant (documented in `operator-trust.md`). `Auth.normalize_result/1` accepts a bare actor map (`auth.ex` `normalize_result({:ok, actor}) when is_map(actor)`). ### Contract test design (recommended: source scan with a floor, plus behavior check)

**Why not a library-exported `actions/0`:** it adds public API to a semver-stable package (needs `since:` metadata and an `api_stability.md` entry), makes a `feat` that cuts a release, and still needs a scan to prove the list matches the call sites. A source scan needs no library change, so this phase stays a docs/test/demo debt closure.

**Test location:** `mailglass_admin/test/mailglass_admin/auth_actions_contract_test.exs`. It runs in the required Support Contract Admin lane (`verify.support_contract.admin` = `test --warnings-as-errors`, `mailglass_admin/mix.exs:213-215`). [VERIFIED: mix.exs Read] Precedent for cross-tree reads: `token_parity_test.exs:32-36` reads `../../../reference/demo_app/...`. [VERIFIED: grep]

```elixir
defmodule MailglassAdmin.AuthActionsContractTest do
  use ExUnit.Case, async: true

  @lib Path.expand("../../lib", __DIR__)
  @demo_auth Path.expand("../../../reference/demo_app/lib/mailglass_demo_web/admin_auth.ex", __DIR__)
  @api_doc Path.expand("../../docs/api_stability.md", __DIR__)
  # Call sites pass the action as the 2nd positional arg, always on one line today.
  @call ~r/\bAuth\.authorize\(\s*[^,()]+(?:\([^)]*\))?[^,]*,\s*(:[a-z_]+)/
  @known [:destructive_action, :operator_access, :replay_inbound, :reveal_raw]

  defp called_actions do
    @lib |> Path.join("**/*.ex") |> Path.wildcard()
    |> Enum.flat_map(&(Regex.scan(@call, File.read!(&1), capture: :all_but_first)))
    |> List.flatten() |> Enum.map(&String.to_atom(String.trim_leading(&1, ":"))) |> Enum.uniq() |> Enum.sort()
  end

  test "scan finds the library's authorize call sites (a zero-match scan must fail)" do
    actions = called_actions()
    assert actions != [], "scan matched nothing: the call-site pattern drifted"
    assert Enum.all?(@known, &(&1 in actions)), "scan lost a known action: #{inspect(actions)}"
  end

  test "demo AdminAuth grants every action the library calls" do
    [{mod, _}] = Code.compile_file(@demo_auth)   # module only needs the MailglassAdmin.Auth behaviour
    on_exit(fn -> :code.purge(mod); :code.delete(mod) end)
    ctx = %{actor: %{subject_id: "operator-1"}}
    for action <- called_actions() do
      assert {:ok, _} = mod.authorize(action, ctx), "demo AdminAuth denies #{inspect(action)}"
    end
  end

  test "every called action is documented in api_stability.md" do
    doc = File.read!(@api_doc)
    for action <- called_actions(), do: assert doc =~ inspect(action)
  end
end
```

- The test above is a sketch, not verified code. Run it and tighten the regex. Today's four call sites are the oracle: the scan must return exactly `[:destructive_action, :operator_access, :replay_inbound, :reveal_raw]`. [ASSUMED] regex is untested.
- The `@known` floor catches silent regex drift. The `!= []` check catches a vacuous pass. A new library action that the scan finds automatically fails the demo and docs assertions until both are updated. This is the intended anti-drift behavior.
- Compiling the demo file with `Code.compile_file/1` avoids needing demo deps. `@behaviour MailglassAdmin.Auth` resolves inside the admin test VM. If a `redefining module` warning appears under `--warnings-as-errors`, purge in `setup_all`, or use `Code.require_file` guarded by `Code.ensure_loaded?`. Verify during implementation.

- Reverse check (optional): scan the demo file for atoms the library never calls (the dead `:replay_webhook` case). A `[:replay_webhook]` atom grep over the demo adapter is cheap, but `authorize(_action, ...)` catch-all makes a generic dead-clause scan fragile. Removing `:replay_webhook` by hand is enough.

## Common Pitfalls

### Pitfall 1: Demo e2e writes into committed `.planning` evidence
**What goes wrong:** `demo.spec.js` `captureEmailPreview` writes PNGs to `.planning/phases/172-.../artifacts/browser-evidence` (`demo.spec.js:5-12,23-26`). Any local run dirties frozen evidence. [VERIFIED: demo.spec.js Read] A related open todo, `2026-10-24-e2e-specs-overwrite-frozen-phase-evidence.md`, tracks this.
**How to avoid:** For local repros, use a throwaway script outside the repo (as I did), or `git checkout -- .planning/phases/172-*` after any local spec run. `make demo` also needs `MAILGLASS_DEMO_HTTP_PORT`/`MAILGLASS_DEMO_DB_PORT` overrides to avoid colliding with retained ports.

### Pitfall 2: Do not run `npm ci` inside the demo_e2e container against the bind mount
The compose bind mount is `.:/workspace`, so Linux `npm ci` overwrites the host's `reference/demo_app/assets/node_modules` with Linux binaries. My repro mounted `node_modules` read-only and ran only a standalone node script in the demo image. [VERIFIED: compose.demo.yml:75-98]

### Pitfall 3: `phx-update="ignore"` plus raw `style` mutation
The iframe is `phx-update="ignore"`, and the code comment at `preview_live.ex:221-224` says only a new element id re-renders the inline style. Any test that mutates `iframe.style.width` before the socket connects loses the change when the id changes at connect. The same race hides in `captureEmailPreview` (`demo.spec.js:14-27`), but it self-corrects because it asserts bounds immediately after the mutation. [VERIFIED: tabs.ex:106-113 and preview_live.ex:221-228 Read]

### Pitfall 4: Contract-test lane blind spot recurring
An admin-test ExUnit file is only run by the admin lane. Confirm the new test file is picked up: `verify.support_contract.admin` runs the full `test` (`mix.exs:213-215`), so no allow-list edit is needed. Older memory notes describing a 9-file allow-list are stale for this alias. [VERIFIED: mix.exs Read]

### Pitfall 5: Existing e2e does not cover outbound replay
`grep` of `reference/demo_app/assets/e2e/*.js` for `replay|Confirm|authorized|destructive` finds no replay confirm and no assertion of the denial. So **no existing e2e needs flipping**. A demo e2e that confirms an outbound replay and asserts success is still wanted by the owner todo (items 8-9), but it depends on the demo seed's "ready" delivery actually executing (the todo notes a prior replay showing `webhook_replay_failed`/`webhook_event_not_found`). That is out of scope for this phase unless trivially provable. See Open Questions.

### Why it surfaced only on main
It is a latent race, not a code change. The spec's `await expect(emailFrame.locator("h1"))` is satisfied by the *static* iframe, so the test proceeds before the socket joins. Whether the join lands before or after the mutation depends on runner and container timing. Four earlier CI runs got lucky; the main push and the later dependabot runs (each with a cold Docker rebuild) did not. I could not reproduce the precise "clientWidth 320 but scrollWidth 373" pairing from CI; that mid-swap measurement is consistent with the replacement mechanism but is not proven. Confidence is MEDIUM-HIGH for the cause, MEDIUM for "why exactly now". The run-to-run flake rate is itself the finding, so the plan must verify with repetition, not one green run.
