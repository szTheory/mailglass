### Area 1: Inbound version line

**Recommendation:** Path A — separate 0.x line, ship at 0.1.0.

**Decisive factor:** `guides/compatibility-and-deprecations.md:161,197` already excludes `mailglass_inbound` from the 1.x compatibility promise. Path B would require actively rewriting three documents (compatibility guide, api_stability.md, ROADMAP) to make a false promise true.

**Path A mechanical cost:** Remove inbound from `linked-versions.components`; hand-edit manifest `0.3.2 → 0.0.0` (sanctioned bootstrap edit per release-please docs); reset `@version → 0.1.0`; rewrite literal pin `→ "== 1.0.0"`; rename CHANGELOG header `[0.3.2] → [0.1.0]`; restructure `release-please.yml:61-90` sync step to per-pin target lookups (admin and inbound BOTH pin to core's 1.0.0).

**Ecosystem precedent:** Phoenix LiveView, Phoenix PubSub, Ecto.SQL, ash_postgres all spent years on 0.x sibling lines.

**Open uncertainties:** None.

### Area 2: CHANGELOG curation

**Recommendation:** Path C — hybrid (curated header + auto-generated commit ledger preserved beneath it).

**Decisive factor:** Matches the only working precedent in this repo — `CHANGELOG.md:63-164` (v0.2.0 entry) leads with curated narrative and was created via `13-01-PLAN.md` hand-editing the open Release PR. Path B (raw ledger) puts 169 commit bullets as the first thing on hexdocs.pm/mailglass/changelog.html — adopter-hostile and fails success criterion #2's "with REQ-ID references" requirement.

**Path C shape:** "## What's new in 1.0.0 (v0.5 → v1.1 bundle)" prose section as the FIRST content of the 1.0.0 entry, four subsections per bundled milestone with REQ-ID families and milestone-audit links. Auto-generated `### Features`/`### Bug Fixes` ledger preserved below.

**Sibling CHANGELOGs:** Short coordinated sibling notes per D-13-05 (admin and inbound).

**Companion doc:** Create `docs/upgrade-from-0.x.md` (success criterion #2 mandates it) modeled on `guides/upgrading-from-v0_1.md`.

**Merge discipline:** Edit the open Release PR after final pre-1.0 commit; merge immediately to dodge force-push clobber.

**Open uncertainties:** None.

### Area 3: publish-hex.yml inbound integration

**Recommendation:** Path A — full automation in this phase.

**Decisive factor:** Most scaffolding already done — `mix mailglass.publish.check` already inbound-aware (15+ line references), allowlist already committed, mix.exs already toggles `MIX_PUBLISH=true`. Remaining work is YAML-only: clone publish-admin job → publish-inbound, add input enum value, add prepublish-summary step, parallel additions to post-publish-smoke.yml waiters/retracted-check, MAINTAINING.md prose update.

**Path B (manual one-shot) cost:** Reintroduces HEX_API_KEY-on-maintainer-machine secret-handling risk; trades a known, rehearsed code path for an unrehearsed manual ceremony at the highest-blast-radius moment.

**Idempotency:** Existing `mix hex.info … grep Released:` skip pattern + post-index waiter transfer cleanly.

**Sequencing:** `needs: [publish-core]`; can run in parallel with `publish-admin` after core indexes.

**Open uncertainties:** None.

### Area 4: Rehearsal posture

**Recommendation:** Path B — `dry_run=true workflow_dispatch` on release-please PR head ref BEFORE merging.

**Decisive factor:** `publish-hex.yml:188-191,275-278` `dry_run=true` invokes a real `mix hex.publish --dry-run` (full tarball build, allowlist match, dependency resolution against actual Hex, metadata validation), not a no-op. Phase 38 rehearsal was real but anchored at `mailglass-v0.3.2`; 169 commits, 4 milestones, and a third package now in scope. Cost: ~45 min vs Path C's ~10 min, retires four staleness risks (drifted allowlists, MIX_PUBLISH swap regression, first-publish inbound surprises, dependency resolution against Hex vs path).

**Path A (throwaway branch) cost:** ~3-4 hours; redundant once Path B taken.

**Path D (post-publish aggressive smoke):** Detection happens inside the 60-minute window — every minute spent installing is a minute lost from the revert decision. For first-publish inbound, Hex's 24-hour new-package window only helps if zero downloads.

**Compatible with MAINTAINING.md:108-149 runbook** — runbook step 1 already relies on `prepublish-summary` + `gate-ci-green`, both of which run on `dry_run=true`.

**Open uncertainties:** None.
