## Summary

Phase 44.5 is a release-engineering phase with **zero greenfield work**: every authoritative seam already exists. `mix mailglass.publish.check` is already inbound-aware (15+ line references). `.planning/publish/mailglass_inbound-files.expected` already lists 38 entries. `mailglass_inbound/mix.exs:58-64` already implements the `MIX_PUBLISH=true` swap. `release-please-config.json` already declares all three packages. `MAINTAINING.md` already documents the 60-minute window and retract decision tree. The Phase 38 forms (`38-03-RELEASE-CHECKLIST.md`, `38-03-RELEASE-RECORD.md`) already encode the proof shape. [VERIFIED: repo audit]

The phase's load-bearing risk is **operational sequencing**, not technical novelty. Three pre-ceremony commits (A=unlink inbound, B=publish-hex.yml extension, C=curated CHANGELOG + upgrade doc) MUST land in that order on `main` BEFORE release-please opens the 1.0.0 PR — because (A) governs what release-please includes in the cut, (B) governs whether `dry_run=true package=all` works during rehearsal, and (C) governs what survives release-please's force-push behavior on subsequent commits to `main`. After the PR opens, the rehearsal+merge+60-minute-window+evidence sequence is irreversible, single-pass, and bounded by Hex's 60-minute revert window plus the 24-hour first-publish window for `mailglass_inbound`. [VERIFIED: `release-please/customizing.md` + `MAINTAINING.md:108-189` + Hex publish docs at https://hex.pm/docs/publish]

The `release-please.yml` sync-step rewrite (lines 61-90) is the single most error-prone mechanical change. The current single-`NEW_VERSION` jq read assumes all linked packages share a version. After D-44.5-01 unlinks inbound, both `mailglass_admin` and `mailglass_inbound` still pin to **core's** version (`== 1.0.0`), so the rewrite must read `.["."]` once and apply that to BOTH path entries — not read each entry separately and apply per-pin (which would pin inbound's `mix.exs` to inbound's `0.1.0`, breaking everything). The REL-05 exit-1 guard plus `mailglass_admin/test/mailglass_admin/mix_config_test.exs:107-122` sed-anchor regex must remain green; if either falls silently, the published `mailglass_admin` and `mailglass_inbound` tarballs would carry stale path-deps and fail at adopter `mix deps.get`. [VERIFIED: release-please.yml:53-104 + mix_config_test.exs read]

**Primary recommendation:** Plan this phase as 4-5 tightly-sequenced plans:
1. **Plan 1 (Wave 0+1, Commit A):** Inbound version-line break — manifest bootstrap edit, mix.exs version + pin updates, CHANGELOG header rename, release-please.yml sync-step rewrite, REL-05 guard re-validation. Single commit, single PR.
2. **Plan 2 (Wave 2, Commit B):** `publish-hex.yml` `publish-inbound` job + `post-publish-smoke.yml` parallel inbound steps + `MAINTAINING.md` update. Single commit, single PR; rehearsable now via `dry_run=true package=mailglass_inbound`.
3. **Plan 3 (Wave 3, Commit C):** Curated `CHANGELOG.md` 1.0.0 header + sibling `mailglass_admin` + `mailglass_inbound` notes + `docs/upgrade-from-0.x.md` create + `mix.exs` docs `extras` registration. Single commit, single PR.
4. **Plan 4 (Wave 4):** Live ceremony — dry-run dispatch, PR review, merge, 60-min window, sandbox install, evidence capture into `044.5-RELEASE-RECORD.md`.
5. **Plan 5 (Wave 5):** Branch-protection evidence (`044.5-BRANCH-PROTECTION-EVIDENCE.md`) + MILESTONES.md + PROJECT.md "Current State" + STATE.md updates + CLOSE-06 closeout note.

The shape mirrors Phase 13's five-plan ceremony precedent (13-01-PLAN through 13-05-PUBLISH-EVIDENCE). The validation surface is the existing `mix verify.stability_contract` + `mix mailglass.publish.check --package all` + the new `dry_run=true package=all` workflow dispatch. ### Pattern 1: Manifest bootstrap edit (D-44.5-01 mechanic)

**What:** Hand-edit `.release-please-manifest.json["mailglass_inbound"]` from `"0.3.2"` to `"0.0.0"`. This is the [release-please manifest-releaser docs](https://github.com/googleapis/release-please/blob/main/docs/manifest-releaser.md)-sanctioned bootstrap edit.

**When to use:** Exactly once, in Commit A. The bootstrap edit signals to release-please: "treat the next bump for this component as a fresh first-release".

**How release-please interprets `0.0.0`:** On the next pass after Commit A lands, release-please reads the manifest, sees `mailglass_inbound: 0.0.0`, finds zero released tags matching `mailglass_inbound-v*` (because no such tag exists), and computes the next version from the conventional commits affecting `mailglass_inbound/**`. ### Pattern 2: Per-pin target lookup in release-please.yml sync step (D-44.5-01 mechanic)

**What:** The current release-please.yml:61 reads `NEW_VERSION` from `mailglass_inbound // mailglass_admin // .` — a fallback chain that returns whichever is highest in priority. This works only when all three packages share a version. After D-44.5-01, both `mailglass_admin/mix.exs` AND `mailglass_inbound/mix.exs` must pin to **core's** 1.0.0 (NOT to their own version), so the rewrite must read `.` once and apply to both.

**Concrete shape:**

```yaml

CORE_VERSION=$(jq -r '.["."]' .release-please-manifest.json)
if [ -z "$CORE_VERSION" ] || [ "$CORE_VERSION" = "null" ]; then
  echo "ERROR: could not read core version (.[\".\"]) from .release-please-manifest.json" >&2
  exit 1
fi
echo "Target dep pin: {:mailglass, \"== $CORE_VERSION\"}"

# REL-05: Bash-loop generalization keyed on (path, dep_atom) pairs.
# Both admin and inbound pin to CORE'S version, not their own.
PINS=(
  "mailglass_admin/mix.exs:mailglass"
  "mailglass_inbound/mix.exs:mailglass"
)

for entry in "${PINS[@]}"; do
  path="${entry%:*}"
  dep="${entry##*:}"

  matches=$(grep -cE "\{:${dep}, \"== [0-9]+\.[0-9]+\.[0-9]+\"\}" "$path" || true)
  if [ "$matches" -eq 0 ]; then
    echo "ERROR: sed anchor regex matched zero lines in $path." >&2
    echo "The dep tuple shape may have been renamed — see CONTRIBUTING.md REL-05 section." >&2
    exit 1
  fi

  sed -i -E "s/\{:${dep}, \"== [0-9]+\.[0-9]+\.[0-9]+\"\}/{:${dep}, \"== ${CORE_VERSION}\"}/" "$path"
done
```

**What survives:**
- The PINS array shape (already present at release-please.yml:70-73).
- The REL-05 exit-1 guard (already present at release-please.yml:79-87).
- The git config + commit + push sequence (release-please.yml:100-104).
- The `mix_config_test.exs:107-122` sed-anchor regex `~r/\{:mailglass, "== \d+\.\d+\.\d+"\}/` test.

**What changes:**
- Variable name: `NEW_VERSION` → `CORE_VERSION` (semantic clarity; both pins target core's version).
- jq query: `'.["mailglass_inbound"] // .["mailglass_admin"] // .["."]'` → `'.["."]'` (read core directly, no fallback chain).

**Why the fallback chain breaks after unlinking:** The current chain returns inbound's version (0.1.0) first if the manifest has it set, then admin's (1.0.0), then core's (1.0.0). Under linked-versions all three are equal so the chain works. ### Pattern 5: Curated CHANGELOG hand-edit + force-push avoidance (D-44.5-02 mechanic)

**What:** release-please's behavior on `git push` to `main` is to update the open Release PR — re-running its analysis, regenerating CHANGELOG entries, and **force-pushing** to `release-please--branches--main`. Hand-edits to the Release PR's CHANGELOG are vulnerable to clobber UNLESS the curated content is in CHANGELOG.md on `main` BEFORE the PR is finalized.

**The 13-04-REHEARSAL.md proven pattern (Phase 13 v0.2.0 ceremony):** Hand-edit the open Release PR's CHANGELOG.md directly (after release-please's last force-push), then merge IMMEDIATELY without further commits to `main`. This worked for v0.2.0 because no commit landed on `main` between the curation and the merge.

**Why D-44.5-02 takes a slightly different path:** The Phase 44.5 commit sequence puts curated CHANGELOG headers in **Commit C on `main`** (BEFORE the Release PR opens), not as an edit to the open PR. This is more robust because:
- release-please's CHANGELOG ledger generation appends entries to the **top** of the existing file. If `main`'s CHANGELOG.md already has a curated 1.0.0 stub (or even just the section heading `## [1.0.0]`), release-please... actually the behavior is more subtle.

**Tested release-please behavior (per [release-please customizing.md](https://github.com/googleapis/release-please/blob/main/docs/customizing.md) section "Pull Request Body Changes" + the v0.2.0 evidence):**
- release-please regenerates CHANGELOG.md by **prepending** a new section above the existing top entry. It does NOT modify pre-existing entries.
- If Commit C on `main` adds curated `## [1.0.0]` content, release-please will see the file already has a 1.0.0 section and either skip prepending (if it detects the version) or prepend a duplicate (if it doesn't).

## Common Pitfalls

### Pitfall 1: release-please force-push clobbers curated CHANGELOG hand-edit

**What goes wrong:** Maintainer hand-edits the open Release PR's `CHANGELOG.md` to add curated four-milestone subsections. A subsequent commit lands on `main` (e.g., a typo fix, a CI tweak, a Phase 51 prep commit). release-please re-runs, regenerates the PR's CHANGELOG.md from scratch, and force-pushes. The curated subsections are gone. [VERIFIED: release-please customizing.md fetch + 13-04-REHEARSAL.md history]

**Why it happens:** release-please's PR is generated artifact, not maintainer-owned source. Any input change (a new commit since last run) triggers regeneration. The action is recursion-safe (`GITHUB_TOKEN` pushes don't re-trigger workflows per the workflow comment line 39-40), but maintainer pushes to `main` DO re-trigger.

**How to avoid:**
1. Land Commit C (curated headers in CHANGELOG.md + `docs/upgrade-from-0.x.md`) BEFORE release-please opens the PR.
2. After the PR opens, do the hand-edit IMMEDIATELY before merge — within a coordination window where no other commit will land on `main`.
3. If the window slips, redo the hand-edit after the force-push and merge again immediately.
4. Squash-merge (per MAINTAINING.md:131) preserves the linear history; the curated content lands on `main` as a single commit. After merge, the content is permanent.

**Warning signs:** PR shows a `chore(release-please): sync sibling mailglass dep pins...` commit AND a CHANGELOG.md regeneration commit between the hand-edit and the merge. The hand-edit is gone. Re-do.

### Pitfall 2: jq fallback chain in release-please.yml returns wrong version after unlinking

**What goes wrong:** Phase 44.5 Plan 1 (Commit A) updates the manifest but forgets to update the jq query at release-please.yml:61. release-please opens the PR; sed step runs; `NEW_VERSION=$(jq -r '.["mailglass_inbound"] // .["mailglass_admin"] // .["."]' ...)` returns `"0.1.0"` (inbound's value, first non-null in fallback chain). Both `mailglass_admin/mix.exs:128` AND `mailglass_inbound/mix.exs:60` get rewritten to `{:mailglass, "== 0.1.0"}`. The release commits, tags, and (if D-44.5-04 dry-run is skipped) publishes. Adopters install `mailglass_admin 1.0.0` and get `mailglass 0.1.0` (or fail to resolve, since `0.1.0` may not satisfy other constraints). [VERIFIED: release-please.yml:61 + D-44.5-01 mechanical implications]

**Why it happens:** The fallback chain `jq -r '.["mailglass_inbound"] // .["mailglass_admin"] // .["."]'` was correct under linked-versions where all three values were identical. After unlinking, the chain returns the wrong value with no error. The REL-05 exit-1 guard fires only if the regex match count is zero — it doesn't validate that the substituted version is correct.

**How to avoid:** Plan 1 (Commit A) MUST include the jq query rewrite (`.["."]` direct read) per Pattern 2 above. Plan 1 verification step: re-run `mix_config_test.exs` AND simulate the sed step locally with `CORE_VERSION=$(jq -r '.["."]' .release-please-manifest.json)` followed by the loop body, with a Postgres-free local Mix env.

**Warning signs:** After release-please opens the PR, `mailglass_admin/mix.exs:128` shows `{:mailglass, "== 0.1.0"}` instead of `{:mailglass, "== 1.0.0"}`. Or post-publish-smoke fails with a dependency resolution error.

### Pitfall 3: post-publish-smoke `cron-guard` outputs single version; inbound has different version

**What goes wrong:** After D-44.5-03 adds inbound to consumer-install, the cron-guard step at post-publish-smoke.yml:39-135 outputs `version` as a single value (e.g., `1.0.0`). Downstream jobs use `${{ needs.cron-guard.outputs.version }}` for both core+admin (correct, both 1.0.0) AND inbound (wrong, should be 0.1.0). `wait-for-index` for inbound waits on `mailglass_inbound 1.0.0` which never indexes. Smoke times out at 5 minutes per package. [VERIFIED: post-publish-smoke.yml:39-184 + D-44.5-03 mechanical implications]

**Why it happens:** post-publish-smoke was designed pre-D-44.5-01, when all three packages had a single version. After unlinking, inbound's version is independent and must be resolved separately.

**How to avoid:** Plan 2 (Commit B) MUST extend cron-guard to output `version_inbound` separately. Two options (per Pattern 4):
- **Option A:** Hardcode `version_inbound: '0.1.0'` in the github-script step. Simple but requires updating each release. After Phase 50.5 ships inbound 0.2.0, this hardcoded value must be bumped. Not future-proof.
- **Option B:** Resolve inbound version at runtime by checking out the release tag and reading `mailglass_inbound/mix.exs`. Works for arbitrary inbound versions; slightly more complex.

**Recommendation:** Option B. Add a checkout step in cron-guard that reads `mailglass_inbound/mix.exs` and outputs `version_inbound`. ~5 added lines; future-proof.

**Warning signs:** Post-publish-smoke run times out on `wait-for-index for mailglass_inbound 1.0.0` at the 5-minute deadline. The 1.0.0 version doesn't exist for inbound, so `mix hex.info` returns nothing.

### Pitfall 4: Maintainer dispatches `dry_run=true` from `main` instead of release-please PR head

**What goes wrong:** D-44.5-04 step 3 says "dispatch from PR head ref". Maintainer instead dispatches from `main` (muscle memory from regular `workflow_dispatch`). The publish-hex.yml checkout step uses `ref: ${{ github.event.inputs.tag || github.event.release.tag_name }}` (publish-hex.yml:68), which resolves `inputs.tag` first. If maintainer supplies `tag=mailglass-v1.0.0` and that tag doesn't yet exist (because PR isn't merged), checkout fails with "ref not found". [VERIFIED: publish-hex.yml:65-68 + D-44.5-04 step 3]

**Why it happens:** The dispatch-from-tag pattern is the post-publish recovery path. Pre-publish dispatch (D-44.5-04) is a different model — there is no tag yet because no merge has happened.

**How to avoid:** D-44.5-04 step 3 explicitly says "PR's head ref". The PR's head branch is `release-please--branches--main`. The dispatch command is:

```bash
gh workflow run publish-hex.yml \
  --ref release-please--branches--main \    # ← PR head, NOT a tag
  -f tag=mailglass-v1.0.0 \                  # ← This is informational; checkout uses --ref
  -f dry_run=true \
  -f package=all
```

But wait — the `ref` parameter to `gh workflow run` is what GitHub Actions uses to resolve the workflow's invocation. Then `inputs.tag` is what the workflow's checkout step uses for `actions/checkout`. If `tag=mailglass-v1.0.0` is passed and that tag doesn't exist, checkout fails. **Better:** pass `tag=release-please--branches--main` (or empty `tag` and let the `release.tag_name` fallback to empty, which would also fail).

**Resolution:** publish-hex.yml's checkout step needs to handle the dry-run-on-PR-head case. Two options:
- **Option A (workflow change):** Add a third fallback `|| github.ref` so the checkout uses the dispatched ref when no tag is supplied. Requires Plan 2 work.
- **Option B (process change):** Maintainer manually creates a `dry-run-mailglass-v1.0.0` annotated tag on the PR head SHA before dispatching. After dry-run, delete the tag. Adds 30 seconds of work; no workflow change.

**Recommendation:** Option B for Phase 44.5; defer Option A to Phase 51 cleanup. The process is: `git fetch origin release-please--branches--main; git tag mailglass-v1.0.0-rc1 origin/release-please--branches--main; git push origin mailglass-v1.0.0-rc1; gh workflow run publish-hex.yml --ref release-please--branches--main -f tag=mailglass-v1.0.0-rc1 -f dry_run=true -f package=all`. Then `git push origin :mailglass-v1.0.0-rc1` to clean up.

**Open question for plan-phase:** confirm with the user which option to take. Option B has zero workflow risk but adds an artifact tag. Option A has higher first-cut risk (workflow change inside the ceremony commit window).

**Warning signs:** Dispatched workflow fails at the checkout step with "remote: error: cannot find ref `mailglass-v1.0.0`". Re-run with the corrected `ref` resolution.

### Pitfall 5: release-please skips the major bump because no `feat!`/`BREAKING CHANGE` commit exists in the bundle range

**What goes wrong:** release-please reads commits since v0.3.2 tag. If none of the 169 commits has a `feat!:` or `BREAKING CHANGE:` footer, release-please calculates the next version using the smallest applicable bump rule. For `feat:` commits, that's a minor bump → `0.4.0`, not `1.0.0`. The Release PR opens at v0.4.0; CHANGELOG curation lands at the wrong version. [VERIFIED: release-please conventional-commits semantics + MAINTAINING.md:136-139 recovery procedure]

**Why it happens:** The 4-milestone bundle (v0.5/v0.6/v1.0/v1.1) was authored in many commits, mostly `feat:` and `fix:` scopes. The "v1.0 stability lock" branding is editorial — release-please doesn't see "this is the v1.0 cut" anywhere in the conventional commit log.

**How to avoid:** CONTEXT line 115 (Claude's discretion) flags this: "Whether to add a Conventional Commits `Release-As: 1.0.0` footer on a synthetic commit to force release-please to cut the version." MAINTAINING.md:136-139 documents the recovery: "recover with a tiny follow-up commit that carries a `Release-As: <intended-version>` footer. Do not hand-edit `.release-please-manifest.json` to force the version."

**Recommendation:** Plan 1 (Commit A) should include a `Release-As: 1.0.0` footer on the commit message itself. Conventional Commit format:

```text
chore: prepare 1.0.0 release ceremony

Unlinks mailglass_inbound to its own 0.x version line and rewrites the
release-please.yml sync step to handle the new pin shape per D-44.5-01.

Release-As: 1.0.0
```

This forces the next release-please run to cut `mailglass` and `mailglass_admin` at 1.0.0 regardless of what conventional commits in the bundle range suggest. `mailglass_inbound` is unlinked, so the `Release-As` only applies to the linked group.

**Sanity-check question for plan-phase:** does `Release-As: 1.0.0` on a single commit in the linked group apply to all linked packages, or only to the package whose path the commit touched? Per release-please docs, the Release-As trailer applies to the component(s) the commit touches by path. For a chore commit touching all four files (release-please-config.json, manifest, inbound mix.exs, inbound CHANGELOG, release-please.yml), the package association may be ambiguous. **Safer pattern:** put the `Release-As: 1.0.0` on a commit that touches `mix.exs` (root), since that's the canonical core package path. Alternatively, use the workflow input shape (release-please-action supports a `release-as` input).

**Open question for plan-phase:** confirm with one of:
- Pre-cut local rehearsal: `release-please github-release --dry-run --token ...` to see what version it computes.
- Ask the user: "should we explicitly force 1.0.0 via Release-As trailer, or trust the bundle range to imply it?"

**Warning signs:** Release PR opens with title `chore(main): release 0.4.0` instead of `chore(main): release 1.0.0`. Recovery is a follow-up commit with the Release-As footer; release-please force-pushes the PR with the corrected version on next run.

### Pitfall 7: `mailglass_inbound/mix.exs:60` pin update missed in Commit A

**What goes wrong:** Plan 1 (Commit A) updates `@version` to `0.1.0` but forgets to update the `mailglass_dep/0` literal pin from `{:mailglass, "== 0.3.2"}` to `{:mailglass, "== 1.0.0"}`. Release PR opens; sed step in release-please.yml runs and rewrites the pin to `== 1.0.0` (because the sed step uses the manifest's `.["."]` value). So actually... the sed step covers this. Except: the sed step only runs WHEN release-please opens a PR. If Plan 1 lands on `main` and release-please's next run is delayed (or there's no triggering commit), the pin sits at `== 0.3.2` indefinitely. Local `mix deps.get` from `mailglass_inbound/` with `MIX_PUBLISH=true` would resolve `mailglass 0.3.2` from Hex (if it's still indexed). Local validation fails subtly. [VERIFIED: release-please.yml:68-90 + mailglass_inbound/mix.exs:58-64]

**Why it happens:** The sed step is a PR-time mechanism, not a `main`-time mechanism. Between Commit A landing and release-please opening the PR, the pin is stale.

**How to avoid:** Plan 1 manually updates `mailglass_inbound/mix.exs:60` to `{:mailglass, "== 1.0.0"}` in Commit A (NOT relying on the sed step to fix it). The sed step idempotency means re-running with already-correct values is a no-op.

**Sanity check:** the `mix_config_test.exs:107-122` REL-05 sed-anchor test asserts the pattern `\{:mailglass, "== \d+\.\d+\.\d+"\}` matches the file content. It does NOT assert the version is 1.0.0. So updating the pin to 1.0.0 in Commit A (manually) keeps the test green — and the subsequent sed step is a no-op (correct value already present).

**Warning signs:** After Commit A, `cat mailglass_inbound/mix.exs | grep '== '` shows `0.3.2` instead of `1.0.0`.
