**Gathered:** 2026-05-07

<domain>
## Phase Boundary

Cut and ship the linked-version Hex release that bundles four unreleased milestones (v0.5 + v0.6 + v1.0 + v1.1, 169 commits since the `v0.3.0` tag) before any v1.2 implementation begins. The ceremony publishes:

- `mailglass` 0.3.2 → **1.0.0**
- `mailglass_admin` 0.3.2 → **1.0.0**
- `mailglass_inbound` (never published) → **0.1.0** (first Hex appearance, on its own 0.x version line)

This phase resolves CLOSE-06 and converts Phase 38's repo-local rehearsal artifacts to live publish proof at the new SHA. It is NOT a feature phase, NOT a runtime change, and NOT a CI overhaul beyond what is required to extend the release pipeline to the third sibling package.

The release-cadence rule (added 2026-05-06) is the load-bearing constraint: each milestone closes with a release ceremony before the next milestone implementation begins. The 4-milestone gap between v0.3.2 and "what should have been" v1.0.0 is the failure mode this phase repairs.
</domain>

## Implementation Decisions

### Inbound version line (D-44.5-01)

**`mailglass_inbound` ships at 0.1.0 on a separate, unlinked 0.x version line.**

**Why:** `guides/compatibility-and-deprecations.md:161,197` already excludes `mailglass_inbound` from the 1.x compatibility promise. ROADMAP Phase 44.5 success criterion #1 and Phase 50.5 explicit text both specify 0.1.0. Path B (1.0.0 linked) requires actively rewriting three documents to make a false stability promise true and forecloses breaking inbound APIs without a core 2.x bump.

**Ecosystem precedent:** Phoenix LiveView, Phoenix PubSub, Ecto.SQL, ash_postgres all spent years on 0.x sibling lines while their primary packages reached 1.x.

**Mechanical implications (locked):**
- Remove `mailglass_inbound` from `release-please-config.json:27` `linked-versions.components` list. Linked-versions plugin cannot mix major versions ([release-please #1750](https://github.com/googleapis/release-please/issues/1750)) — the only correct shape is unlinking, not customizing within the group.
- Hand-edit `.release-please-manifest.json["mailglass_inbound"]` from `"0.3.2"` to `"0.0.0"` (sanctioned bootstrap edit per [release-please manifest-releaser docs](https://github.com/googleapis/release-please/blob/main/docs/manifest-releaser.md) — "manually editing the manifest is only appropriate in the bootstrap case"; this *is* the bootstrap case).
- `mailglass_inbound/mix.exs:4` `@version "0.3.2"` → `"0.1.0"`.
- `mailglass_inbound/mix.exs:60` `{:mailglass, "== 0.3.2"}` → `{:mailglass, "== 1.0.0"}` (inbound depends on core's 1.0.0, not on its own 0.1.0).
- `mailglass_inbound/CHANGELOG.md:8` rewrite the only existing `[0.3.2] - 2026-05-06` section header to `[0.1.0] - 2026-05-XX` (never published, no contradicted artifact). Preserve content; this is a header-only rename + curation pass (D-44.5-04).
- `.github/workflows/release-please.yml:61-90` sync step rewrite — replace the single-`NEW_VERSION` jq read with per-pin target lookups so admin and inbound BOTH pin to core's `1.0.0`. Concrete shape: `CORE_VERSION=$(jq -r '.["."]' ...)` then both PINS entries write `{:mailglass, "== $CORE_VERSION"}`. The existing REL-05 exit-1 guard (`:81-87`) and the `mix_config_test.exs` sed-anchor stability test must be re-validated against the new shape.

### CHANGELOG curation strategy (D-44.5-02)

**Hybrid (Path C): pre-authored curated header + auto-generated commit ledger preserved beneath it.**

**Why:** Matches the only working precedent in this repo — `CHANGELOG.md:63-164` (the v0.2.0 entry) leads with curated narrative ("Breaking Changes", "Exact Upgrade Path", "Dependency / Runtime Floor", "Rollback") and was created via Plan 13-01-PLAN.md by hand-editing the open Release PR. Path B (raw release-please ledger) puts 169 commit bullets as the first thing an adopter sees on `hexdocs.pm/mailglass/changelog.html` — adopter-hostile and fails success criterion #2 verbatim ("CHANGELOG entries... document the bundled milestones **with REQ-ID references**" — auto commit scopes are not REQ-ID references). Path A (pre-authored only) throws away the audit trail that auditors and security reviewers expect.

**Locked shape:**
- `CHANGELOG.md` (core) `1.0.0` entry: lead with `## What's new in 1.0.0 (v0.5 → v1.1 bundle)` curated prose section, four subsections (v0.5 Adoption Hardening / v0.6 Production Maturity / v1.0 Stability Lock / v1.1 Inbound Core Slice), each citing the relevant REQ-ID families and linking to the corresponding `.planning/milestones/v0.X-MILESTONE-AUDIT.md`. Below the curated header, leave release-please's `### Features` / `### Bug Fixes` ledger intact as the audit trail.
- `mailglass_admin/CHANGELOG.md` `1.0.0` entry: short coordinated sibling note per D-13-05 (version-coordinated with core, names what adopters do beyond the core upgrade, points to core entry for the full story).
- `mailglass_inbound/CHANGELOG.md` `0.1.0` entry: same short coordinated sibling note shape, plus first-publish framing ("first Hex appearance", explicit 0.x stability disclaimer aligned with `guides/compatibility-and-deprecations.md:161`).
- **Companion doc — `docs/upgrade-from-0.x.md`** (mandated by success criterion #2 — currently does not exist): create as the deep-dive companion modeled on the existing `guides/upgrading-from-v0_1.md` shape. The CHANGELOG narrative links to it. The success-criterion verification ("verified end-to-end against a sandbox app") targets the upgrade doc, not the CHANGELOG, narrowing the verification surface.
- **Merge discipline:** Author the curated header *after* the final pre-1.0 commit lands (so a subsequent release-please force-push doesn't clobber the edit), then merge the Release PR immediately. Same workflow as v0.2.0 ceremony (`13-04-REHEARSAL.md:20-32`).

### `publish-hex.yml` inbound integration (D-44.5-03)

**Add a `publish-inbound` job to `publish-hex.yml` in this phase. Full automation parity, no manual one-shot.**

**Why:** The bulk of scaffolding is already done — `lib/mix/tasks/mailglass.publish.check.ex` is already `mailglass_inbound`-aware (lines 62, 66, 215, 222, 235, 471, 628, 732, 766, 845, 933, 1082, 1148, 1244, 1253), `.planning/publish/mailglass_inbound-files.expected` is already committed (38 entries), and `mailglass_inbound/mix.exs:58-64` already implements the `MIX_PUBLISH=true` swap pattern that admin uses. Remaining work is approximately one YAML job and one MAINTAINING.md prose update. Path B (manual first cut) reintroduces a HEX_API_KEY-on-maintainer-machine secret-handling risk class the workflow eliminates and trades a known, rehearsed code path for an unrehearsed manual ceremony at the moment of highest blast radius.

**Locked shape:**
- Clone `publish-admin` job (publish-hex.yml:210-282) → new `publish-inbound` job. Mirror: env-gated approval (`environment: hex-publish`), idempotency guard (`mix hex.info mailglass_inbound "${VERSION}" 2>/dev/null | grep -q "Released:"`), `MIX_PUBLISH=true` env, post-index waiter (`until mix hex.info mailglass_inbound "${VERSION}"`), `working-directory: mailglass_inbound`.
- Sequencing: `needs: [publish-core]` (inbound depends on core 1.0.0 being indexed; same as admin). Inbound and admin can run in parallel after core indexes — they have no inter-dependency.
- Update input enum (publish-hex.yml:23-31): `package: mailglass | mailglass_admin | both` → add `mailglass_inbound` and `all`. Update `if:` conditionals throughout to handle the `all` value.
- Add prepublish-summary step mirroring lines 95-106 (`mix mailglass.publish.check --package mailglass_inbound`).
- Parallel additions to `.github/workflows/post-publish-smoke.yml`: `wait-for-index` (lines 167-184), `wait-for-hexdocs` (lines 211-228), `retracted-check` (lines 356-367) — all need an inbound parallel step.
- `MAINTAINING.md` runbook updates: `--package both` → `--package all` (or document `package=all` covers all three); fan-out narrative "core then admin" → "core, then admin and inbound in parallel".
- Idempotency: workflow remains safely re-runnable. If inbound publish.check fails after admin succeeds, partial-release recovery is the same `workflow_dispatch` fallback path documented in MAINTAINING.md:149.

### Rehearsal posture (D-44.5-04)

**Path B: `dry_run=true workflow_dispatch` on the release-please PR head ref BEFORE merging.**

**Why:** Phase 38 rehearsal proof was real but anchored at `mailglass-v0.3.2` — 169 commits, four milestones, and a third package now in scope. `publish-hex.yml:188-191,275-278` `dry_run=true` invokes a real `mix hex.publish --dry-run` (full tarball build, allowlist match, dependency resolution against actual Hex, metadata validation), not a no-op. This is the cheapest way to retire the four staleness risks (drifted allowlists, MIX_PUBLISH swap regression, first-publish inbound surprises, dependency resolution against Hex vs path) without consuming the 60-minute irreversibility window or the 24-hour first-release window for `mailglass_inbound`. Costs ~45 minutes vs. Path C's ~10. Strictly compatible with `MAINTAINING.md:108-149` runbook (runbook step 1 already relies on `prepublish-summary` + `gate-ci-green`, both of which run on `dry_run=true`).

**Locked sequence:**
1. Release-please opens the v1.0.0 PR (after the curated CHANGELOG headers + `docs/upgrade-from-0.x.md` are committed to `main`, AND the unlinked-inbound config is merged).
2. Review the PR diff for: manifest bumps for all three packages (`.` → 1.0.0; admin → 1.0.0; inbound stays at 0.1.0 unlinked), `mailglass_admin/mix.exs` and `mailglass_inbound/mix.exs` pin sync (both → `{:mailglass, "== 1.0.0"}`), CHANGELOG curated headers preserved.
3. **Before merging,** dispatch `.github/workflows/publish-hex.yml` from the PR's head ref with `dry_run=true, package=all`. Read the prepublish-summary `GITHUB_STEP_SUMMARY` output. Verify file count, total size, CHANGELOG excerpt, and top files all match expectations for all three packages.
4. Merge release-please PR (squash-merge); approve `hex-publish` Environment; start the literal 60-minute timer per MAINTAINING.md:150-164.
5. Runbook step 4 sandbox install during the 60-minute window. Concrete `phx.new --no-ecto --no-mailer --install` host (D-38-05); add all three packages to deps; verify `GET /dev/mail/` returns HTTP 200; verify `mix mailglass.install` and `mix compile --warnings-as-errors`.
6. Append the dry-run dispatch URL, live publish URL, post-publish smoke URL, and 60-minute-window decision to a fresh `044.5-RELEASE-RECORD.md` (do NOT overwrite `38-03-RELEASE-RECORD.md` — Phase 44.5 owns the live cut record; Phase 38 owns the rehearsal record).
