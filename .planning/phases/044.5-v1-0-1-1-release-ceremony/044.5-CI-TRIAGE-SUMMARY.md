## What Was Fixed

### Lane 1 — Format Check (commit `750e5ed`)

**Root cause.** Elixir 1.18 and 1.19 disagree on multiple wrapping decisions. The repo standardizes on the 1.18 formatter for CI parity. Local toolchain (1.19.5/OTP 28) wrote some files in a way 1.18's formatter wants rewrapped (and vice versa). Affected: 16 files across `lib/` and `test/`.

**Fix.** Ran `mix format` against the worktree using `hexpm/elixir:1.18.4-erlang-27.2.3-alpine-3.21.3` Docker image (matches CI's setup-beam pin). Verified the result also passes `mix format --check-formatted` under the local 1.19 toolchain — both versions accept the rewritten files (1.19's formatter is idempotent on the 1.18-flavoured output for this set of changes).

**Evidence.** `mix format --check-formatted` exits 0 on both Elixir 1.18.4 (Docker) and 1.19.5 (local) at HEAD `750e5ed`.

### Lane 2 — Credo Strict (commit `1476305`)

**Root cause (two issues).**

1. `lib/mix/tasks/mailglass.publish.check.ex:507` — `Enum.reject |> Enum.reject` chained pipe, flagged by Credo's `Refactor.FilterFilter` ("One Enum.reject is more efficient").
2. `test/support/citext_probe.ex:50` — `try/rescue` block contained a `raise` on the exhaustion branch, flagged by Credo's `Warning.RaiseInsideRescue` ("Use reraise to preserve the original stacktrace"). The rescue is **intentionally non-reraising** (the `Postgrex.Error` is the *expected* poisoned-OID retry signal — reraising defeats the probe loop), so the warning is technically correct but contextually wrong for this site.

**Fix.**

1. Collapsed `Enum.reject(required, &glob_entry?/1) |> Enum.reject(&MapSet.member?(paths, &1))` into a single `Enum.reject/2` with a combined predicate.
2. Extracted the `try/rescue` into `attempt_probe/2` so the `raise` (on probe exhaustion) lives in the *caller*, outside any rescue block. The rescue itself now only returns `:rescued`. Behaviour is bit-identical; Credo no longer fires.

(Trailing-whitespace findings in `mailglass.gen.mailable.ex:25,52` and `webhook_case_test.exs:10,32,36,39` were already cleaned by the Lane 1 formatter rewrite.)

**Evidence.** `mix credo --strict` reports `2322 mods/funs, found no issues` at HEAD `1476305` under Elixir 1.18.4.

### Lane 3 — Dialyzer (commit `fdcbb25`)

**Root cause.** Five warnings, all suppressible by ignore-file:

- `lib/mailglass/deliverability/result.ex` × 4: `contract_supertype` warnings on `schema_version/0`, `statuses/0`, `empty_summary/0`, `empty_facts/0`. The specs are intentionally broader than the success typing — narrowing `schema_version() :: pos_integer()` to `:: 1` would force every consumer to widen on the next bump. These are **forward-compatibility contracts**, not laziness.
- `test/support/outbound_route_test_support.ex:54`: `callback_type_mismatch` on `Mailglass.TestTenancy.InvalidRoute.resolve_outbound_adapter_ref/1`. The adapter is **deliberately misshapen** — it returns `{:error, :bad_shape}` so the dispatcher's negative-path test can prove malformed shapes are rejected. The divergence IS the test contract.

**Fix.** Two ignore-file entries added to `.dialyzer_ignore.exs` (one ignore covers all 4 result.ex warnings since they share the same short_description string in the same file). Both entries have one-line `# Reason:` comments per `scripts/check_dialyzer_ignore.sh` convention. New count: 6 of 15 (D-08-07 budget cap).

**Evidence.** `bash scripts/check_dialyzer_ignore.sh` exits 0; ignore-file entries match the exact message strings dialyzer emits on Elixir 1.18.4.

### Lane 4 — Operator Browser Gate (commits `befbd02`, `0a409c8`) — RULE 4 DEVIATION

**Surface this as a Rule 4 (architectural) deviation.** The CI lane needs work outside the scope of this triage cycle. Two diagnostic cycles confirmed the Phoenix endpoint is healthy; the failure is at the Playwright / browser-auth-flow layer, which requires the user's input on the right architectural fix.

**What we know from the diagnostics (commits `befbd02` + `0a409c8`).**

After two CI re-runs with progressively richer diagnostics in `OperatorBrowserServer.run!`, the GHA log now prints the following on every run:

```
[operator-browser-server] booting
[operator-browser-server] port=4101 — starting :mailglass app
[operator-browser-server] :mailglass started — running AdminBootstrap.setup_all
[operator-browser-server] AdminBootstrap done — seeding fixtures
[operator-browser-server] tcp probe OK — port 4101 is bound
[operator-browser-server] http probe /ops/browser-login?tenant_id=browser-tenant → status 302
[operator-browser-server] http probe /dev/mail/operator → status 404
[operator-browser-server] ready at http://127.0.0.1:4101/dev/mail/operator?tenant_id=browser-tenant
```

This proves:

- The cowboy listener IS bound on port 4101 (TCP probe succeeds).
- The route `/ops/browser-login` is wired correctly and responds with the expected 302 redirect to `/ops/mail?tenant_id=browser-tenant`.
- The route `/dev/mail/operator` returns 404 because the test endpoint only has `/ops/*` routes (the dev path is a leftover string in the IO.puts URL — cosmetic only).

Yet **Playwright still times out after 5 minutes** despite the URL it polls (`/ops/browser-login`) returning a healthy 302. Per [Playwright docs](https://playwright.dev/docs/api/class-testconfig#test-config-web-server), `webServer.url` polling considers any 2xx or 3xx response as "ready", so a 302 should satisfy the gate.

**Why this is Rule 4, not a quick fix.** The remaining failure modes all require investigating the Playwright/test-architecture interface, not the mailglass codebase:

1. Playwright may be following the 302 redirect, hitting `/ops/mail?tenant_id=browser-tenant` (the LiveView dashboard), and getting an auth-failure response because the BrowserSessionController set session cookies on the *previous* request that aren't carried forward into the redirect-following GET.
2. Playwright's `webServer.url` may not be configured for `redirect: false` semantics; the redirect-target's response is what's gating, not the 302 itself.
3. There may be a CSP or origin-check on the `/ops/mail` LiveView mount that rejects requests from the Playwright user-agent.
4. The endpoint may need additional plugs (Plug.Parsers, Plug.MethodOverride, Plug.RequestId) that the synthetic `MailglassAdmin.TestAdopter.Endpoint` (test/support/endpoint_case.ex:128) is missing — this could cause LiveView mount to fail silently.

Picking one of (1)–(4) and applying it would be a speculative architectural fix. The right path is for the user / Phase 05 closeout owner to:

- Reproduce the failure end-to-end against a local Elixir 1.18/OTP 27 + Node 22 + Postgres-16 stack (Docker Compose recipe needed).
- Decide whether the Operator Browser Gate stays a strict gate (in which case the synthetic endpoint needs hardening to be a complete Phoenix endpoint) OR drops to advisory (`continue-on-error: true`) until Phase 09 properly exercises the browser flow.

**What landed (despite the failure).**

1. `mailglass_admin/test/support/operator_browser_server.ex` (commit `befbd02` + `0a409c8`) — IO.puts at each boot stage AND TCP/HTTP probes that report the actual port-binding + URL-path state. **This is the diagnostic baseline** for whoever picks up the Rule 4 follow-up: any future failure will surface at one of the printed lines, not as a 5-minute silent freeze.
2. `mailglass_admin/playwright.config.cjs` (commit `befbd02`) — `webServer.timeout` raised from 120s to 300s; `stdout`/`stderr` set to `pipe` so the IO.puts traces reach the GHA log.

These changes make the lane **diagnosable on every run** going forward; they do NOT make the lane green.

**Does this block release?** Maybe. The publish-hex.yml `gate-ci-green` check requires every `ci.yml` lane to be green. With Operator Browser Gate red, Plan 04's dry-run dispatch will continue to be blocked until either (a) the lane is fixed, or (b) the lane is moved to advisory. Recommendation: drop Operator Browser Gate to advisory for the v1.0/1.1 publish ceremony only (it's a NEW lane that has never gated a successful publish), and re-strict it after Phase 05 closeout.

### Lane 5 — Support Contract Admin (commit `27ce54e`)

**Root cause.** New lane added in `6b4732f`; never passed on `main`. The lane runs `cd mailglass_admin && mix verify.support_contract.admin`, which boots `mailglass_admin/test/test_helper.exs`. The test helper runs the core repo migrations against `MailglassAdmin.TestRepo` (database `mailglass_test`) — but the lane has **no `mix ecto.create` step at all**. Other CI lanes (`support_contract_core`, `operator_browser_gate`, `installer_golden_gate`) all create the database from the root project context where `Mailglass.TestRepo` is loaded; this lane was a copy-paste miss.

**Evidence in CI log.** `Postgrex.Error FATAL 3D000 (invalid_catalog_name) database "mailglass_test" does not exist` repeated 4× before `Could not create schema migrations table`.

**Fix.** Added a "Wait for postgres + create test DB" step to the `support_contract_admin` lane, mirroring `support_contract_core` byte-for-byte (`mix ecto.create -r Mailglass.TestRepo --quiet`). Both repos point to the same database name (`mailglass_test`), so a single create from the root context satisfies both modules.

**Why this didn't surface earlier.** Phase 044.5 Plan 04's release-please-PR dry-run worked because `gate-ci-green` checked the **release-please-PR head SHA**, not main. The PR head ref doesn't have a `ci.yml` run at all (Issue A in the orchestrator brief), so the gate trivially passed. After the worktree merged to main and ci.yml ran for the first time at HEAD `6d55639`, the lane finally executed and surfaced the missing infrastructure.
