## Verified Findings (locked — do not re-derive)

These were established by reading run logs and the live GitHub API on 2026-09-18, not by reading prose.
The prose in `166-UAT.md`, `166-POSTMERGE-EVIDENCE.md` and session memory said something different and
was **wrong**; see `.planning/v2.8-MILESTONE-AUDIT.md` § "The one thing actually blocking closure".

- **F-01: The mechanism.** `release-preflight` (`:71-163`) reads the checked-out `main` manifest
  (`2.6.0/2.6.0/2.3.0`), finds all three tags present, logs *"All expected release tags already
  exist"*, and sets `should_run=false` at `:132-136`. That is **correct** for its own question — the
  release-please action should not re-run.
- **F-02: The defect.** Both evidence-producing steps are gated on that same flag:
  - `:517-518` `Discover an open Release Please proposal before capture` (`id: proposal-discovery`)
  - `:602-603` `Capture Release Please proposal identity without activation` (`id: capture-proposal`)
  With both skipped, the writer's override branch at `:826-829` sees an empty `DISCOVERY_STATUS` and
  never fires, so the initialized defaults from `:823-824` stand — `cannot-check` /
  `github_evidence_unavailable`. `:857` and `:885` then fail the job.
- **F-03: It is permanent, not transient.** `main`'s manifest equals the published tags in the steady
  state after *every* completed close-out. 23 consecutive reds as of 2026-09-18T16:27Z.
- **F-04: Not a rate limit.** `gh api rate_limit` read 5000/5000. Both the push run (`35361151297`)
  and the schedule run (`35368608097`) at `dcbda58f` ran exactly two steps —
  `Detect already-tagged release PR` → `Write proposal-only release control result` — with the
  release-please action, discovery and capture all skipped. Same verdict from both triggers, so this
  is *not* the `event`-scoped split that #278 fixed.
- **F-05: The regression window is v2.8.** The reds begin exactly at `7e9617b2` (2026-09-17T19:39Z,
  first post-close-out push carrying a shippable commit). The runs immediately before — `b4dd27f0`
  and the 2.6.0 tag SHA `6a0447a9` — were green with `pending` / `no_open_proposal`, proving discovery
  *did* report a verdict under the pre-v2.8 workflow.

## Implementation Decisions

- **D-01: `should_run` conflates two questions.** "Should the release-please *action* run?" (answered
  by tag existence — correct today) and "can the control gather evidence?" (always yes in proposal
  mode). The fix separates them. Two candidate shapes, both acceptable in principle; the planner picks
  one on the research evidence and records why:
  - **(a)** un-gate `proposal-discovery` from `should_run` so it reports `no_open_proposal` /
    hands off to capture on its own; or
  - **(b)** have the preflight short-circuit emit a named, non-alarm verdict for the proposal control
    (a second preflight output consumed by the writer).
- **D-02: `cannot-check` must never report as `pass`.** This is CTRL-03's own explicit clause. Whatever
  reason string the fixed path emits, it must be a *positive observation* ("no open proposal", "an
  open proposal was discovered and its identity captured"), never a renamed non-verdict.
- **D-03: Ordering hazard if (a) is chosen.** `capture-proposal`'s own comment (`:682-684`) says it
  captures identity *only after the sibling-pin sync has settled the release branch* — and that sync
  step (`:391-392`) is itself gated on `should_run == 'true'`. Un-gating capture without un-gating the
  sync would capture a pre-sync digest. The planner must resolve this explicitly: either keep capture
  gated and let discovery alone carry the verdict, or establish that an un-synced capture is correct
  in the `should_run=false` case. **This is the trap in this phase.**
- **D-04: The writer's override predicate is load-bearing.** `:826` fires only when
  `CAPTURE_OUTCOME == skipped` AND `CANDIDATE_DIGEST` is empty AND both `DISCOVERY_*` are non-empty.
  Any fix must keep all four conditions coherent, and the `case` at `:831-834` still whitelists exactly
  `pass|blocked|cannot-check|pending`.
- **D-05: The two fail points are duplicated.** The predicate
  `[ "$status" = pass ] || { [ "$status" = pending ] && [ "$reason" = no_open_proposal ]; }` appears
  twice — at `:857` (inside the writer) and at `:885` (the dedicated
  `Fail non-pass proposal control result after evidence upload` step, `:879-885`). They must stay
  identical. If the fix introduces a new legitimate pass reason, **both** change together, and that
  widening is the one place this phase comes closest to the prohibition — it must be justified in the
  plan as admitting a *truthful observation*, not as suppressing a failure.
- **D-06: Correct CTRL-02's requirement prose.** `REQUIREMENTS.md:78-81` still says the fix is
  *"removing the redundant API work that trips the rate limit."* The audit refuted the rate-limit
  diagnosis. The **Accept clause stays as written** (it is correct and still the bar); only the
  mechanism sentence is corrected. This is a DOCS-01-class truthfulness fix and belongs in this phase.

## Acceptance (from REQUIREMENTS.md, unchanged)

- **CTRL-03:** *"three consecutive pushes to `main` produce `success`, and `push` and `schedule` at the

Both are post-merge observations. Expect this phase to end `human_needed` / evidence-pending exactly
