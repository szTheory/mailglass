## Pattern Assignments

### 1. `.github/workflows/release-please.yml` — the verdict-emitting branch shape

**Analog:** the `0)` arm of the same `case "$count"` inside the step
`- name: Discover an open Release Please proposal before capture` (`id: proposal-discovery`).

**Grep anchor:** `grep -n 'count=$(jq -er .length. <<<"$prs")' .github/workflows/release-please.yml`

**Core pattern — how a case arm sets a verdict (verbatim, ~:580-598):**
```bash
          count=$(jq -er 'length' <<<"$prs")
          case "$count" in
            0)
              should_capture=false
              result_status=pending
              result_reason=no_open_proposal
              ;;
            1)
              # Capture retains the existing exact identity and candidate
              # validation semantics for an active proposal.
              ;;
            *)
              # Keep capture authoritative for the existing multiple-proposal
              # blocked classification rather than converting ambiguity into
              # a successful pending observation.
              ;;
          esac

          printf 'should_capture=%s\nresult_status=%s\nresult_reason=%s\n' "$should_capture" "$result_status" "$result_reason" >> "$GITHUB_OUTPUT"
```

**The three properties a new arm MUST copy:**
1. Set all three shell locals (`should_capture`, `result_status`, `result_reason`) — never leave any at
   the initialized empty string (`should_capture=true` / `result_status=""` / `result_reason=""`, grep
   anchor `should_capture=true`). Empty `result_status`/`result_reason` is precisely what makes the
   writer's override predicate not fire.
2. Do **not** write `$GITHUB_OUTPUT` inside the arm. There is exactly **one** trailing `printf ... >>
   "$GITHUB_OUTPUT"` at the end of the step body that all non-error arms fall through to.
3. Bare unquoted literals on the RHS (`result_status=pending`), matching the `0)` arm exactly.

**The one exception (early-exit error path) — do not copy this shape for a pending verdict:**
```bash
          if ! prs=$(retry_gh gh pr list --head release-please--branches--main --base main --state open --json number,headRefOid,baseRefOid); then
            should_capture=false
            result_status=cannot-check
            result_reason=github_evidence_unavailable
            printf 'should_capture=%s\nresult_status=%s\nresult_reason=%s\n' "$should_capture" "$result_status" "$result_reason" >> "$GITHUB_OUTPUT"
            exit 1
          fi
```
This arm writes output *and* `exit 1` inline because it is the failure path. A new truthful `pending`
verdict must use the **fall-through** shape (pattern above), not this one — it must exit 0.

### 3. `.github/workflows/release-please.yml` — the two duplicated pass predicates (D-05)

`printf 'reason=%s\n' "$reason"` block):
```bash
          [ "$status" = pass ] || { [ "$status" = pending ] && [ "$reason" = no_open_proposal ]; }
```

**Site B — the dedicated gate step, entire step verbatim** (anchor:
`- name: Fail non-pass proposal control result after evidence upload`):
```yaml
      - name: Fail non-pass proposal control result after evidence upload
        if: ${{ always() && github.event.inputs.candidate_digest == '' }}
        env:
          RESULT_STATUS: ${{ steps.proposal-control-result.outputs.status }}
          RESULT_REASON: ${{ steps.proposal-control-result.outputs.reason }}

          [ "$RESULT_STATUS" = pass ] || { [ "$RESULT_STATUS" = pending ] && [ "$RESULT_REASON" = no_open_proposal ]; }
```
Note the twins differ only in **variable names** (`$status`/`$reason` vs `$RESULT_STATUS`/`$RESULT_REASON`).
Any added `||` clause must be structurally identical at both sites, differing only by those names.

**The status whitelist is a DIFFERENT piece of code — confirmed it needs no edit for a new reason**
(anchor: `pass|blocked|cannot-check|pending) ;;`):
```bash
          if [ "${CAPTURE_OUTCOME:-skipped}" = skipped ] && [ -z "${CANDIDATE_DIGEST:-}" ] && [ -n "${DISCOVERY_STATUS:-}" ] && [ -n "${DISCOVERY_REASON:-}" ]; then
            status="$DISCOVERY_STATUS"
            reason="$DISCOVERY_REASON"
          fi

          case "$status" in
            pass|blocked|cannot-check|pending) ;;
            *) status=cannot-check; reason=invalid_capture_result ;;
          esac
```
It inspects `$status` only. A new `pending`+new-reason pair passes it unmodified. (Confirms RESEARCH.md
Pitfall 3.) Do **not** edit this `case`.

### 4. `test/scripts/release_trigger_recovery_test.exs` — extract a named step's bash body and run it

**Analog:** `"scheduled discovery preserves capture for active or ambiguous proposals and fails unavailable evidence"`.

**The extraction chain — three helpers, reuse them, do not invent a parallel harness:**

`extract_step_block!/2` → `extract_bounded_block!/3` (grabs the step by its `- name:` header up to the
next `      - ` sibling):
```elixir
  defp extract_step_block!(source, name) do
    extract_bounded_block!(source, "      - name: #{name}", "step #{name}")
  end

  defp extract_bounded_block!(source, header, description) do
    lines = String.split(source, "\n")
    start_index = Enum.find_index(lines, &(&1 == header))

    assert start_index != nil, "expected #{description} header #{inspect(header)}"

    block =
      lines
      |> Enum.drop(start_index)
      |> Enum.take_while(fn line ->
        line == header or line == "" or not String.starts_with?(line, "      - ")
      end)
      |> Enum.join("\n")

    assert String.trim(block) != "", "#{description} block must not be empty"
    block
  end
```

`proposal_result_script/1` (splits off the `run: |` body and de-indents 10 spaces — this is the helper
used for discovery, writer, and gate alike; `capture_script/1` is a literal alias for it):
```elixir
  defp proposal_result_script(result) do
    case String.split(result, ~r/^\s*run: \|\n/m, parts: 2) do
      [_, script] when script != "" ->
        script
        |> String.split("\n")
        |> Enum.map_join("\n", &String.replace_prefix(&1, "          ", ""))

      _ ->
        raise ArgumentError, "could not extract the proposal result shell script"
    end
  end
```

`read_output!/1` (parses the fake `$GITHUB_OUTPUT` file into a map):
```elixir
  defp read_output!(path) do
    path
    |> File.read!()
    |> String.split("\n", trim: true)
    |> Map.new(fn line ->
      [key, value] = String.split(line, "=", parts: 2)
      {key, value}
    end)
  end
```

**Full table-driven test to mirror (verbatim) — this is the template for the new
`should_run=false` × `{0, 1, many}` table:**
```elixir
  test "scheduled discovery preserves capture for active or ambiguous proposals and fails unavailable evidence" do
    discovery =
      workflow_source()
      |> extract_step_block!("Discover an open Release Please proposal before capture")

    for {mode, expected_capture, expected_status, expected_reason, expected_exit} <- [
          {:one, "true", "", "", 0},
          {:many, "true", "", "", 0},
          {:unavailable, "false", "cannot-check", "github_evidence_unavailable", 1}
        ] do
      with_idle_schedule_fixture(mode, fn temp_dir, env ->
        script = Path.join(temp_dir, "discovery.sh")
        File.write!(script, proposal_result_script(discovery))

        assert {_, ^expected_exit} =
                 System.cmd("bash", [script],
                   cd: @repo_root,
                   env: Map.to_list(env),
                   stderr_to_stdout: true
                 )

        outputs = read_output!(env["GITHUB_OUTPUT"])
        assert outputs["should_capture"] == expected_capture
        assert outputs["result_status"] == expected_status
        assert outputs["result_reason"] == expected_reason
      end)
    end

```

add a `with_fake_gh(:all_present, ...)` variant. `with_fake_gh/3` is the **preflight-only** fixture: its
fake `gh` answers `api:` and `pr:` (`gh pr view` label text), and its env map has **no**
`FAKE_DISCOVERY`, no `RUNNER_TEMP`, no `EVENT_NAME`, no `COMMAND_LOG` — so the discovery/writer/gate
bodies cannot run under it as written. The fixture that *can* run discovery is
`with_idle_schedule_fixture/3`, whose fake `gh` handles the exact `pr list ...` command line:
```elixir
    if [ "$*" = "pr list --head release-please--branches--main --base main --state open --json number,headRefOid,baseRefOid" ]; then
      case "$FAKE_DISCOVERY" in
        none) printf '[]\\n' ;;
        one) printf '[{"number":222,"headRefOid":"bbbb...","baseRefOid":"cccc..."}]\\n' ;;
        many) printf '[{"number":222},{"number":223}]\\n' ;;
        unavailable) printf 'simulated GitHub API failure\\n' >&2; exit 1 ;;
      esac
      exit 0
    fi
```
and whose env map is the one to extend:
```elixir
    env = %{
      "PATH" => fake_bin <> ":" <> System.get_env("PATH"),
      "GH_REPO" => "test-owner/test-repo",
      "GH_LOG" => Path.join(temp_dir, "gh.log"),
      "COMMAND_LOG" => Path.join(temp_dir, "command.log"),
      "GITHUB_OUTPUT" => Path.join(temp_dir, "github-output"),
      "GITHUB_STEP_SUMMARY" => Path.join(temp_dir, "summary"),
      "RUNNER_TEMP" => temp_dir,
      "EVENT_NAME" => event_name,
      "RUN_ID" => "16208",
```

**Recommended shape:** rather than a new fixture, follow the precedent already set for the `event_name`
axis — `with_idle_schedule_fixture/2` delegates to a 3-arity version that takes the extra axis:
```elixir

  defp with_idle_schedule_fixture(mode, event_name, fun) do
```

keeps all existing call sites untouched. Note its fake `gh` also already answers the preflight's tag

`should_run=false` it must either flip those to 200 or inject `SHOULD_RUN=false` directly. Injecting the
env value directly matches how the existing writer tests inject `DISCOVERY_STATUS` (pattern 5).

### 5. `test/scripts/release_trigger_recovery_test.exs` — end-to-end discovery → writer → gate pin

**Analog:** `"a push run with no open proposal reaches the same pending verdict a scheduled run does"` —
the closest existing template for a new `should_run=false` end-to-end pin. It is shorter and more
focused than the `an empty-digest schedule records bounded pending evidence...` test (which also asserts
step ordering and the `GH_LOG` call trace).

**The three-script setup + hand-off convention (verbatim):**
```elixir
    source = workflow_source()

    discovery =
      extract_step_block!(source, "Discover an open Release Please proposal before capture")

    result = extract_step_block!(source, "Write proposal-only release control result")

    gate =
      extract_step_block!(source, "Fail non-pass proposal control result after evidence upload")

    with_idle_schedule_fixture(:none, "push", fn temp_dir, env ->
      File.write!(Path.join(temp_dir, "discovery.sh"), proposal_result_script(discovery))
      File.write!(Path.join(temp_dir, "result.sh"), proposal_result_script(result))
      File.write!(Path.join(temp_dir, "gate.sh"), proposal_result_script(gate))
```

**Step 1 — run discovery, read its outputs:**
```elixir
      assert {_, 0} =
               System.cmd("bash", [Path.join(temp_dir, "discovery.sh")],
                 cd: @repo_root,
                 env: Map.to_list(env),
                 stderr_to_stdout: true
               )

      discovery_outputs = read_output!(env["GITHUB_OUTPUT"])
      assert discovery_outputs["should_capture"] == "false"
      assert discovery_outputs["result_status"] == "pending"
      assert discovery_outputs["result_reason"] == "no_open_proposal"
```

**Step 2 — hand discovery's outputs to the writer as env, simulating the skipped capture.** This is the
key convention: the test manually reproduces the `env:` mapping of the writer step, including
`CAPTURE_OUTCOME => "skipped"` and empty `CAPTURE_STATUS`/`CAPTURE_REASON`, which is exactly the
`should_run=false` world state:
```elixir
      writer_env =
        Map.merge(env, %{
          "CAPTURE_OUTCOME" => "skipped",
          "CAPTURE_STATUS" => "",
          "CAPTURE_REASON" => "",
          "DISCOVERY_STATUS" => discovery_outputs["result_status"],
          "DISCOVERY_REASON" => discovery_outputs["result_reason"],
          "PROPOSAL_HEAD" => "",
          "SOURCE_SHA" => ""
        })

      assert {_, 0} =
               System.cmd("bash", [Path.join(temp_dir, "result.sh")],
                 cd: @repo_root,
                 env: Map.to_list(writer_env),
                 stderr_to_stdout: true
               )
```

**Step 3 — assert on the persisted artifact, then drive the gate from that artifact's own values:**
```elixir
      json =
        temp_dir
        |> Path.join("release-proposal-control-result.json")
        |> File.read!()
        |> Jason.decode!()

      assert Map.take(json, ["status", "reason", "event_name"]) == %{
               "status" => "pending",
               "reason" => "no_open_proposal",
               "event_name" => "push"
             }

      # The gate is the step that actually reddened main.
      assert {_, 0} =
               System.cmd(
                 "bash",
                 [Path.join(temp_dir, "gate.sh")],
                 env: [
                   {"RESULT_STATUS", json["status"]},
                   {"RESULT_REASON", json["reason"]}
                 ],
                 stderr_to_stdout: true
               )

      # Nothing may merge, tag, or push on this path.
      refute File.read!(env["COMMAND_LOG"]) =~
               ~r/(gh pr merge|git tag|gh release|git push|protected-dispatch)/
    end)
```
Feeding the gate from `json["status"]`/`json["reason"]` (not from hardcoded strings) is what makes this
test catch a D-05 divergence between the twin predicates — copy that exactly.

**For the `cannot-check`-never-passes negative case**, the existing convention is a non-zero expected
exit asserted via a pinned match (`assert {_, ^expected_exit} = System.cmd(...)`), as in the
`{:unavailable, ..., 1}` table row in pattern 4.

### 6. `test/scripts/release_trigger_recovery_test.exs` — "this `if:` guard is still there" mutation test

**Analog:** `"release action is mutually guarded by preflight output"` — the template for the D-03
regression test that `capture-proposal` stays gated on `should_run == 'true'`.

```elixir
  test "release action is mutually guarded by preflight output" do
    source = workflow_source()
    action = extract_action_block!(source, "release")

    assert action =~ "googleapis/release-please-action@"
    assert release_action_guarded?(source)

    refute release_action_guarded?(
             String.replace(source, "steps.release-preflight.outputs.should_run == 'true'", "true",
               global: false
             )
           )
  end
```
with its predicate helper:
```elixir
  defp release_action_guarded?(source) do
    action = extract_action_block!(source, "release")

    action =~ "uses: googleapis/release-please-action@" and
      action =~ "steps.release-preflight.outputs.should_run == 'true'" and
      action =~ "steps.protected-dispatch.outputs.content_verified == 'true'" and
      action =~ "steps.protected-merge.outcome == 'success'"
  end
```
**The pattern to copy:** a `<thing>_guarded?/1` private predicate that extracts the block and `and`s a
list of literal substring assertions, then a test that asserts it true on the real source **and**
`refute`s it on a mutated source with `global: false`. A new `capture_gated_on_should_run?/1` should
assert the capture step block contains all three of
`steps.release-preflight.outputs.should_run == 'true'`,
`github.event.inputs.candidate_digest == ''`, and
`steps.proposal-discovery.outputs.should_capture != 'false'`.

**Also reuse `step_precedes?/2`** for the ordering facts (already used to pin
`Sync sibling package -> ... ` before discovery, and discovery before capture):
```elixir
  defp step_precedes?(source, first_name, second_name) do
    {first, _} = :binary.match(source, "- name: #{first_name}")
    {second, _} = :binary.match(source, "- name: #{second_name}")
    first < second
  end
```

**Security-guard grep test (T-166-12 pattern):** the un-gated discovery must *retain*
`github.event.inputs.candidate_digest == ''`. Assert that with the same substring-on-extracted-block
shape, and mutation-`refute` it.

## Shared Patterns

### Reason-string naming convention

**Source:** `scripts/scheduled_control_evidence.sh` (the sibling scheduled-control classifier that
*consumes* this workflow's artifact via `scheduled_control_evidence.sh bind --control release-please`).

The closed status enum is shared and validated there:
```bash
  if ! jq -e '.status == "pass" or .status == "blocked" or .status == "cannot-check" or .status == "pending"' "$temporary" >/dev/null; then
    jq -n \
      --arg status "cannot-check" \
      --arg reason "source_status_invalid" \
      '{status: $status, reason: $reason}' >"$temporary"
    bind_failed=true
  fi
```
**Implication:** a new top-level status is impossible without editing this script too. `pending` + a new
reason is the only low-coupling move — confirming RESEARCH.md's anti-pattern call.

Existing reason strings across both files: `no_open_proposal`, `github_evidence_unavailable`,
`invalid_capture_result`, `source_result_missing`, `source_result_invalid`, `source_status_invalid`,
`source_provenance_mismatch`, `all_controls_current`, `awaiting_current_main_schedule`.

**Convention:** lowercase `snake_case`, no prefix, a **noun phrase describing the observed world state**
— not an instruction and not an error code. Crucially, `awaiting_current_main_schedule` is the direct
precedent for a "we looked, and the thing we're waiting on hasn't happened yet" reason paired with
`status: "pending"`. It is exactly the class of verdict this phase needs.

**Applies to:** the new count==1/`should_run=false` reason. RESEARCH.md's proposed
`proposal_awaiting_release_action` fits this convention (noun phrase, snake_case, positive observation,
`awaiting_` prefix matching the existing sibling). Pattern-conformant alternatives if renamed:
`proposal_awaiting_release_run`, `open_proposal_not_yet_released`.

### Fail-closed comment discipline

**Source:** `.github/workflows/release-please.yml`, the comment block immediately above the discovery
step (grep anchor: `This discovery is deliberately NOT scoped to`).

Every non-obvious control decision in this file carries a comment stating **the incident it prevents**,
with a SHA, and often a requirement ID (`# CTRL-03 (#166-04):`, `# CTRL-02 (#166-04):`). The new branch
and the widened predicates must carry the same: which requirement, which run/SHA evidence, and why this
is a truthful observation rather than a suppressed failure (D-05's justification burden).

### `set -euo pipefail` + defaulted expansion

Every `run: |` body in the proposal path opens with `set -euo pipefail`. Under `set -u`, any env var
that may be unset is read as `"${VAR:-}"` (see `"${CAPTURE_OUTCOME:-skipped}"`, `"${CANDIDATE_DIGEST:-}"`,
`"${DISCOVERY_STATUS:-}"`). A new `SHOULD_RUN` read must use `"${SHOULD_RUN:-}"`.

### Requirements-prose correction (D-06)

**Source/analog:** the CTRL-01 entry directly above CTRL-02 in `.planning/REQUIREMENTS.md` (already in
its corrected, shipped form). The house shape is: a `- [ ] **ID**:` bullet, a mechanism paragraph, then
an italic `*Accept:*` clause, optionally an italic `*Note:*` clause.

Current CTRL-02/CTRL-03 text to correct (grep anchor: `removing the redundant API work that trips the rate limit`):
```markdown
- [ ] **CTRL-02**: `release-please` no longer re-runs the action against an already-tagged SHA on the
      push event. The tagged-PR preflight skip is restored for `push` in proposal mode
      (`release-please.yml` ~L92), removing the redundant API work that trips the rate limit.
      *Accept:* the merge of a `chore: release main` PR produces a green `release-please` push run.
```
Per D-06 only the mechanism sentence changes; the `*Accept:*` line is verbatim-preserved. Note CTRL-03
carries a `*Note:*` line asserting the same refuted secondary-rate-limit mechanism (grep anchor:
`research verified this is a **secondary** rate limit`) — flag it to the planner as the same D-06 class
of untruth in the adjacent requirement, and note the CONTEXT.md scope says the Accept clauses stay.
