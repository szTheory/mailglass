# Phase 167.1 Plan 01: Unblock proposal-discovery from should_run Summary

**Split `proposal-discovery`'s `count==1`/`count>1` case arms on a threaded `should_run` flag so the control reaches a truthful `pending`/`blocked` verdict in the permanent post-close-out steady state instead of falling through to `cannot-check`, with the twin pass predicates widened by exactly one D-05-justified reason and all five reachable world states pinned by executing the workflow's own bash bodies.**

## Performance

- **Duration:** 24 min
- **Tasks:** 3
- **Files modified:** 2 (`.github/workflows/release-please.yml`, `test/scripts/release_trigger_recovery_test.exs`)

## Accomplishments

- Added a `SHOULD_RUN` axis to `with_idle_schedule_fixture` (4-arity, defaulted `"true"`) so tests can drive the preflight's verdict directly into the extracted discovery body under `set -u`.
- Un-gated `proposal-discovery`'s `if:` from `should_run` (retaining the `candidate_digest == ''` guard) and threaded `should_run` into the step's `env:` as `SHOULD_RUN` — the first env-threading of a preflight output in this file (still exactly 7 references to `steps.release-preflight.outputs`: 6 untouched `if:` sites + this new `env:` site).
- Split the `count==1` arm: `should_run=true` keeps today's hand-off to capture byte-for-byte; `should_run=false` emits `pending` / `proposal_awaiting_release_action` — a positive observation reachable only after `gh pr list` succeeded and exactly one open proposal was counted.
- Split the `count>1` (`*)`) arm the same way: `should_run=false` reproduces capture's own `blocked` / `multiple_open_proposals` verdict verbatim, adding no admissible pass pair.
- Widened both twin pass predicates identically to admit the new `pending` + `proposal_awaiting_release_action` pair — no other status or reason admitted, and the `pass|blocked|cannot-check|pending` status whitelist was not touched.
- Left `capture-proposal`'s `if:` byte-identical (still gated on `should_run == 'true'`) so an un-gated discovery can never validate a pre-sibling-sync digest.
- Pinned all five reachable world states, the twin-predicate parity, two negative controls (`cannot-check`/`blocked` never pass), and both guards that must not move (`capture-proposal`'s three-clause gate, discovery's candidate-digest bar) — 7 new tests, all runtime assertions against the workflow's own extracted bash bodies, none source-grep-only.

## Decisions Made

- **D-05 widening scope, explicit:** exactly one new admissible pass pair was added to both predicates: `status=pending` AND `reason=proposal_awaiting_release_action`. It is emitted only from the `1)` arm of `case "$count"`, only after `gh pr list` succeeded and `jq -er 'length'` returned exactly `1`, never as a `*)` default or an initializer. No other status or reason is admitted anywhere in this plan.
- **`capture-proposal` untouched by design:** its `if:` still requires `steps.release-preflight.outputs.should_run == 'true'`. The sibling-pin sync that settles the release branch is itself gated on `should_run`, so an un-gated capture would validate a pre-sync digest — that is the trap this plan deliberately avoided (D-03).
- **The `*)` arm gets a name, not a pass:** under `should_run=false`, more-than-one-open-proposal now reports `blocked` / `multiple_open_proposals` instead of falling through to `cannot-check`'s defaults. `blocked` remains outside both pass predicates, so this is a truthfulness improvement with zero change to gate behavior for that state.
- **Test infrastructure precedent followed, not invented:** the new `SHOULD_RUN` axis mirrors the existing `event_name` axis precedent (2-arity delegates to 3-arity delegates to 4-arity, all with defaults), per `167.1-PATTERNS.md` § 4's correction of `RESEARCH.md`'s Wave-0 wording.

## Issues Encountered

- The negative-control test (Task 3c) initially asserted the writer script (`result.sh`) exits 0 for `cannot-check`/`blocked` inputs, mirroring the happy-path e2e pin's shape too literally. In fact the writer step's own trailing pass-predicate assertion means it deliberately exits non-zero for a non-pass verdict too (which is exactly why the real workflow marks that step `continue-on-error: true` — it is itself a belt-and-suspenders gate, not just a diagnostic write). Fixed by not asserting the writer's exit code and instead asserting only on the persisted JSON artifact (written before the trailing assertion runs) and the dedicated gate step's exit code. This is a same-task self-correction, not a plan deviation requiring a rule.
- The first draft of the `discovery_bars_candidate_digest?/1` mutation test used the bare substring `"github.event.inputs.candidate_digest == ''"` for `String.replace/4` with `global: false` — this string is not unique in the file (11 occurrences), so the mutation would have silently patched an unrelated `skip-github-release:` input line rather than discovery's `if:`. Fixed by mutating the full unique line `if: ${{ github.event.inputs.candidate_digest == '' }}` instead (verified unique via `grep -cF`).
