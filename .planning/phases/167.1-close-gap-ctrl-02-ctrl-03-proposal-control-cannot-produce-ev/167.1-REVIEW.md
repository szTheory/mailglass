# Phase 167.1: Code Review Report

**Reviewed:** 2026-09-18T14:15:00Z
**Depth:** standard
**Files Reviewed:** 2
**Status:** issues_found

## Summary

This phase un-gates `proposal-discovery` from `should_run` (retaining only the
`candidate_digest == ''` guard), adds two new discovery-outcome branches
(`pending`/`proposal_awaiting_release_action` for exactly one open proposal,
`blocked`/`multiple_open_proposals` for more than one) that only fire when
`should_run != 'true'`, and widens both proposal-control pass predicates
(the writer's inline trailing assertion and the dedicated "Fail non-pass..."
gate) to admit the new `pending`/`proposal_awaiting_release_action` pair
alongside the existing `pending`/`no_open_proposal` pair. I traced every
reachable `(count, should_run)` combination by hand and ran the full test
file locally (`mix test test/scripts/release_trigger_recovery_test.exs`,
27/27 passing) plus `shellcheck` on the extracted discovery script — no
syntax errors, no way for `cannot-check` or `blocked` to reach the pass
predicate, and the protected candidate-digest dispatch path (workflow_dispatch
with a non-empty `candidate_digest`) remains structurally unreachable from the
discovery step (its `if:` is the single, unique `github.event.inputs.candidate_digest
== ''` literal in the file — confirmed via grep, so the T-167.1-01 mutation
test can't be silently patching an unrelated site). `capture-proposal` is
still gated on `steps.release-preflight.outputs.should_run == 'true'`
unchanged. The two pass predicates are byte-for-byte twins modulo variable
names (`$status`/`$reason` vs `$RESULT_STATUS`/`$RESULT_REASON`) — confirmed
both by grep (exactly two `= pass ]` lines in the whole file) and by the new
dedicated D-05 test.

I did not find a way to make a non-observation pass the gate. The one
substantive finding below is a maintainability risk (duplicated magic string
literals across the fix's own load-bearing sites) rather than a functional
defect — but it's exactly the class of drift this phase exists to guard
against, so I'm flagging it as a Warning rather than Info.

## Warnings

### WR-01: `proposal_awaiting_release_action` / `no_open_proposal` are duplicated literals with no single source of truth

**File:** `.github/workflows/release-please.yml:606-610, 623-627, 889, 917`
**Issue:** The two new/existing reason strings each appear in at least three
independent places that must stay in lockstep for the fail-closed guarantee
to hold: the `case "$count"` arms in `proposal-discovery` (lines 606-610,
623-627) that *produce* `result_reason`, and the two pass predicates (line
889 in "Write proposal-only release control result", line 917 in "Fail
non-pass proposal control result after evidence upload") that *consume* it.
Nothing enforces that a reason string typo'd or renamed in the producer is
mirrored in both consumers — the D-05 test added in this phase asserts the
two *consumers* stay identical to each other, but nothing structurally ties
either consumer's literal set back to the producer's literal set. A future
edit that renames `proposal_awaiting_release_action` in the discovery step
without updating both predicates would silently convert a previously-passing
observation into a `cannot-check`-style false failure (fail-closed, so not a
security risk, but exactly the kind of stale-drift outage this phase's
change log (CTRL-02/CTRL-03, "23 consecutive reds") describes for the
*previous* generation of this same class of bug).
**Fix:** Extract the two allowed `(status, reason)` pairs into a single
named list (e.g. a small `ADMISSIBLE_PENDING_REASONS` shell array sourced by
both the writer and the gate step, or at minimum a code comment at each of
the four sites cross-referencing the other three by line-anchor) so a grep
for the reason string surfaces every site that must move together. A test
similar to the existing D-05 predicate-equality test, but that also diffs the
producer's literal reason set against the consumer's, would catch this class
of regression mechanically instead of relying on future reviewers reading the
prose comments.

## Info

### IN-01: `SHOULD_RUN` truthiness check compares against an unquoted bareword

**File:** `.github/workflows/release-please.yml:606, 623`
**Issue:** `if [ "${SHOULD_RUN:-}" != true ]; then` compares against the
unquoted word `true`. This works correctly today because `SHOULD_RUN` can
only ever be the GitHub Actions boolean-output strings `"true"` or `"false"`
(or unset), and an unquoted bareword with no metacharacters/globbing matches
behaves identically to a quoted string in `[ ... ]`. It is nonetheless
inconsistent with the rest of the same file, which quotes comparison
literals elsewhere (e.g. `[ "$status" = pending ]`), and an unquoted RHS is
a common source of shellcheck SC2086-adjacent confusion for future editors.
**Fix:** Quote it for consistency: `if [ "${SHOULD_RUN:-}" != "true" ]; then`.

### IN-02: Discovery now runs unconditionally on every non-protected trigger, including when `should_run=true` and no proposal exists

**File:** `.github/workflows/release-please.yml:516-518`
**Issue:** Not a bug — this is the intended behavior change — but worth
noting for future readers: un-gating the `if:` from `should_run` means
`proposal-discovery` now performs a `gh pr list` call on *every* push,
schedule, and digest-free `workflow_dispatch` run, even in the steady state
where `should_run=true` and release-please is about to create a brand-new
proposal (count will legitimately be 0). This is already handled correctly
(arm `0)` is unconditional and unaffected by `SHOULD_RUN`), so there's no
functional issue, but the extra API call on every trigger (previously
skipped whenever `should_run=false`) is a small, permanent increase in
`gh` call volume for a control that used to short-circuit. Out of this
review's correctness/security scope (performance is explicitly out of v1
scope), noted only so it isn't mistaken for an oversight later.
**Fix:** No action required; documenting only.
