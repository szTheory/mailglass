## CTRL-02 — harvest procedure

**Accept clause (verbatim, unchanged):** "the merge of a `chore: release main` PR produces a
green `release-please` push run."

**Trigger:** the next merge of a `chore: release main` PR (a real release proposal, e.g. the
one PR #280 currently represents, reaching a merge).

**Commands to run once the trigger has fired:**

```bash
# List the resulting push run on main
gh run list --workflow=release-please.yml --branch=main --event=push --limit=1 --json databaseId,headSha,conclusion,createdAt

# Read its conclusion and the step that distinguishes a real pass from a skip
gh run view <run-id> --json jobs --jq '.jobs[].steps[] | select(.name | test("Write proposal-only release control result|Fail non-pass proposal control result after evidence upload")) | {name, conclusion}'

# Download and inspect the persisted artifact rather than trusting the green checkmark
gh run download <run-id> -n release-proposal-control-result
cat release-proposal-control-result.json
```

The step whose outcome distinguishes a real pass from a skip: `Fail non-pass proposal control
result after evidence upload` (`release-please.yml:879-885`) must itself conclude `success`
(not `skipped`) — a `skipped` conclusion here means `should_run` short-circuited the whole path
again, which would mean Plan 01's fix did not engage.

**Expected verdict:** the run concludes `success` and uploads
`release-proposal-control-result.json` with `status=pending` /
`reason=proposal_awaiting_release_action` (if merged while another proposal is still open) or
`status=pending` / `reason=no_open_proposal` (if merged with none) — either is a pass. Do not
expect `status=pass` from a proposal-only run; per D-02 the proposal control never emits a bare
`pass` status, only a passing `pending` reason.

## CTRL-03 — harvest procedure

**Accept clause (verbatim, unchanged):** "three consecutive pushes to `main` produce
`success`, and `push` and `schedule` at the same SHA agree. **`cannot-check` must still never
report as `pass`.**"

**Trigger:** three consecutive pushes to `main`, plus at least one hourly schedule firing that
lands on a SHA a push also observed.

**Commands to run once the trigger has fired:**

```bash
# List the push runs (need 3 consecutive)
gh run list --workflow=release-please.yml --branch=main --event=push --limit=5 --json databaseId,headSha,conclusion,createdAt

# List the schedule runs over the same window
gh run list --workflow=release-please.yml --event=schedule --limit=10 --json databaseId,headSha,conclusion,createdAt

# For each SHA observed by both event types, compare status AND reason from the artifact
gh run download <push-run-id> -n release-proposal-control-result -D /tmp/push-<sha>
gh run download <schedule-run-id> -n release-proposal-control-result -D /tmp/schedule-<sha>
diff <(jq '{status, reason}' /tmp/push-<sha>/release-proposal-control-result.json) \
     <(jq '{status, reason}' /tmp/schedule-<sha>/release-proposal-control-result.json)
```

**Two facts to assert:**
1. All three push runs conclude `success`.
2. For every SHA observed by both a `push` and a `schedule` run, the two report the **same**
   `status` **and** the **same** `reason` — not merely the same job conclusion.

**Watch for the #278 signature:** the same SHA reporting *opposite* verdicts split purely by
`event` (e.g. `push` passes while `schedule` at the identical SHA reports `cannot-check`). That
signature previously indicated an event-scoped code path divergence; F-04 in `167.1-CONTEXT.md`
confirmed the 2026-09-18 reds were *not* this — both `push` (`35361151297`) and `schedule`
(`35368608097`) at `dcbda58f` agreed with each other (both skipped the same two steps). Its
reappearance here would be a genuine regression, not a repeat of the 2026-09-18 finding.

## Expected verdicts by world state

Per Plan 01's shipped verdict strings (`167.1-01-SUMMARY.md`), the repaired control should now
report the following. This table is a prediction to check the harvested evidence against, not
itself a harvested observation.

| World state | `status` | `reason` | Passes the gate? |
|---|---|---|---|
| No open proposal | `pending` | `no_open_proposal` | Yes |
| Exactly one open proposal, manifest tags already present (the state PR #280 currently produces) | `pending` | `proposal_awaiting_release_action` | Yes |
| More than one open proposal | `blocked` | `multiple_open_proposals` | **No** — fail-closed by design, not a regression |
| GitHub API failure during discovery | `cannot-check` | `github_evidence_unavailable` | **No** — fail-closed by design, not a regression; D-02 requires `cannot-check` never report as `pass` |

The last two rows are *expected* to fail the gate. That is correct fail-closed behavior: a
control that cannot observe its subject, or that observes an ambiguous subject, must not report
a pass just to keep `main` green.

## What would refute the fix

Any of the following, if observed post-merge, means Plan 01's fix did not actually work and the
gap is not closed:

- The artifact still reports the blind `cannot-check` / `github_evidence_unavailable` verdict on
  a run where `proposal-discovery` should have executed (i.e., discovery ran but still produced
  the pre-fix default rather than a positive observation).
- `proposal-discovery` shows as `skipped` on a run with no `candidate_digest` input (the
  un-gating from Plan 01 did not take effect on `main`).
- `push` and `schedule` disagree — same SHA, different `status` or `reason` — reproducing the
  #278 signature this fix was never meant to touch.
- `capture-proposal` runs (is not skipped) when `should_run=false` — this would mean the D-03
  ordering guard regressed and a pre-sibling-sync digest was captured.
