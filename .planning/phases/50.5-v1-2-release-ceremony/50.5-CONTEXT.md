### Version Computation (D-50.5-01)

**Replace `"release-as": "1.0.0"` with `"release-as": "1.2.0"` in `release-please-config.json` as part of pre-ceremony Commit A. No force needed for inbound.**

- `release-please-config.json` lines 9 + 17 carry the sticky `"release-as": "1.0.0"` from the 1.0.0 ceremony recovery (deferred-items.md item #6). This field must be addressed before release-please is triggered.
- The correct shape is: replace `"1.0.0"` with `"1.2.0"` on both `.` and `mailglass_admin` blocks in the same Commit A. This is the same mechanism used to force 1.0.0, now used to force 1.2.0 (which skips the 1.1.0 that conventional commits alone would compute).
- After the v1.2.0 ceremony settles, `"release-as": "1.2.0"` becomes the next deferred cleanup item for Phase 51 (same pattern as deferred-items.md item #6). Phase 51 removes it.
- **Inbound** (unlinked): 32 `feat:` commits touch `mailglass_inbound/` since `mailglass_inbound-v0.1.0`. Release-please computes **0.2.0 naturally** from conventional commits — no `"release-as"` override needed for inbound.

### Pre-Ceremony Commit Sequence (D-50.5-02)

**Three commits land on `main` before release-please is triggered, in this order:**

1. **Commit A — Release-engineering cleanup + version force:**
   - `release-please-config.json`: change `"release-as": "1.0.0"` → `"release-as": "1.2.0"` on both `.` and `mailglass_admin` blocks.
   - `mix.exs:5`: remove the editorial comment `# v1.0.0 cut — see Phase 044.5 release ceremony record` (deferred-items.md item #7).
   - `mailglass_inbound/mix.exs:5`: remove the editorial comment `# First Hex publish — see Phase 044.5 release ceremony record` (deferred-items.md item #7).
   - Conventional Commit: `chore(release-engineering): clean up post-1.0 publish recovery anchors + force 1.2.0 cut`

2. **Commit B — Pre-author curated CHANGELOG headers** (see D-50.5-03 for scope). Must land before release-please opens the PR, as release-please force-pushes the CHANGELOG on PR open, which would clobber hand-authored headers added after.

3. **Wait** for release-please to open the 1.2.0 PR after Commits A-B land on `main`.

Then: dry-run dispatch → merge → live publish → sandbox smoke → proof record.

This ordering is load-bearing: same as D-44.5 locked sequence. Commit A must precede release-please's PR generation so the correct version lands in the cut. Commit B must precede the release-please force-push.
