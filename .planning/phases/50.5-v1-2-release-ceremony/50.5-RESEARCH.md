The key research findings are: **both package allowlists are significantly stale** from all the v1.2 implementation work in Phases 45–50, and this must be repaired before the dry-run dispatch can succeed. The `mailglass_inbound-files.expected` is missing 39 new entries (36 lib files + 3 migrations). The CHANGELOG curation is the most content-heavy authoring work — the inbound 0.2.0 entry covers five full phases of feature work (45–49) compared to the existing `[Unreleased]` section which covers only partial Phase 46 (error structs + SES provider).

## Common Pitfalls

### Pitfall 1: Stale Package Allowlists Block Dry-Run

**What goes wrong:** `mix mailglass.publish.check` fails in the `prepublish-summary` job of the dry-run dispatch because `mailglass_inbound-files.expected`, `mailglass_admin-files.expected`, or `mailglass-files.expected` do not match the actual tarball contents.

**Why it happens:** The allowlists were last updated at Phase 44.5 (Phase 38 for core/admin). Five full implementation phases (45–50) have added new lib files, new mix tasks, new migrations, and new docs since then.

**How to avoid:** Update all three allowlist files as part of Commit A (or at minimum before the dry-run dispatch). Run `mix mailglass.publish.check --package <each>` locally to verify exit 0 before pushing.

**Warning signs:** `prepublish-summary` job exits with "Delivery blocked: missing required file" or the file counts don't match the Step Summary output.

### Pitfall 2: Release-Please Force-Push Clobbers CHANGELOG Headers

**What goes wrong:** CHANGELOG curated headers authored as a separate commit after Commit A are clobbered when release-please force-pushes the CHANGELOG on PR open.

**Why it happens:** Release-please's linked-versions plugin generates the CHANGELOG from scratch on each PR update, overwriting any manual edits that aren't already captured in the commit history before the PR opens.

**How to avoid:** Commit B (CHANGELOG curation) must land on `main` BEFORE waiting for release-please to open the PR. The ordering constraint in D-50.5-02 is load-bearing.

**Warning signs:** The release-please PR shows no curated `## What's new in 1.2.0` section in the diff, only raw commit ledger entries.

### Pitfall 3: Dry-Run Sibling MIX_PUBLISH Resolution Failure

**What goes wrong:** The `publish-admin` and `publish-inbound` jobs fail during dry-run because `MIX_PUBLISH=true mix deps.get` can't resolve `{:mailglass, "== 1.2.0"}` from Hex during a dry-run dispatch (1.2.0 isn't on Hex yet during dry-run).

**Why it happens:** This exact bug was hit in Phase 44.5 (dispatch attempt #3, run id 25506297193) and fixed in commit `a0ba244` which guards sibling `MIX_PUBLISH` steps so dry-run skips dep resolution against unpublished siblings.

**How to avoid:** The fix is already in place in `publish-hex.yml` — the `Install deps (MIX_PUBLISH=true)` step in both `publish-admin` and `publish-inbound` has `if: github.event.inputs.dry_run != 'true'`. No action needed. Just confirm the dry-run Step Summary shows these steps as "skipped" not "failed".

### Pitfall 4: Admin CHANGELOG Missing `[Unreleased]` Before Commit B

**What goes wrong:** Release-please generates the 1.2.0 admin CHANGELOG entry from raw commit ledger with no curated narrative.

**Why it happens:** `mailglass_admin/CHANGELOG.md` has no `[Unreleased]` section today — it goes directly from the header to `## [1.0.0]`. Release-please will add its own section but without the coordinated sibling note D-50.5-03 requires.

**How to avoid:** Pre-author the `## [Unreleased]` section in Commit B with the coordinated sibling note shape from `[1.0.0]` entry (lines 23–30 of `mailglass_admin/CHANGELOG.md`).

### Pitfall 5: MAINTAINING.md Sandbox Recipe Still References v1.0.0 Versions

**What goes wrong:** The smoke install step in MAINTAINING.md (line 212) still says `{:mailglass, "== 1.0.0"}, {:mailglass_admin, "== 1.0.0"}, {:mailglass_inbound, "== 0.1.0"}`.

**Why it happens:** The runbook was not updated after Phase 44.5 to be version-agnostic. For Phase 50.5, the 60-minute sandbox smoke should use `"~> 1.2"` and `"~> 0.2"` per the release notes, not pinned old versions.

**How to avoid:** Update MAINTAINING.md sandbox recipe as part of Commit A or Commit B to use `"~> 1.2"` / `"~> 0.2"`, or document in the plan that the executor uses current versions regardless of the runbook literal. Consider whether this update belongs in Phase 51 vs Phase 50.5.

### Pitfall 6: `publish.check` CHANGELOG Check Will Require 1.2.0 / 0.2.0 Sections

**What goes wrong:** The dry-run dispatch fails `verify_changelog` in `prepublish-summary` because the CHANGELOG.md files don't have sections for the target version (1.2.0 or 0.2.0).

**Why it happens:** `mix mailglass.publish.check` verifies that CHANGELOG.md contains a non-empty section for `ctx.version` (the version from `@version` in `mix.exs`). At the time of dry-run, the release-please PR has already bumped `@version` to 1.2.0/0.2.0 in the branch — so publish.check looks for those version sections. They won't exist until Commit B has landed AND release-please has generated the PR (which appends its raw ledger and updates `[Unreleased]` to `[1.2.0]`).

**How to avoid:** The dry-run dispatch runs AFTER the release-please PR is open — at that point, the PR branch has both the curated Commit B headers (now titled `[1.2.0]` and `[0.2.0]` by release-please) and the raw ledger. The CHANGELOG check should pass. The ordering (Commit B → wait for PR → dry-run) is what makes this work.
