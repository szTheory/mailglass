**Why the boundary-only ledger missed all of this — a genuine, live confirmation of the
blind spot 143-01-SUMMARY flagged, not a defect introduced by this plan.**
`Mailglass.TestSupport.SuiteTruthFormatter` probes pool mode, `Config.schema()` drift,
and baseline-table presence ONLY at `:module_finished` of an `async: false` module — once
per module, never mid-module. Three modules in this suite manipulate
`Mailglass.Config.schema()` via `Application.put_env/3` +
`:persistent_term.erase({Mailglass.Config, :schema})` inside a PER-TEST `setup`/`on_exit`
pair, not a `setup_all` — `test/mailglass/schema_isolation_integration_test.exs`,
`test/mailglass/schema_isolation_immutability_test.exs`, and
`test/mailglass/schema_prefix_hardening_test.exs`. Each test in these modules drifts the
schema and (in the normal case) restores it before the NEXT test in the SAME module
starts. Because the probe fires only once, at the end of the WHOLE module, a corruption
that occurs and self-heals between two tests inside the same module's own lifecycle is
structurally invisible to it — exactly the class of miss 143-01-SUMMARY's "Next Phase

reproduces that prediction live: real Class A/B/C symptoms occurred, and the boundary
probe correctly reported that IT observed nothing wrong AT THE BOUNDARIES IT CHECKS —
