<objective>
Harden the `NoPiiInResponseBody` egress PII guard against its real false negatives (code-review
WR-02/WR-03) so the "No PII on egress" invariant holds against the most likely future regression
shapes — without false-positiving the legitimate static-map/binary closed-code body or the
Jason-encoded `body` binary in the JSON helper. Today the check flags a body arg only for
`inspect(...)`, an `%Ecto.Changeset{}` literal, or a variable whose NAME contains
`reason`/`changeset` — so a changeset bound to `err`/`error`/`e`/`result` (WR-02), or a payload
assembled in a prior `=` assignment (WR-03), escapes it. Current `plug.ex` is clean (static body),
so this is LATENT, not an active leak; the broadening prevents the obvious refactor from silently
bypassing the guard.

Per the user's WR-02 decision (REAL ENFORCEMENT, not documentation), apply the same standard to
WR-03: the bare-variable body-arg rule (Option B) is the MANDATED mechanism — it catches BOTH the
err-named-variable shape (WR-02) AND the two-step construction shape (WR-03), where Option A
(fragment-name broadening) catches only WR-02. Option A fragment names MAY be layered on top, but
are not sufficient alone.

This plan is file-disjoint from the registration plan (45-10) and the convention plan (45-11), so
it runs in parallel. It also folds in IN-01: a one-line doc note on `gen_smtp.ex` `available?/0`
(naturally co-located optional-dep doc work).

payload), not only the two narrow shapes the original check recognized.
Output: a broadened egress check with the safe-shape carve-out preserved + a documented remaining
boundary + two regression tests (err-bound + two-step) + the IN-01 doc note.
