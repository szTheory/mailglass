<objective>
Decide the Health composition by measurement and keep the winning composition's geometry, link-landing and focus behavior under a retained browser spec.

Purpose: OUTUX-06 D-15 (bounded comparison, not presumption) and D-20 (Playwright gates).
Output: an all-eight-categories browser scenario, `e2e/phase177-health.spec.js`, `177-HEALTH-COMPARISON.md`, and, only if B wins, the B composition in production.

Orchestrator decisions recorded here (CLAUDE.md Decision Policy):
- The comparison spike runs on the real operator browser route rather than a demo Storybook iframe: the viewports 320..1440 produce exactly the UI-SPEC container widths (sidebar and padding included), which also satisfies the "real main width" backstop, and it avoids depending on the unverified demo boot (A4). Candidate B is applied to the same production DOM with an injected stylesheet (grid on `.operator-health-column`, activity placed in column 2 spanning the column-1 rows, 42rem cap lifted at >= 56rem). The spike spec is created, run and deleted in Task 2 (never committed); its raw JSON output is pasted into the comparison record.
- The long-count scenario is produced by rewriting the count text of the all-eight rows to "123,456" in the DOM before measuring (geometry only), because seeding 100,000 records per category in a browser fixture is wasteful; the component-level long-count case is already covered in plan 177-04.
- Tie-breaker order is the UI-SPEC's (CONTEXT discretion): scan path, row slack, activity subordination, fewer layout rules.
- Bundle: Tasks 1 and 3 use only committed utilities and restore the bundle after runs; Task 2 rebuilds only if B wins, using the one phase bundle procedure (revision W-8, defined in plan 177-04): `mix mailglass_admin.assets.build`, `token_parity_test.exs` and `assets_test.exs`, commit the rebuilt bundle as emitted, no manual theme-block restoring.
- Shared browser server (revision INFO): every operator-browser spec in this phase (plans 177-01, 177-04, 177-06, 177-07, 177-08, 177-11) runs against the one Playwright webServer on port 4101 and resets state through `/ops/browser-reset?scenario=...`. Browser verifies are therefore never run concurrently across plans; waves serialise them, and a stale server is killed before final runs (A7).
