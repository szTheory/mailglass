# Phase 48 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Phase goal (verbatim from ROADMAP.md):** "An operator opens `/admin/inbound` in `mailglass_admin` and gets the same observability they already have for outbound."

This is an **inheritance phase**. The entire visual and interaction language is already shipped and locked in `mailglass_admin` (Phases 5 + 22, OperatorLive). Almost every token, component, and pattern below is recorded as INHERITED — reused verbatim, never re-decided. The genuinely novel surface — the **routing-trace card** (IADM-04) — has no outbound analog and is the one place this contract specifies fresh design, built strictly from existing primitives.

## Screen Contract

The `/admin/inbound` surface is a **direct structural clone of `OperatorLive`** (`lib/mailglass_admin/operator_live.ex`). New module `MailglassAdmin.InboundLive` mirrors the same shell:

- Root: `<div data-theme="mailglass-light" class="min-h-screen bg-base-100">` → `<main class="mx-auto max-w-7xl px-4 py-6 md:px-6 md:py-8">` (INHERITED, operator_live.ex:192-193).
- Page header: `<h1 class="text-xl font-bold tracking-tight">` + a one-sentence `text-sm text-secondary` description (INHERITED, operator_live.ex:194-199).
- Flash band: success bordered `border-success bg-success/10`, error bordered `border-error bg-error/10`, both `rounded-box` (INHERITED, operator_live.ex:201-214).
- Filter card: `<section class="card rounded-box border border-base-300 bg-base-200 p-4 md:p-5">` wrapping a `<.form phx-change="validate_filters" phx-submit="apply_filters">` with a responsive grid of compact controls (INHERITED, operator_live.ex:216-240).
- Master/detail split: `<section class="mt-6 grid gap-6 lg:grid-cols-[minmax(22rem,28rem)_1fr]">` — list `<aside>` left, detail `<section>` right (INHERITED, operator_live.ex:242-303). Collapses to stacked single column below `lg`.
- Replay modal: rendered outside `<main>` at the end of the root div (INHERITED, operator_live.ex:306-311).

**Desktop layout:** two panes — inbound records list left (`minmax(22rem,28rem)`), selected-record detail right (`1fr`).
**Mobile layout:** stacked — filters, then list, then detail below.

**Detail pane visual priority (fixed order, top to bottom):**
1. Detail header (canonical `%InboundMessage{}` summary + matched mailbox + execution outcome + Replay action)
2. Execution timeline (all `ExecutionRun` rows, fresh + replay, chronological)
3. Routing-trace card — **rendered only when the selected/displayed execution outcome is `:no_match`** (otherwise omitted entirely)
4. Evidence card (raw provider source from `InboundEvidence`, PII-redacted by default)

State surfaces required: missing-tenant/empty list, no-record-selected, detail load error, no-execution-runs, replay-blocked. All four follow the inherited centered-card or bordered-band patterns.

### Routing-trace card (NET-NEW — IADM-04)

Answers "why didn't this message match `SupportMailbox`?" without `iex`. Rendered **only for a `:no_match` execution**. Data model is fully determined by `MailglassInbound.Router.Route` (4 fields: `mailbox`, `recipient`, `subject`, `headers`) and `Router.Matcher` semantics (recipient AND subject AND all-headers; each matcher is `nil`=wildcard-pass, exact-string-equality, or `Regex`). Reuse `Router.Matcher.matches_route?/2` internals so the rendered verdict matches real matcher behaviour exactly (per ROADMAP "Hardest sub-tasks").

**Visual model — a per-route diff list, each route a bordered card reusing timeline chrome:**

- Card container: `card rounded-box border border-base-300 bg-base-200 p-6`, heading `Routing trace` (`text-base font-bold`) + sub-label `text-xs text-secondary` reading `Why this message did not match`.
- One bordered sub-card per route tried (in declared order from `__mailglass_inbound_routes__/0`): `rounded-box border bg-base-100 p-4`. Route header = mailbox module name (mono) + an overall route verdict badge (`badge badge-outline badge-error` "No match" — every route is a no-match by definition on this card).
- Inside each route, a **clause table** — one row per matcher dimension that the route declares (`recipient`, `subject`, each `headers` entry). Each clause row shows three columns:
  1. **Dimension** — `Recipient` / `Subject` / `Header: <name>` (label style `text-xs font-bold uppercase tracking-[0.08em] text-secondary`).
  2. **Expected** — the route's matcher rendered as mono text: exact strings verbatim; regex shown as `~r/.../` form; a wildcard (`nil` matcher) shown as the literal `any` in `text-secondary`.
  3. **Actual** — the message's value for that dimension in mono, masked where PII per the masking rule (envelope_recipient masked via `mask_recipient/1`).
  - Each clause row carries a pass/fail marker: a `hero-check-circle` in `text-success` for a passing clause, a `hero-x-circle` in `text-error` for the failing clause. The **first failing clause** additionally gets `border-l-4 border-error pl-3` emphasis and a one-line `text-sm text-secondary` reason (e.g. `Header AND-semantics: this clause must also pass`).
- A short legend line at the bottom of the card explains the three matcher kinds (`any` = no constraint, exact = string equality, `~r/…/` = regex) and AND-semantics across clauses (all clauses in a route must pass).

This reuses ONLY existing primitives: `card`, `rounded-box`, `border-base-300`, `badge badge-outline`, `text-secondary`, mono via `.mono`, and the success/error/check/x heroicons already in the bundle. No charts, no diagrams, no new JS.

### Evidence card (NET-NEW chrome reuse — IADM-02)

Shows the raw provider source from `InboundEvidence`. PII handling is **determined by the schema**: `raw_payload` and `raw_mime` are `redact: true` (inbound_evidence.ex:34,36); `raw_headers`, `verification_facts`, `parse_warnings` are not redacted.

- Card chrome: `card rounded-box border border-base-300 bg-base-200 p-6`, heading `Raw provider source`.
- **Default state: redacted + collapsed.** Render `verification_facts` and a redacted summary (provider, payload byte size, header count) always. The raw payload / raw MIME body renders as a masked placeholder block (`mono text-xs text-secondary`) reading `Raw source redacted — reveal requires the reveal_raw capability.`
- **Reveal control:** a `Reveal raw source` button gated by `MailglassAdmin.Auth.authorize/3` with action `:reveal_raw` (extends `atom()` action type; NO new auth surface). When the capability is granted, the raw payload renders in a `<pre class="mono text-xs">` scroll region inside the card; when denied, the redacted placeholder stays and a brand-voice line explains the gate.
- Raw source, once revealed, is read-only and never editable.

## Interaction Contract

- Primary interaction is **row selection inside the master/detail**, not navigation to a separate page (INHERITED).
- **URL is the source of truth.** Selected record id + all filter params live in the query string via `handle_params` + `push_patch`, so refresh/back/forward/copied-links preserve operator context (INHERITED, operator_live.ex:69-117).
- Filters: free-text inputs submit on explicit `Open record` submit or debounced change; selects apply on change. Never per-keystroke on free-text search (INHERITED contract from Phase 22).
- Selecting a record updates the detail pane in place; do not remount the screen (INHERITED).
- **Live updates (IADM-05):** `InboundLive` subscribes on mount to `MailglassAdmin.PubSub.Topics.inbound_record_inserted/1` (per-tenant) — a NEW typed topic added to `pub_sub/topics.ex` following the existing `mailglass:`-prefixed convention (topics.ex; LINT-06 PrefixedPubSubTopics). New records appear in the list card without manual refresh. New records must NOT steal the current selection or reset filters; they prepend to the list only.
- **Replay (IADM-03):** `Replay` button in detail header → opens `InboundReplayModal` → `Confirm replay` runs `DestructiveAction.authorize/4` (action `:replay_inbound`) then `MailglassInbound.Internal.Replay`. On success a NEW `ExecutionRun` with `source: :replay` appends to the timeline (append-only — never UPDATE). On auth/availability failure, a brand-voice flash explains.
- Routing-trace card appears/disappears based purely on whether the displayed execution outcome is `:no_match`; no toggle.
- Evidence reveal is a capability-gated action, not a free toggle.
- Loading states use muted placeholder blocks, not spinners as primary layout (INHERITED).

## Accessibility Contract

- Minimum touch target `min-h-11` (44px) for list rows, buttons, selects, and filter inputs (INHERITED; the only declared spacing exception).
- Selected list row exposes state via `aria-current` / `aria-selected`, not color alone (INHERITED, deliveries_list.ex:35-36).
- Routing-trace pass/fail must NOT rely on color alone: each clause carries a check/x heroicon AND a text verdict, and the failing clause gets a left border + reason text.
- Replay modal uses the inherited modal chrome with explicit `Cancel` + `Confirm replay` buttons; focusable, dismissible via `Close`/`Cancel`.
- Evidence redaction state and reveal-denied state are communicated in text, not by absence alone.
- Transient feedback uses the polite live region (`Components.flash/1`); blocking errors use explicit heading/body copy.
- Timeline DOM order must match visible chronological order exactly (INHERITED).

## Copywriting Contract

Brand voice (CLAUDE.md / brand book §5): clear, exact, confident, warm, technical — "a thoughtful maintainer." Banned: "Oops", "Whoops", "Uh oh", "Something went wrong", any playful phrasing. The voice test greps rendered HTML; IADM-06 requires composed, specific error copy.

| Element | Copy |
|---------|------|
| Primary CTA (filter submit) | Open record |
| Empty state heading | No inbound records |
| Empty state body | No inbound records match these filters. Clear the filters or wait for the next inbound message. |
| Error state | Inbound data could not be loaded. Refresh the page or adjust the filters, then try again. |
| Destructive confirmation | Replay inbound: This re-runs mailbox routing against the stored message and records a new replay run in the append-only ledger. Confirm to replay. |

Additional required copy:

- No record selected: `Select an inbound record to inspect its routing, execution timeline, and raw source.`
- No execution runs: `No execution runs have been recorded for this message yet.`
- Missing tenant / empty scope: `No inbound records match these filters. Clear the filters or wait for the next inbound message.` (the tenant-required-or-empty contract renders `[]`, never a cross-tenant leak — mirrors `OperatorLive.load_deliveries/1` line 338)
- Routing-trace card heading: `Routing trace` — sub-label: `Why this message did not match`
- Routing-trace failing-clause reason (examples, composed not generic):
  - Recipient mismatch: `Recipient did not match: expected {expected}, message envelope was {actual}.`
  - Subject mismatch: `Subject did not match: expected {expected}, message subject was {actual}.`
  - Header mismatch: `Header {name} did not match: expected {expected}, message had {actual}.`
  - Missing header: `Header {name} was required by this route but the message had no such header.`
- Routing-trace legend: `Each route matches by AND across its clauses: any = no constraint, an exact value matches by string equality, and ~r/…/ matches by regular expression.`
- Evidence card redacted default: `Raw source redacted. Revealing the raw provider payload requires the reveal_raw capability.`
- Evidence reveal denied (brand-voice, specific): `Raw source not revealed: the reveal_raw capability is not granted for this operator.`
- Replay blocked — not authorized: `Replay blocked: this action is not authorized for the current operator.`
- Replay blocked — stale auth: `Replay blocked: recent authentication is required before replaying.`
- Replay blocked — mailbox missing (IADM-06 verbatim example): `Replay blocked: mailbox module not found.`
- Replay success: `Replay recorded. A new replay run was appended to this message's timeline.`
- Suppression flag (IOPS-05, surfaced in detail header): `Sender suppressed: this message was flagged, not bounced, to preserve diagnostic signal.`

No vague language. Every error states the problem AND the recovery path or reason.

## Implementation Notes

- Reuse current admin primitives/classes directly: `card`, `badge`, `btn`, `join`, `rounded-box`, `bg-base-*`, `text-secondary`, `min-h-11`, `Components.icon/1`, `Components.flash/1`, and the existing toast/modal chrome.
- `InboundLive` is a sibling of `OperatorLive`, not a refactor of it — clone the shell, do not couple the two LiveViews.
- Tenant-required-or-empty is a structural correctness invariant: every inbound query must go through `Mailglass.Tenancy.scope/2`; an empty/blank tenant returns `[]`. (ROADMAP "Hardest sub-tasks" suggests a Credo check that no `MailglassAdmin.Inbound*` module queries inbound tables without `Tenancy.scope/2` — out of scope for the UI contract but noted.)
- Routing-trace verdict MUST be computed from `MailglassInbound.Router.Matcher` internals (e.g. `matches_route?/2` + per-clause re-evaluation) so the displayed pass/fail matches real matcher behaviour — do not re-implement matcher semantics in the view.
- `:reveal_raw` and `:replay_inbound` are new capability ATOMS passed to the existing `MailglassAdmin.Auth.authorize/3` adapter seam (action type already accepts `atom()`). No new auth module, plug, or behaviour callback.
- `inbound_record_inserted/1` is a new typed builder in `MailglassAdmin.PubSub.Topics`, `mailglass:`-prefixed, per-tenant. All subscribe/broadcast goes through the builder — no literal topic strings (LINT-06).
- Favor server-rendered LiveView updates over client state. This phase must build with `mix mailglass_admin.assets.build` (zero Node). No charting/animation libraries.
- PII discipline: never render unmasked recipient/sender by default; never put PII in any telemetry the LiveView emits; raw payload stays redacted until `:reveal_raw` is granted (raw_payload/raw_mime are `redact: true` in the schema).

## Decisions Made Without Asking (rationale)

Per the project's standing preference (research-driven recommendations; only ask the user for VERY impactful, non-inferable decisions), the two reserved questions were decided from codebase evidence rather than asked:

1. **Routing-trace visual model** — decided as a per-route bordered card with a three-column clause table (Dimension / Expected / Actual) plus check/x markers and first-failing-clause emphasis. Rationale: `Router.Route` has exactly four fields and `Router.Matcher` has exactly three matcher kinds with AND-semantics, so the diff is fully structured; the existing timeline component already establishes the bordered-card + colored-marker + badge language to reuse. A table is the most legible rendering of finite, labeled clause pass/fail and needs zero new primitives.
2. **Default PII-redaction of raw provider source** — decided as default-redacted + capability-gated reveal. Rationale: `InboundEvidence.raw_payload`/`raw_mime` are `redact: true` in the schema, the project's PII rules forbid casual exposure, the phase explicitly defines a `:reveal_raw` capability gate, and the existing `mask_recipient/1` masking pattern is the established treatment. Default-collapsed-redacted is the only option consistent with the locked system.
