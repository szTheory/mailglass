Replacement, in the required lane, always executed:
  1. Shape: `source.git_sha` is 40-hex and its first seven characters are the sha7 in `catalog_id`.
  2. Internal binding: `source.bundle.sha256` equals the sha256 of the served `css-<md5>` asset in the same manifest, and `source.bundle.git_blob_sha` equals that asset's `git_blob_sha`. The driver additionally refuses to write the manifest unless both recorded blob shas equal `git rev-parse <git_sha>:<path>` at capture time (full clone there).
  3. Repository binding, time-scoped: the test reads the checkout's `mailglass_admin/priv/static/app.css` and `mailglass_admin/lib/mailglass_admin/layouts/root.html.heex` bytes and computes sha256 plus the git blob sha1 (`sha1("blob <size>\0" <> bytes)`) in Elixir. If both equal the recorded values the catalog is LIVE: a `superseded.json` must not exist (a marker on a live catalog is a false claim). If either differs the catalog is SUPERSEDED: `<catalog_id>/superseded.json` must exist with the closed schema `{schema: "mailglass.before_catalog.superseded.v1", catalog_id, superseded_by {bundle_sha256, root_layout_git_blob_sha}, superseded_in, reason}` (`superseded_in` and `reason` non-empty strings naming the change that last moved the bytes), its `catalog_id` must equal the directory, and — recomputed on every run — `superseded_by.bundle_sha256` must equal the checkout's CURRENT app.css sha256 and `superseded_by.root_layout_git_blob_sha` must equal the checkout's CURRENT root layout blob sha1. Any other marker is red: missing, malformed, unknown key, wrong catalog_id, or well-formed hex that names bytes other than the checkout's (which includes a marker equal to the recorded values, and a once-valid marker after a further bundle or root-layout change). The red message prints the catalog_id, the checkout's current two values and the two fixes (recapture under a new catalog_id, or set `superseded.json` `superseded_by` to the printed values in the same change). The marker is NOT a one-time record: it tracks the current bytes, so every later bundle or root-layout change costs exactly one marker update in the same PR, which is the reviewable act; the catalog PNGs, `cases.json` and `manifest.json` stay immutable.
  Why this route: (a) it needs only working-tree bytes, so it is fail-closed in a depth-1 checkout with no skip branch; (b) it never needs the source commit object, so it survives the squash-merge (origin/main `c94fcdda` #317 has a single parent; after merge the source SHA is not in main's history); (c) a Phase 181 bundle change goes red until that PR adds `superseded.json` naming the new bytes, and every later bundle or root-layout change goes red again until its PR updates `superseded_by` — no marker ever disables the binding; (d) each branch, including the stale-marker branch, has a teeth case (Task 3); (e) no CI job or workflow edit.
