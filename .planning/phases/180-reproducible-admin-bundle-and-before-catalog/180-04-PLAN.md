- OQ3 ancestry (F8) — B1 decision: **content-identity binding plus time-scoped strict check, no git objects needed, no ci.yml change.** The previous conditional (ancestry only when the clone is full and the object exists) was skipped in the depth-1 `support_contract_admin` checkout, so the required lane passed on shape alone. Replacement, in the required lane, always executed:
  1. Shape: `source.git_sha` is 40-hex and its first seven characters are the sha7 in `catalog_id`.
  2. Internal binding: `source.bundle.sha256` equals the sha256 of the served `css-<md5>` asset in the same manifest, and `source.bundle.git_blob_sha` equals that asset's `git_blob_sha`. The driver additionally refuses to write the manifest unless both recorded blob shas equal `git rev-parse <git_sha>:<path>` at capture time (full clone there).
  3. Repository binding, time-scoped: the test reads the checkout's `mailglass_admin/priv/static/app.css` and `mailglass_admin/lib/mailglass_admin/layouts/root.html.heex` bytes and computes sha256 plus the git blob sha1 (`sha1("blob <size>\0" <> bytes)`) in Elixir. If both equal the recorded values the catalog is LIVE: a `superseded.json` must not exist (a marker on a live catalog is a false claim). If either differs the catalog is SUPERSEDED: `<catalog_id>/superseded.json` must exist with the closed schema `{schema: "mailglass.before_catalog.superseded.v1", catalog_id, superseded_by {bundle_sha256, root_layout_git_blob_sha}, superseded_in, reason}`, its `catalog_id` must equal the directory, at least one `superseded_by` value must differ from the recorded value, and both must be well-formed hex; otherwise red with a message naming the two fixes (recapture under a new catalog_id, or add the marker). The marker is a one-time record, so later bundle changes after it need no further edit.
  Why this route: (a) it needs only working-tree bytes, so it is fail-closed in a depth-1 checkout with no skip branch; (b) it never needs the source commit object, so it survives the squash-merge (origin/main `c94fcdda` #317 has a single parent; after merge the source SHA is not in main's history); (c) a Phase 181 bundle change goes red only until that PR adds `superseded.json` in the same change, which is the deliberate, reviewable act the stop line wants, and never again afterwards; (d) each branch has a teeth case (Task 3); (e) no CI job or workflow edit. The marker is a sidecar, not a manifest edit, because Phases 182-183 cite the manifest sha256 (D-17) and editing the manifest would break those citations. `fetch-depth: 0` was rejected: it adds a full-history fetch to every run of a required job and still cannot prove ancestry after squash-merge (constraint b). The strict `git merge-base --is-ancestor <git_sha> HEAD` and the render-input diff are still run once when the PR opens and recorded as evidence (backstop truth). This refines D-24's "ancestor of HEAD" for the squash-merge convention; it does not drop it.
