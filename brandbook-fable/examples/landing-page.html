Transactional email for Phoenix, made visible.

mailglass composes on Swoosh and ships the framework layer teams rebuild by hand: HEEx-native components, a LiveView preview dashboard, normalized webhook events, suppression lists, and an append-only event ledger.

# mix.exs
{:mailglass, "~> 1.5"},
{:mailglass_admin, "~> 1.5", only: [:dev]}
mix deps.get
mix mailglass.install
mix ecto.migrate

The installer generates a mailing context, the three-table migration with its immutability trigger, router mounts for the dev preview and webhook plug, and a default mailable and layout.

What ships in the box

Preview before you send

Every Mailable renders in a dev dashboard: device widths, dark mode, HTML, text, raw source, and headers, with live-editable assigns.

One event vocabulary

Provider webhooks normalize into a single stream — queued, sent, bounced, deferred, delivered, complained — the same names whichever provider reported them.

Suppressions that hold

Hard bounces and complaints project Suppression records automatically. A suppressed recipient is blocked before dispatch, and the error names the cause.

One-click unsubscribe

RFC 8058 List-Unsubscribe headers with signed tokens — the unsubscribe mechanics inbox providers now expect, generated for you.

An audit trail you can trust

Deliveries and Events land in an append-only Postgres ledger. A trigger raises on UPDATE or DELETE — history is evidence, not state.

Deliverability, diagnosed

mix mail.doctor checks SPF, DKIM, DMARC, MX, and BIMI against DNS, and answers cannot_verify when DNS alone cannot prove a claim.

A mailable is just a module

Define the email next to the code that triggers it. The same definition renders in the preview dashboard, in tests against the fake adapter, and in production through whichever Swoosh adapter you configure.

defmodule MyApp.UserMailer do
  use Mailglass.Mailable, stream: :transactional

  def welcome(user) do
    new()
    |> to(user.email)
    |> from({"MyApp", "support@example.com"})
    |> subject("Welcome to MyApp")
    |> html_body("<h1>Welcome to MyApp</h1>")
    |> text_body("Welcome to MyApp")
    |> Mailglass.Message.put_function(:welcome)
  end
end

Send it synchronously, in the background, or as a batch:

MyApp.UserMailer.welcome(user) |> Mailglass.deliver()
MyApp.UserMailer.welcome(user) |> Mailglass.deliver_later()
Mailglass.deliver_many(Enum.map(users, &MyApp.UserMailer.welcome/1))

Dispatch is not delivery: dispatched means handed to the provider; delivered means the destination accepted it. mailglass records both as separate Events, so "did it really go out?" has an answer.

Why not just Swoosh?

Keep Swoosh. mailglass composes on it — it does not replace it. Swoosh is the transport: you still choose its adapter for your provider. mailglass is the framework layer above the transport, the part teams end up writing by hand on every project.

Swoosh, kept

  • Adapters for the major providers
  • The mailer and its delivery path
  • Local development mailbox
  • Test assertions for sent mail

mailglass, added

  • Mailables with HEEx components and Outlook fallbacks
  • The LiveView preview and admin dashboard
  • Delivery records and provider-normalized Events
  • Suppression lists and signed one-click unsubscribe
  • Multi-tenant routing and an append-only ledger

If Swoosh alone already covers your needs, use Swoosh alone. mailglass is for the teams who keep rebuilding the layer above it.
